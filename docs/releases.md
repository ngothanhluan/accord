# Release notes

Each section lists what changes for tickets in flight and for repositories pinned to an older accord. A release pull request copies the `## Unreleased` section into its `release:` commit body and renames the section to the release version.

## Unreleased

- A new path in a plan names a model file (from 0.6.0). A path a plan task creates is written on its `files:` line as `<path> (new, like <path of an existing file of the same kind>)`, or `<path> (new, no model: <reason>)` when no file of that kind exists yet. `accord gate plan` refuses a bare `(new)` (`gate.task-model-missing`) and a model that does not exist at the plan baseline (`gate.task-model-unknown`), each naming the task and the path. A ticket claimed before 0.6.0 keeps the bare `(new)` and answers as before; a repository pinned to 0.5.x keeps its answers, and the planner and plan checker it has installed, until `accord upgrade`. The planner and the plan checker also ask for the valid spellings of a `risk:parsing` task's input and for a `## Failure modes` section after the last task (the likeliest failures no task's tests exercise); that adds no gate rule. Every tool that installs accord agents gets the asks (today Claude Code only).
- A planner, verifier or debugger that stalls leaves what it finished (from 0.6.0). These three agents write their file section by section behind the line `<!-- accord: unfinished -->`, which they write first and remove last: `plan.md` task by task, `verification.md` block by block, `debug.md` part by part. `accord gate plan` refuses a `plan.md` that carries the line (`gate.plan-unfinished`) and `accord gate done` a `verification.md` that does (`gate.verification-unfinished`, part of the locked floor, so no strictness key lowers it). `accord anchor` prints an `Unfinished:` line: resume the planner, resume the verifier when `verification.md` was written at the commit now checked out or when nothing outside `accord/tickets/<id>/` changed since (the verify stage commits the partial file before `accord worktree sync`, which moves HEAD), start the verifier over when product code changed since, or resume the debugger. The line counts on any line of the body of a `plan.md` or `verification.md` that is outside a fenced code block, so a heading above it hides nothing, while a file that quotes it inside a fence (pasted test output, an example) is not refused; in `debug.md` it is the first line under the last `## Episode <n>` heading, with earlier episodes kept above it, and an episode is open while no `## Resolved` heading follows its `## Episode <n>` heading. The plan, verify and debug stages then dispatch the agent in resume mode, which keeps every finished section and writes the rest; a verifier on another commit starts over, and a debugger dispatched on one hypothesis in a parallel round still writes nothing. The debugger gains the `Edit` tool to append without rewriting. The two rules apply to every ticket, whatever its claim pin: this is a deliberate exception to the rule that a ticket keeps the rules it was claimed under, because only 0.6.0 agents write the line, so a ticket claimed earlier cannot be refused wrongly, while exempting it would let a stalled agent's half-written plan or verification pass the gate after an upgrade. A repository pinned to 0.5.x keeps its answers, skills and agents until `accord upgrade`. Every tool that installs accord agents gets the agent text (today Claude Code only); the skills render for all four tools.
- The executor writes a report file and `accord task-done` checks it (from 0.6.0). `accord brief <id> <n>` prints `Report file: <path>` (`.accord-reports/<id>/task-<n>.md` under the checkout) and, under it, the report contract, so an executor in any of the four tools learns the lines task-done checks; it also clears the task's old report. The folder holds its own `.gitignore`, so a report never shows in `git status` or in `accord review-package`. `accord task-done` refuses a task whose report is missing, older than HEAD's commit, without a `red reason:` line (the behaviour the failing test showed missing; `none`, `n/a` and a placeholder do not count; a task with no red test of its own writes `red reason: no red test — <why>`), or without a `self-review:` line that has text after each of `missing:`, `extra:` and `misread:` (`none` is text); it prints each reason and records nothing. Known limit: the CLI checks that the lines exist, not that they are true; the reviewer and the verifier stay the check on that. A ticket claimed before 0.6.0 records with no report, and its `accord brief` prints what 0.5.x printed: no `Report file:` line, no contract, no file written; a claim that cannot be read gets the 0.6.0 behaviour. A repository pinned to 0.5.x keeps its answers, brief and skills until `accord upgrade`.
- The executor checks its own work and fixes only what it caused (from 0.6.0). The `accord-executor` agent names the red reason (the behaviour the failing test showed missing, not an error in the test), reads its diff against the brief and writes `self-review: missing: …; extra: …; misread: …` and `concerns:` into its report. When it fixes review or debug findings it changes only what its own change caused (anything else goes under `deferred:`), lists `places checked: <n>: <path>[:<line>], …` for each finding, reverts its own red fix with `git revert` (never a reset), and returns `BLOCKED: conflict` when the brief and the code disagree. The build skill re-briefs a task refused for its report and sends a conflict to the owner. Every tool that installs accord agents gets the agent text (today Claude Code only); the skills render for all four tools.
- A fix closes only when the next reviewer says so (from 0.6.0). A review finding written `fixed in <sha>` carries `checked: <path>[:<line>], …`, the places the fix checked (a placeholder such as `none` or `<path>` is no place) (copied from the executor's `places checked:` line; in lane S, the places the session checked itself), and the re-review answers it: the next round's reviewer is given the findings it re-checks and answers each `<r>.<n>: ADDRESSED <path>:<line>` or `<r>.<n>: NOT ADDRESSED <path>:<line> — <what still fails>`, which the session writes on the finding as `addressed: <path>:<line>` or `not addressed: <path>:<line>`; a NOT ADDRESSED finding is carried into the next round (`carried from <r>.<n>`). `accord round` and `accord gate done` refuse, in lane M and in lane S, a fix with no `checked:` mark (`gate.fix-places-missing`); a fix with no answer once a later round of its cycle exists (for the last round of a cycle a return from verify closed, once round 1 of the next cycle exists: that round answers it), an uncarried NOT ADDRESSED finding, or a last round whose fix no re-review has answered (`gate.fix-not-addressed`); and a re-review finding outside the fix diff left open (`gate.fix-outside-open`). Every fix round gets a re-review, a Should-only one included (before 0.6.0 the test command alone checked a Should-only fix), and converged means no Must or Should open and every fixed finding answered `addressed:`. A re-review finding outside the fix diff (a Must or Should in a file the previous fix did not change, or located nowhere) is written `deferred` with its `## Deferred` line and starts no round, from round 2 and in lane S too; a `test:` or `command:` mark no longer keeps it open, and a `risk: security` or `risk: data-loss` finding is never deferred. A ticket claimed before 0.6.0 and every version 1 record keep their rules, and a repository pinned to 0.5.x keeps its answers, skills and agents until `accord upgrade`. The reviewer's re-review mode installs in every tool that installs accord agents (today Claude Code only); the record rules and the skills apply in all four tools.

## 0.5.1 — 2026-11-16

- Argument hints: every installed skill now carries `argument-hint` in its frontmatter, so the slash-command picker shows what to type after the name: `/accord [request | continue <id> | pick-up <id> | upgrade]`, `/accord-intent`, `/accord-approach`, `/accord-plan`, `/accord-build`, `/accord-review` and `/accord-verify` `[ticket id]` (the ticket of the current branch when left out), `/accord-debug [ticket id] [failure]` and `/accord-designer <ticket id>`. It is the one frontmatter key outside the Agent Skills spec that accord ships: two runtimes show it, the other two ignore it, and the same text still goes into both `.claude/skills` and `.agents/skills`. A spec-strict packager or uploader refuses the key; an installed skill is never packaged or uploaded. Repositories pinned to an older accord get the hints at `accord upgrade`, which regenerates the skills.
- Repository scripts need `accord trust` (new command; replaces the default-branch check on `tracker.command` that 0.5.0's notes describe): a script the repository declares, `tracker.command` under `tracker.adapter: script` and `git.sync`, no longer runs by itself. `accord status` prints one `tracker script: tracker.command "<command>" ...` line on stderr and shows the tracker column empty (exit code and verdicts do not change); `accord worktree sync <id>` refuses with the same sentence and exit 2 before any fetch; Continue leaves the branch as it is and ends its `behind:` line with `git.sync is not allowed to run here yet - run accord trust in "<ticket worktree>" to see what it covers, then accord trust git.sync@<the digest it shows> there`. The sentence says why the script did not run (never allowed, another command, or which covered files changed), what an allow covers, and the checkout to run `accord trust` in, because the files are read from that checkout: Continue checks the ticket's worktree, not the checkout it runs from, and it checks and runs the `git.sync` of the ticket's worktree (the one `accord worktree sync <id>` runs there and `accord trust` there shows), so the allow the line asks for is the one that unblocks the next Continue; when the worktree's `accord/config.yml` is missing or does not load, the checkout's own `git.sync` is used, under the same check. `accord trust` alone shows each declared script, with its command, a digest of what it covers (`(digest <16 hex characters>)`), what an allow covers (and the files themselves when there are at most 20) and the files that changed since its last allow, and allows nothing. `accord trust git.sync@<digest>`, `accord trust tracker.command@<digest>`, or both, with each digest as the preview printed it, allow only the scripts named and only the content that was shown, and print the same block: a script named without a digest, or whose covered files changed after the preview so the digest no longer matches, exits 2 and nothing is written, so a file an agent or a pull edits between show and allow is never bound unread, and allowing the sync script after reading its diff never also allows a changed tracker script; `accord trust --revoke` withdraws every allow, and `accord trust --revoke git.sync` that script's only. Each command and covered path is printed with its control characters (ESC, the other C0 and C1 controls, bidi and zero-width marks) written as `<U+001B>` and the like, so a command cannot hide its start from the person reading it. The allow is a local file, `accord-trust.json` inside the repository's common git directory (`git rev-parse --git-common-dir`): every worktree of the clone shares it, it is never committed and nothing under `accord/` changes. It holds up to 16 allows per script, one per command and set of file contents, so two worktrees whose script files differ each keep their own allow and going back to content you allowed before needs no new allow. Allows and revokes take a lock file beside the record (`accord-trust.json.lock`; one left by a killed process is taken over after 60 s) and apply their change to the record as it is on disk, so allows made in parallel worktrees both land and an allow never brings back what a revoke withdrew; an entry accord cannot read is ignored, read as no allow, with one `warning:` line from `accord trust`, and from `accord status` when it checks a tracker script. An allow is bound to the command text and to the git content id of every tracked file the command reaches, as it is in the working tree: for a file git sees unchanged, the id the index holds (the blob of a file of any size, the target text of a symlink, the commit of a submodule); for a changed file, the id `git add` would give it (a checked-out submodule counts by the commit it has checked out). That boundary is stated, not promised. A check that finds no allow of the command to compare with (`accord status`, Continue, `accord worktree sync`) computes no digest at all. A tracked file the command names, or one a word becomes with an extension that Node, Windows PATHEXT or an interpreter adds (`node scripts/tracker` runs `scripts/tracker.js`; `.mjs`, `.cjs`, `.cmd`, `.ps1`, `.sh`, `.py` and the like), binds the whole directory of that file, every tracked file below it at any depth; a file at the repository root binds every tracked file outside `accord/`, so a script kept in a folder of its own is asked about less often. A tracked directory the command names binds everything below it, and `node .` binds `package.json` and, as above, the directory of the file its `main` names (`index.js` when it names none). `npm run <name>` (and `npm run-script`, `npm test`, `pnpm run`, `yarn run`, a bare `yarn <name>`, `bun run`) binds `package.json` and the runner's own files (`.npmrc`, `.yarnrc.yml`, `.pnp.cjs`, `.yarn/releases/` and the like), and follows the package.json script, with its `pre` and `post` scripts, as a command of its own. When the command reaches no tracked file, the root manifests an interpreter or task runner reads (`package.json`, `Makefile`, `justfile` and the like) are bound. Paths are matched without regard to case on every system and in every path component, so `Scripts/tracker.mjs` on Windows binds `scripts/`, and an index entry `Scripts/lib.mjs` beside `scripts/tracker.mjs` is held by `scripts/`. A bare word with no `/` or `\` is tried with an added extension only where a script stands: the word that starts a command, or the first word that is not an option or an `A=1` assignment after it or after a launcher (`node`, `python`, `bash`, `env`, `npx` and the like); anywhere else it matches a tracked file only as written, so the `main` of `--since main` never reaches a root `main.py` and with it every tracked file. accord checks only the files `accord trust` lists; anything else the command loads is not checked, and every `accord trust` output says so in one line. Not checked: other runner forms (`node --run`, `npm -w`/`--workspace`, `--prefix` and the other workspace options, `bash -c` or `sh -c "..."` and `cmd /c "..."`, `node -e`, `python -m`, `npx` and `npm exec`, the `npm install` lifecycle scripts, `.npmrc` `node-options`); a file loaded from outside the listed directories (an `import '../lib/x.mjs'`, a path read from a config file); the scripts a `make` or `just` target runs (the Makefile is bound only when the command reaches nothing else); a path built from an environment variable (`$ACCORD_ROOT/scripts/x.mjs`); a package.json script chain deeper than 8; `npm start` with no `start` script, which runs `server.js`; a command word and a tracked name that differ only in Unicode normalization (macOS); and anything outside the repository (programs on PATH, installed dependencies in `node_modules`). When the command, or a package.json script it follows, uses one of the forms above that accord can spot, `accord trust` adds a `not followed:` line and the refusal adds `(not followed here: ...)`, so a cover of `package.json` alone never reads as complete. Whoever allows a script must review the pull request that changed it. A branch that changes a covered file, with the command text unchanged, is not run until you allow it again; a branch that changes only a file outside the cover is run. The built-in adapters (`none`, `github-issues`, `jira`, `linear`) run no repository script and are unchanged; the Jira credential still goes only to the `tracker.url` the default branch names. That comparison needs a default branch ref (`origin/HEAD`, `origin/main` or `origin/master`, else a local `main` or `master`): in a clone with none, such as one made with `git init`, `git remote add` and `git fetch` of a repository whose default branch has another name, there is nothing to compare with and the working `url` stands; and a `url` you set with `accord config set` is not sent a credential until it is committed to the default branch. Because the pin on `tracker.command` is gone, a command that only a branch holds runs once you have allowed it there. A repository that uses neither script is not affected. Never allow a script you have not read: run `accord trust` first and read the files it names, since the script runs as you, with your whole environment.
- `accord config set` stores the value as typed. A value is never unwrapped: `'"./my scripts/sync.sh"'` and `'"C:\tools\build.cmd"'` are stored with their quotes and backslashes. The onboard skill passes the bare value (`accord config set git.merge 'squash'` for the printed `"squash"`).
- `accord upgrade` no longer writes `ruleset` into any ticket (this retires the backfill described under 0.5.0). A ticket approved on the default branch is still in flight on its claim branch, where the next `accord approve`, `gate ready` or plan write appends to the same end of the frontmatter, so the line conflicted at the next merge, and the ticket, not done, made the upgrade pull request's `gate done` loop fail. While the claim commit is reachable the claim fact already gives the rules the ticket was claimed under. `ruleset` is written into the branch's own copy (`backfilled: <id> ruleset <pin>`), before a rebase or a team script can rewrite the claim commit, only by the first Continue (stages intent to review) or `accord worktree sync <id>` (at verify) after the upgrade that takes the default branch into the ticket branch; one that takes nothing in, because the branch is not behind or Continue leaves it alone and prints `behind:`, writes nothing. In a repository that declares `git.sync` that waits for the allow: Continue leaves a branch alone and `accord worktree sync` refuses until `git.sync` is allowed in the ticket's worktree (`accord trust` there, then `accord trust git.sync@<digest>`), and the next Continue or `worktree sync` that takes the default branch in after it writes `ruleset`. Until then, merge such a ticket with a merge commit, or allow and sync it first: a squash or rebase merge drops the claim commit, and a ticket with neither a claim fact nor a `ruleset` is judged by the pin of `accord/config.yml`, that is by the 0.5.x rules.
- The rules a ticket was claimed under (corrects the 0.5.0 note on `ruleset`): the five rules that read the claim pin take the claim fact from git first (its first `ruleset`, else its pin), and a failed claim read applies the new rules. The ticket's own `ruleset` field decides only when git holds no claim fact and the ticket is done (it carries `verified_hash` and `verified_commit`), which is the squash or rebase merge of a finished ticket that dropped its claim commit. A ticket that is not done, with no claim commit, takes the pin of `accord/config.yml`, so a hand-edited field cannot lower the rules of an unclaimed ticket before `accord approve`.

## 0.5.0 — 2026-11-15

Release 0.5.0 gives a team settings for how it merges, names its tickets and commits, how strict it is and what a ticket holds, which tracker it reads, and how it sets accord up on an existing repository (five groups below). A repository that sets none of the new keys behaves as in 0.4.1, except for the `ruleset` line a claim now writes into each new ticket. The rule that reads the ticket's own `ruleset` has a cut-off constant in `packages/core/src/round/pin.ts`, `RULESET_FROM`, which holds the first release that ships the rule and reads `0.5.0`.

- Tickets in flight: a ticket claimed under 0.4.x keeps the claim-commit reader of 0.4.1 (the five pin-reading rules read the `accord:` pin at its claim commit) until `accord upgrade`, or its first `accord worktree sync` or Continue, writes `ruleset: "<claim pin>"` into it. From then on a squash merge or a rebase merge, which drops or rewrites the claim commit, keeps the ticket's rules. A ticket claimed under 0.5.0 or later carries `ruleset` from its claim. A ticket that is done or has no claim branch is left as it is.
- Repositories pinned to 0.4.1: they keep 0.4.1's answers and skills until `accord upgrade`, which moves the pin, regenerates the skills and backfills `ruleset` into the tickets in flight. Nothing in this release moves a pin by itself, and the repository's own pin moves after publish through `accord upgrade`. A config that uses one of the new keys (`git`, `ids`, `commits`, `strictness`, `template`, or a tracker adapter other than `none` and `github-issues`) needs 0.5.0 or later, and an older accord refuses it.

Teams that merge pull requests by squash or rebase (ST-LN-96, group 1). Nothing below changes a repository that sets no `git:` key and keeps merging with merge commits, except the `ruleset` line the claim adds to a new ticket.

- Ruleset per ticket (from `RULESET_FROM`, 0.5.0): the claim writes `ruleset: "<pin>"` into the ticket, in the claim commit (and `accord new ticket <id> --worktree` writes it into the ticket it commits), where `<pin>` is the `accord:` pin of the repository at that moment. A claim under a pin below 0.5.0 writes nothing and stays an empty commit. This is a one-way addition to the published ticket schema (D-02): a ticket that carries the field needs 0.5.0 or later, and an older accord refuses it, so a repository pinned to 0.4.1 never gets the field until `accord upgrade`. The five rules that read the claim pin (`DISCUSS_FROM`, `APPROACH_CAP_FROM`, `PLAN_FORMAT_FROM`, `PLAN_CAP_FROM` and `PLAN_GROUNDS_FROM`) now read the ticket's `ruleset` first, so a squash merge or a rebase merge, which drops or rewrites the claim commit, no longer changes the rules a ticket was claimed under. A ticket without the field keeps the claim-commit reader of 0.4.1, and a `ruleset` that is not a plain x.y.z is ignored.
- `gate.ruleset-changed` and `gate.ruleset-missing` (from 0.5.0): the field is never edited by hand. While the ticket's claim commit is reachable, `accord gate ready`, `gate plan` and `gate done` (lanes M, S and R) compare the field with the first `ruleset` the branch wrote, which is the one in the claim commit or, for a ticket claimed before 0.5.0, the one in the backfill commit below, and a different value is an error that names both. A ticket claimed before 0.5.0 that no commit ever gave a `ruleset` is compared with the pin at its claim commit, as before. `gate.ruleset-missing` fires only when the ticket held a `ruleset` at the reachable claim commit and has none now. A rebase moves the config pin at a rewritten claim commit but replays the ticket's own line, so a rebased ticket passes. After a squash merge no claim commit is reachable and both rules are silent: the ticket is done by then.
- Backfill (from 0.5.0): a ticket in flight at the upgrade has no `ruleset`. `accord upgrade` writes `ruleset: "<pin at its claim commit>"` into every ticket on the default branch that has a lane, is not dropped, is approved there (an `approved_hash` or an `ac_hash`) and has no `ruleset`, is not done there, and has a `claim: <id>` commit on a claim branch (the `branch` template, local or on origin); the value is the `accord:` pin of `accord/config.yml` as committed at that claim commit, and it goes into the one `upgrade/<version>` commit, which the upgrade's own lint pass checks. Done, unclaimed, already written and unapproved tickets are left as they are: a draft's copy on the default branch has no rules to pin yet, its file on the claim branch gets the field at its first sync, and a field written into the draft would conflict with the branch's approve and fail the pull request's gate. A ticket whose claim pin cannot be read, because the blob is missing or the pin is not a plain x.y.z, gets no field and one `warning: <id>: ruleset not written, ...` line on stderr, and the exit code does not change. A ticket whose file is only on its branch gets the field at its first sync instead: `accord worktree sync <id>` and Continue write `ruleset: "<claim pin>"` in one commit named `ruleset: <id> from its claim commit` and print `backfilled: <id> ruleset <pin>`, once the branch carries (or is about to take in) a pin of 0.5.0 or later. Under `git.merge: rebase` or `git.sync` the commit is made before the sync, while the claim commit is still reachable, and a refused sync takes it off again. A branch pinned below 0.5.0 is not given the field (its published schema refuses it), and a ticket that lost a `ruleset` an earlier commit wrote is not backfilled: `gate.ruleset-missing` reports it.
- `git.merge` and `git.sync` (from 0.5.0, new keys of `accord/config.yml`): `git.merge` is `merge`, `rebase` or `squash` and says how the team merges pull requests into the default branch. With no key a repository means `merge`, and everything works as in 0.4.1. Under `merge` and `squash` a ticket branch takes the default branch by an ordinary merge commit, as before (accord never syncs with `git merge --squash`); under `rebase` it rebases. `git.sync` is a shell command that runs instead of the built-in merge or rebase, with the ticket, branch, base ref and root in `ACCORD_*` variables and never in the command text; a script that fails, runs past 600 s, leaves a merge or a rebase unfinished or leaves tracked files uncommitted is refused with exit 2 naming the command, and the branch is not pushed. A config with a `git:` key needs 0.5.0 or later; an older accord refuses it.
- `accord worktree sync <id>` (from 0.5.0): the primary name of `accord worktree merge`, which stays as an alias, so the installed skills and pinned repositories keep working. It takes the default branch into the ticket branch by the way `git.merge` or `git.sync` sets. A rebase prints one `rebased: <old12> -> <new12>` line per commit and pushes with `--force-with-lease --force-if-includes`; a refused push prints the command to run by hand and exits 0. A conflict aborts the rebase and leaves the branch as it was. The `accord-verify` skill and `accord/worktree.md` now call it and say the way is set by `git.merge`.
- `accord gate done` after a rewrite (from 0.5.0): when the commit a tick or the review was recorded against is no longer in the gated commit's history (a rebase or a team script rewrote it), `gate done` compares the contents of the ticket's files instead of the sha. Unchanged contents keep the verification; changed contents refuse it and name the files; a recorded commit that is not in the clone refuses it and says to verify again. The comparison applies only after such a rewrite: a commit made after verify, a merge of the default branch included, is judged as in 0.4.1 and still asks for verification again. `accord status`, `accord anchor` and the dashboard say what `gate done` says.
- Re-bind at accord's own rebase (from 0.5.0): when `accord worktree sync` itself rebases (`git.merge: rebase`, no `git.sync`) and no ticket file changed, it moves `verified_commit` and the `commit:` of `verification.md` to the rebased commit in one records-only commit (`verify: <id> rebound after rebase`) and prints `rebound:`, so the pull request's `gate done` passes in CI after the force-push. A changed ticket file, a rebase by hand and a `git.sync` rebase are not re-bound: CI's `gate done` finds the old commit missing and verifies again, and accord prints `verify again:` with the reason.
- Cleanup after a squash or rebase merge (from 0.5.0): `accord worktree clean` deletes a ticket branch that was squash- or rebase-merged even when the default branch edited the same lines afterwards, when every blob the branch wrote is found in the default branch's history. A deletion, a rename, a mode change, a link, more than 200 paths, a blob the default branch never held, or any git failure keeps the branch.
- Repositories pinned to 0.4.1: nothing changes until `accord upgrade`, which moves the pin, regenerates the skills and backfills `ruleset`. Tickets claimed under 0.4.1 keep the 0.4.1 rules, now also through a squash or a rebase merge once they carry the field.

Teams that set their own ticket ids and commit subjects (ST-LN-50, group 2). Nothing below changes a repository that sets no `ids` key and no `commits` key: its ids and its subjects are today's, byte for byte.

- `ids` (from 0.5.0, a new key of `accord/config.yml`): `ids.pattern` is a team id pattern built from literal characters (`A-Z a-z 0-9 . _ -`) and the tokens `{type}`, `{initials}` and `{n}` (`{n}` exactly once); accord compiles it into a bounded matcher, and a raw regular expression is never accepted. `accord new ticket` then assigns the next `{n}` for that rendered head, one above the highest id any ref of the clone knows, never reused, and `accord lint` checks ids against the pattern. `{type}` renders `ids.types` (default `ST`, `BUG`, `EP`); a pattern with no `{initials}` needs no `people` table. `ids.mode: tracker` takes the key of the Jira or Linear issue instead: `accord new ticket <KEY>` writes that id, refuses a malformed key, a project that `ids.projects` does not list, and a key a ticket, a record folder, a claim or the history of any ref already uses (exit 2, nothing written), and assigns no id of its own. With no `ids` key a repository means today's `ST-`, `BUG-`, `EP-<initials>-<n>` while `people` exists and no convention without it. Existing ids are never renamed. A config with an `ids` key needs 0.5.0 or later; an older accord refuses it.
- `accord config get|set|unset|check` (from 0.5.0): edits `accord/config.yml` from the command line. A key path is resolved against the published config schema (`people.dev@example.com` and `models.reviewer.final.model` resolve, an unknown key is refused by name), the whole result is validated against that schema and written once, and every refusal exits 2 and leaves the file byte-identical. It never commits; the change is yours to commit. Changing the id convention (`ids` or `people`) through it keeps every ticket in flight working: each id the clone knows (tickets, record folders, claims and ids in history on every ref) that breaks the new convention is appended to `legacy_ids` in the same edit, and the command prints one `legacy_ids +<id>` line per id; the list and the new pattern go in together, so a refused edit writes neither. `accord config check` reports every finding in the file and writes nothing.

Then `accord gate ready` names the git error in its discuss finding, `accord round --approach` names it in the refusals the cap rules give (past the cap, an ended loop, a blocked approval), `accord approve` names it when it refuses on a blocking finding, and `accord show <id> --approval --short` names it in its `## Blocking findings` part; the cap itself (the round number and the cap it prints) applies the new rules without naming it. For the plan rules, every finding of `accord gate plan` under the format rules and `gate.plan-rounds`, and every answer of `accord round --plan` (the next round, as a `Note:` line, a stop and a refusal), adds the git error and `the claim pin could not be read, so the new plan rules apply`. Six rules follow the claim: the discuss rule, the approach cap with its approval block, the plan format, the plan cap with its count stop, the plan checker at round 1 and the plan's round-1 grounds, so a ticket claimed before the upgrade keeps no discuss stage, five approach rounds, the old plan format, five plan rounds and the 0.4.0 round-1 dispatch (with the security critic widened to `sensitive:` paths, the one deliberate change) until it is done. Two rules follow the record or the plan instead, and the upgrade changes them for such a ticket once a record or a plan begins after it: the grounds rule (round 2 and Must, `GROUNDS_V2_FROM`, and the plan fix scope) reads the pin at the first round of the record (`review.md`, `plan-review.md` or `approach-review.md`), except that the plan record of a ticket claimed under 0.4.1 or later is asked from round 1 by its claim pin, and the plan size rule (`PLAN_SIZE_FROM`) reads the pin at the plan's baseline commit. The version 2 review record, in force since 0.3.1, is not changed by this release. A ticket claimed under 0.4.0 whose approach critique begins after the upgrade therefore keeps five rounds and its stop but is held to the round 2 grounds rule; one whose record began before the upgrade keeps the old grounds rule.
- Lane R, research (new, no cut-off constant: it applies only to a ticket written as lane R): a ticket that asks a question accord cannot answer from the code, and asks for no change, is worked in lane R. `accord new ticket <id> --lane R` writes its template with `## Question`, `## Timebox` (`<n> minutes` or `<n> hours`) and `## Token budget` (`<n>`, `<n>k` or `<n>M` `weighted tokens`). The owner sets the timebox and the token budget; the session proposes neither. `accord gate ready` passes when the three sections are written and `## Decisions` quotes the owner on both values (D-13); `ac_hash` is taken over the three sections. Lane R has no approach, plan, critic, code review or verification: `accord gate plan` refuses an R ticket as having no plan (`gate.lane-r-plan`), and `accord round`, `accord approve`, `accord review-package`, `accord brief` and `accord task-done` refuse it with exit 2. An epic is never lane R.
- `accord budget <id>` (new): prints `within budget` (exit 0) or `stop: ask owner` (exit 1) for a lane R ticket, the elapsed time from the author time of the ticket's `claim: <id>` commit (a rebase or `git pull --rebase` keeps the author time, so it does not restart the clock), the weighted tokens of the checkout's own Claude Code transcripts since that claim (fresh input 1, cache write 1.25, cache read 0.1, output 5, each message once), and the `Spent:` line the research record copies. It stops only strictly past the timebox or the budget, and then prints the question for the owner and how the answer is written. Tokens read `not measured` when no full count since the claim exists: the checkout has no transcript folder, or its earliest transcript line is later than the claim (Claude Code deletes transcripts after 30 days by default); then the time alone decides (D-20). A ticket of another lane, an allowance that cannot be read, or a ticket with no claim commit is a usage error (exit 2).
- Lane R Done: the session writes a record under `accord/research/` with its header and a `Spent:` line, and lists it under `research:` in the ticket. `accord gate done` passes an R ticket when `ac_hash` still matches the three sections, `## Decisions` still quotes the owner's values, a listed record that the branch added or changed after the ticket's claim commit holds a `Spent:` line, and the branch changes nothing outside `accord/`: every other path it changes, a deletion included, is refused and named (`gate.research-shipped`), so a research script lives under `accord/research/`. Where no claim commit is reachable, as on the default branch after a squash merge, a listed record counts when the commit that added the ticket file, or a later one, changed it. A listed record that already existed is evidence: allowed, but never the ticket's result, and its `Spent:` line is not read; when git cannot say which records changed, or the ticket has neither commit, no record counts. The timebox is compared with the larger of the record's `Spent:` time and the time git measures from the claim commit to the record's last change, both author times, which a rebase keeps (the clock `accord budget` reads), so a `Spent:` line written lower decides nothing; with no claim commit reachable the `Spent:` time alone decides, since the pull request's own gate done judged the branch; the tokens cannot be measured from git and are read as written. A record past the ticket's timebox or token budget is refused unless it holds the owner's `Owner: write now — "…"` or `Owner: extended to … — "…"` line; an extension is the new value written into the ticket with its quoted Decision and a fresh `accord gate ready` (D-14). It asks for no plan, review, verification, suite or ticks.
- Lane R in CI and the views: the CI workflow `accord init` and `accord upgrade` write reads `ac_hash` on a lane R ticket as on lane S (`[SR]`), so a ready R ticket's accord-only pull request runs `accord gate done`, and an R ticket holding `ac_hash` cannot be deleted before it is dropped. A ticket approved as lane M, L or P that moves to lane R is refused as a lane drop, as a move to S is. `accord status`, `accord dashboard`, `accord anchor` and the session line show R tickets with their stage: `intent` until `gate ready`, `research` until a listed record the branch changed since the claim holds a `Spent:` line, then `done` (on the default branch once merged, by a merge commit, a squash or a rebase; the main checkout reads a claimed R ticket's research from its branch); the session line counts `research` as in progress. `accord status --json` may now carry the stage `research`, and `accord show --json` a `question` field (the question, with `intent` left empty) for an R ticket; `accord show` prints `Question:`. The `/accord` skill (a skill change shipped by `accord upgrade`) proposes lane R, without the scout, for a request that only asks a question, and follows the new `lane-r.md` from the owner's timebox and budget to the pull request.
- Lane R and the schema: `R` is a new value of the published ticket schema's `lane`, a one-way addition (D-10): a ticket that uses it needs this release or later, and an older accord refuses it. Tickets in flight and repositories pinned to an older accord change nothing until they write an R ticket.
- Lane R known limits: `accord gate done` judges the branch it runs on, so a later pull request that changes files outside `accord/` and also edits a done R ticket's file is refused for that ticket; edit a done R ticket in a pull request that changes only `accord/`; the timebox is calendar time since the claim commit, so nights and weekends count, and the owner's answer line (`Owner: write now` or `Owner: extended to`) covers a ticket that ran past it; once past `gate ready`, no accord command brings the default branch into a lane R branch that is behind it (`accord worktree merge` runs only at verify and refuses R), so such a pull request is merged as GitHub allows; tokens read `not measured` when the ticket's session ran in another checkout, such as the main one, because only the checkout's own transcripts are read; where no claim commit is reachable, a record added in the same commit as the ticket file counts as the ticket's own, so an R ticket is queued in a commit apart from the records it lists as evidence.
