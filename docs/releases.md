# Release notes

Each section lists what changes for tickets in flight and for repositories pinned to an older accord. A release pull request copies the `## Unreleased` section into its `release:` commit body and renames the section to the release version.

## 0.8.1 — 2026-11-20

Release 0.8.1 ships Phase 8, cleanup and hardening, and the security scan fixes of BUG-LN-25 that merged after 0.8.0 (the bullets below): a guard against slow patterns in a team's `accord/product/security.md` with two new refusals, a security scan that no longer skips whole agent folders or binary files, a scout check that accepts the scout's own path formats, a generated CI job that stops after 15 minutes, and a set of small fixes. Tickets in flight: no rule in this release has a cut-off, and `TITLE_RULE_FROM` and `PLAN_LARGE_FROM` stay 0.8.0. The two new refusals, D-07 (a pattern line the guard refuses is not in force) and D-10 (a pattern line that is not in force blocks the ticket at `accord gate done` and `accord round`), judge a team's `accord/product/security.md`, not a ticket, so they apply to every ticket, in flight or new, once its repository pins 0.8.1: a team runs `accord lint` after upgrading, reads what it reports for `accord/product/security.md` and fixes those lines. D-21's path-entry and heading problems are `accord lint` errors only; `accord gate` and `accord round` do not refuse a ticket for them. Pinned repositories: the skills, agents, hooks and the CI `lint and gate` step (D-23, the non-ASCII ticket names) reach a repository with `accord upgrade`, which moves the pin and regenerates them; the CI job timeout (D-25) does not, so a repository whose workflow `accord init` wrote earlier adds `timeout-minutes: 15` by hand. The owner's answer on D-24: with the review stage off a ticket gets no security review, and that stays as documented; moving the security review onto the locked floor is queued as a backlog item and is not in this release. A repository pinned to 0.8.0 keeps its 0.8.0 answers, skills and hooks until it upgrades.

- The accord job that `accord init` writes now stops after 15 minutes (`timeout-minutes: 15`), so a stuck run no longer holds the required check for GitHub's six-hour default. `accord upgrade` rewrites only the `lint and gate` step, so a repository whose workflow `accord init` wrote earlier adds `timeout-minutes: 15` under the accord job's `runs-on:` by hand.
- New refusals of a team's `accord/product/security.md` (Phase 8, D-07). A `line /…/` pattern that can take exponential or minutes-long time on a failing line is refused when the file is read: it is not in force, `accord lint` reports it at its line as a `lint.security-file` error with the rewrite, and `accord review-package` says how many lines were not read. The guard refuses a repeat inside a repeated group, alternatives or optional parts under a repeat that can match the same text (`(a+)+$`, `(a|a)*$`, `(a?b?)*$`), any backreference (`\1` to `\9`, `\k<name>`), three overlapping repeats in a row, a pattern that can reach one place by more than 16 routes for the same text, and a pattern too large to check. These judge a team's security file, not a ticket, so there is no ticket cut-off: they apply to every ticket once the repository pins 0.8.1, and a file that holds none of these shapes sees no change. The four default line patterns and the shipped `built-path` of 0.7.0 and 0.8.0 pass. The rewrites the reasons name for the shapes a team is most likely to hold: every backreference is written out, for example `(["'])(?:(?!\1).)*\1` becomes `"[^"]*"|'[^']*'`; three chained repeats are merged or trimmed, for example `\d{1,3}\d{1,3}\d{1,3}` becomes `\d{3,9}` and `.*password.*=.*` becomes `password.*=` (a leading or trailing `.*` adds nothing to whether a line matches); a repeated group that can match the same text in more than one way is rewritten so each repeat has one way to match, for example `(a?){2,}` becomes `a*`, and `(a{5})+` (a multiple of five, also refused) becomes `a{5,}` when five or more is what was meant. Read the file with `accord lint` before upgrading to see whether a line is touched.
- A pattern line that is not in force now blocks the ticket (Phase 8, D-10). Any `## Patterns` line that does not compile, is refused by the guard above or cannot be read is a `gate.security-unreviewed` finding of `accord gate done` and `accord round`, at `accord/product/security.md:<line>` with the fix, for a ticket under the security rule; before this only `accord lint` and a line under the review package's triggers said that a pattern was not in force, and the gate did not. Like the refusals above this judges the security file, so it has no ticket cut-off and applies once a repository pins 0.8.1: a team with a pattern line `accord lint` already reports fixes the line, then runs `accord lint`.
- `lint.security-file` reports more of the file (Phase 8, D-21), as `accord lint` errors only: `accord gate` and `accord round` do not refuse a ticket for them. A path entry that can never match, one with a backslash, a leading `/` or `./`, or a `..` segment, and a `##` heading that is repeated (only the first is read) or is not `## Patterns`, `## Checklist` or `## Removed`. Each message names the fix. A team that fails `accord lint` after the upgrade for one of these edits the line named.
- The linear default `built-path` (Phase 8, D-08): the default pattern for a path built from input is rewritten so that it takes about 0.1 ms on a 100,000-character line where the earlier one took over a second. It matches the same lines. A `security.md` written by an earlier `accord init` keeps reading clean and the current default applies; no edit is needed.
- The scan bound is now 1000 characters (Phase 8, D-09), not the 0.8.0 note's 2000. A changed line over 1000 characters is matched on its first 1000 and gets a `cannot` trigger, `<path>:<line>: (cannot tell: line longer than 1000 characters, not fully scanned)`, so a line of 1001 to 2000 characters, which was scanned in full, now calls the security reviewer. The bound caps the cost of one line; the total grows with the number of long changed lines, and a team pattern the guard accepts can still take from about 0.1 s to a few seconds on one hostile 1000-character line, so a diff of very many such lines is slow, though it ends.
- A binary file is no longer a way past the scan (Phase 8, D-20). A file git still calls binary, which one NUL byte in a changed line is enough to make it, is a `cannot` trigger, `(cannot tell: <path>: binary file, its lines were not scanned)`, unless its extension is a known image, font or archive type (png, jpg, jpeg, gif, webp, ico, bmp, avif, woff, woff2, ttf, otf, eot, zip, gz, tgz, tar, bz2, xz, 7z, pdf), or a text reading of the same file was scanned. A repository that commits other binary files sees the reviewer called for them.
- The security scan no longer skips whole agent folders, watches agent configuration, and compares path entries ignoring letter case (BUG-LN-25, merged after 0.8.0 without a note). Before, no content pattern ran over a file under `.claude/skills/`, `.agents/skills/`, `.claude/agents/` or `.claude/accord-panel/`, so code added or hand-edited there reached done with `no pattern matched`. Now a file there is scanned like any other unless it is exactly a copy `accord skills sync` writes, meaning its text at the reviewed commit equals what the running accord renders: unmodified copies raise no trigger, and a copy edited by hand, one an older accord wrote, or a file accord does not write there is scanned. `accord gate done`, `accord round`, `accord review-package --security` and `accord diff-package --security` take the list of rendered copies they leave out from one helper, so they agree on which copies are exempt; with no config no file is exempt. A new default pattern `agent-config` names `.claude/settings.json` and `.mcp.json`, so a change to either calls the security reviewer (D-22 below adds `.claude/settings.local.json`). A path entry of a security pattern now compares ignoring letter case, because Windows and default macOS open `.MCP.json` as `.mcp.json`; the trigger still names the path as the diff spells it. The new default reaches every repository with the release, since the defaults apply whatever the file says. No cut-off applies, so these hold for every ticket once its repository pins 0.8.1.
- Two more agent surfaces are watched (Phase 8, D-22). The default `agent-config` pattern also names `.claude/settings.local.json` (root only, as `.claude/settings.json` is), and a file with a test name (a `test`, `tests` or `__tests__` folder, or `.test.` or `.spec.` in the name) under `.claude/skills`, `.agents/skills`, `.claude/agents` or `.claude/accord-panel` is content-scanned, because an agent loads those folders, where a test-named file elsewhere stays skipped. Markdown there stays skipped as before, so a hand edit of a skill's Markdown gets no line trigger and shows only in the reviewed diff. Every repository gets both with the release, since the defaults apply whatever the file says.
- The CI ticket list reads non-ASCII names (Phase 8, D-23). The generated workflow, this repository's copy and the verify skill's pre-push check list the changed tickets with `git -c core.quotePath=false diff --name-only --diff-filter=d`; before, git quoted a name such as `accord/tickets/Café.md` as `"accord/tickets/Caf\303\251.md"`, the grep missed it and CI did not gate that ticket. `accord upgrade` rewrites the `lint and gate` step, which holds the list, so a pinned repository gets the fix at its next upgrade; until then a ticket file with a non-ASCII name is not gated by its CI.
- With the review stage switched off, a lane M, L or P ticket gets no security review (Phase 8, D-24). `gate.security-unreviewed` belongs to the review stage and reads the review record, so `strictness.stages.<lane>.review: off` removes it, as the `strictness.stages` note of 0.5.0 says of the critics. This is documented, not changed: no rule moves to the locked floor. `accord status` names every stage that is off. The owner kept this as it is for 0.8.1; moving the security review onto the locked floor, so that it survives `review: off`, is queued as a backlog item and is not part of this release.
- `accord scout check`, and the scout check inside `accord approve`, accept the scout's own path formats (Phase 8, D-14). A `## Files` path may be written with a trailing colon, with or without backticks (`- path/to/file.ts: defines x`); a citation may be written with backslashes (`path\to\file.ts:12`); and a shortened path, in `## Files` or in a citation, that exactly one tracked file ends with (`/` plus the path) is read as that file, and `accord scout check` prints one `expanded <short> to <full>` line for it before the verdict. A shortened path with no such file or with several still fails with the same text as before, and `## New files` is never expanded. Absence claims in `## Absent` no longer search tracked files under `.claude/` or `.agents/`, which hold rendered agent text; a row whose folders cover only those still reports that its folders cover no tracked file. The check is shared with `accord approve` and the benchmark scripts, so all of them accept the same reports; a report that passes now but failed before is the only change, and no rule moves, so no cut-off applies.
- The planner agent's description renders whole (Phase 8, D-15). `.claude/agents/accord-planner.md` read `description: "Drafts a ticket's"` because the source held an unquoted ` ## Approach`, which YAML reads as a comment, so Claude Code's agent list showed a stub. The source is now quoted and a test checks every agent's description against its source. A repository gets the whole text at its next `accord skills sync`; nothing else changes.
- `accord skills sync` no longer adds a second set of hooks beside an accord hook you edited (Phase 8, D-16). A hook in `.claude/settings.json` that runs `accord hook <event>` in any form (`npx`, a global `accord`, a path to `cli.js`, another version, extra flags) is kept as you wrote it, sync does not add its own hook for that event and subcommand, and one line per kept hook is printed (`kept SessionStart hook "<command>": ...`), on every run. A hook still in the exact form sync wrote is updated as before. To get accord's hook again, edit or remove yours. `accord init` and `accord upgrade` print the same lines.
- `accord task-done` judges an executor report in a task worktree by that worktree's HEAD (Phase 8, D-18), so a wave task that made no commit is no longer refused because another task's ledger commit moved the ticket's HEAD. A report older than the task worktree's own HEAD is still refused, and the refusal names that HEAD's sha. A task built in the ticket checkout is judged as before.
- A team command that is stopped is reported only after its process tree is gone (Phase 8, D-11). The runner behind the `git.sync` command and the script tracker's commands kills the whole process tree of a command that times out or prints more than its output limit. It now reports only after that kill has returned as well as after the output pipes have closed, where it waited for the pipes alone; on Windows `taskkill /T /F` could still be walking the tree when the report came, and the caller removes the ticket's folder the moment the report returns. The same 10-second safety net keeps a stuck kill from holding the caller longer than before.
- `accord help` and `accord help <command>` exit 0 (Phase 8, D-26), as `--help` does; bare `accord` still exits 2. A ticket file named `__proto__.md` and a `tests.report` or `design.tokens` value of `constructor` no longer crash the loader or hide a ticket: the loader's file, ticket, verification and work maps hold own keys only. A ticket named `__proto__` is now listed and linted (its id fails the id pattern, as any id starting with `_` does).

## 0.8.0 — 2026-11-19

Release 0.8.0 ships Phase 7: intent routing for `/accord <text>`, the duplicate check and related-ticket Decisions, the title rule, `/accord-queue` from any session, kept conventions and Rejected offers, the verify deferred question, the read-only researcher, lane L (epics and their stories), the read-only foreign-PR reviewer, and next-action lines on worktree commands (the bullets below). Tickets in flight: the two new rules with a cut-off, the title rule (`gate.ticket-title`, `lint.ticket-title`, `TITLE_RULE_FROM`) and the large-plan warning of `gate plan` (`PLAN_LARGE_FROM`), both 0.8.0, judge only a ticket claimed (or, for lint, created) under 0.8.0 or later, so no existing ticket is refused for its title or warned for its plan size. Everything else applies to every ticket once its repository pins 0.8.0. Pinned repositories: the new skills, agents (`accord-researcher`, `accord-foreign-reviewer`) and hook matcher reach a repository with `accord upgrade`, which moves the pin and regenerates them; `queue.merge` stays `owner` until a team sets it, and `titles` takes its defaults when absent. A repository pinned to 0.7.x keeps its 0.7.x answers, skills and hooks until then.

- `accord new ticket --title <t>` prints up to five similar tickets of any status, done and dropped included, before it writes a ticket, and creates nothing until the session runs it again with `--related <ids>` for the tickets the request continues or builds on, or `--related none`; the ids are written as `related:` in the ticket's frontmatter. The skills that create a ticket (`/accord-new`, `/accord-queue`, lane S and the type change in `ids.md`) make a short English title first, judge which candidates really match, and ask the owner one question on a match: continue the existing ticket, merge the request into it, or create a new one linked to it. No scout runs for this check. A lane S or M ticket needs `--title` and is refused without it; `--no-dup-check` lets a script create one without the check and prints that it did, and no skill names it (ST-LN-22).
- `accord related <id>` prints the `### Vetoes` and `### Decisions` lines of up to five tickets related to the ticket, with `(none)` for an empty section: first the ids its `related:` list names, in written order, then the tickets the same similarity search as the duplicate check finds for its title and Intent, from the working tree or the default branch. `/accord-intent` step 2 pastes what it printed into the dispatch of `accord-scout`, and the approach critique's round 1 into the dispatch of `accord-critic`, so a new ticket can no longer break a finished ticket's Decision unnoticed; no other stage gets it, and no skill tells an agent to open other tickets (ST-LN-22).
- A ticket's title follows a title rule. `config.yml` gains the `titles` key (`rule`, one line of guidance; `max_length`, default 80; `language`, `english` by default or `any`), edited with `accord config`. `accord new ticket --title <t>` refuses a placeholder, a title over the length or, under `english`, a letter outside A-Z, writes nothing, and prints the rule line `title rule: ...` beside every title it is given, so the model reads the rule when it writes the title. `accord gate ready` (`gate.ticket-title`) and `accord lint` (`lint.ticket-title`) refuse the same, from `TITLE_RULE_FROM` (0.8.0): gate ready for a ticket claimed from that release on (its claim pin is not before it), lint for a ticket whose `ruleset` is not before it, which is a ticket created in its worktree or claimed under that release. Every existing ticket keeps its title unjudged: an older or missing `ruleset` is skipped by lint, and an older claim by gate ready. Both rules are errors a team may lower through `strictness.levels`. (ST-LN-22).
- `/accord <text>` routes the text by intent: a change goes to `accord-new` (a bug whose cause nobody has shown to `accord-debug` before its approach), a question is answered from the code with no ticket and no lane proposal, a brainstorm ends by proposing build now, queue, research or nothing, an idea to queue goes to `/accord-queue`, research to lane R, a change, drop or merge of an existing ticket to an edit or `accord drop <id> --reason`, and a review of code accord did not build to the read-only review. The session says the route out loud ("I read this as … and will …; say so if not") and asks one short question when it is unsure. In a session that works a ticket the prompt-expansion hook now lets the dashboard, free text, `/accord-queue` and `/accord-upgrade` through, so a question, a brainstorm, a review and a queued idea no longer need another session; a change to another ticket is still refused, by the hook for `/accord-new`, `/accord-pickup` and a Continue of another ticket and by `accord worktree check`, `accord worktree open` and `accord new ticket` behind it. The refusal says `this session works <id>`, names the command to type and ends with a line ready to copy, `cd "<path>"; claude`, where `<path>` is that ticket's worktree for a Continue and the main checkout otherwise. No session is moved from one ticket to another. A repository on an older pin gets the same refusal text at its next `accord upgrade`; no cut-off applies.
- `/accord-queue <idea>` and `accord new ticket --queue --title <t> --note <line>` write a draft on `backlog/<id>-<date>` off origin's default branch from a temporary worktree, from any session, a ticket session included; `queue.merge` (`owner` by default, or `at-once`) decides whether the skill merges the pull request at once; `commits.subjects.queue` (default `backlog: queue {id}`) is the subject (ST-LN-83).
- `accord new ticket --queue` now commits the creator's `people` entry in the same commit as the draft when origin's default branch has a `people` mapping that does not list the creator's email, and prints `people: "<email>": <INITIALS> - committed with the draft`, adding that the entry should be removed here when this checkout never committed it; a default branch with no `people` mapping gets no entry, because the queue never switches the id convention on. `/accord-queue` follows that line, so a person registered on the queue route reaches the default branch with the backlog pull request and a ticket session is left as it was. Every form of `accord new ticket` now takes the creator's initials from origin's default branch, else from the fetched branches when their entries agree, when this checkout's `config.yml` does not list the email (or has no `people`); initials another email holds on any branch are still refused, and `lint.initials-duplicate` is unchanged. The `worktree.md` carry rule now also carries an entry an earlier run left uncommitted. No lint or gate rule changes, so no cut-off applies (ST-LN-83).
- `accord diff-package <base> <head> [--security]` prints the review package of the changes from `<base>` to `<head>` (their merge-base diff): `Base:`, `Head:`, `Changed lines:` (lines added plus lines removed), the stat and the diff, or with `--security` the checklist, the security triggers and the matched hunks `accord review-package --security` builds. `/accord` routes a request to review code or a pull request accord did not build to a read-only review: `accord-foreign-reviewer` with lenses by `accord-review`'s size rule (about 500 and 1500 changed lines) and a `security` reviewer on a trigger, no edit, no commit, no fix round, and findings posted to the pull request with `gh pr review --comment` only after the owner's explicit yes. `accord-foreign-reviewer` (routed by `models.reviewer`) declares only Read, Grep and Glob, so a pull request's title, body or diff cannot make it run a command, write a file or dispatch an agent; the ticket reviewer keeps Bash for ticket reviews. A pull request number needs gh; a local branch or a commit range does not (ST-LN-83).
- The shipped executor default is now sonnet at high (it was medium) and the auditor default is opus at high (it was medium); the planner and the critic stay opus at high. A repository with no `models:` entry for them gets the new values at its next `accord skills sync`, which `accord upgrade` runs, and an entry under `models:` still wins field by field. There is no cut-off, so the executor of a ticket in flight runs at high from that sync on, which costs tokens (in benchmark round 1 an executor run at high read a median of about 13% more cached tokens than at medium), not correctness (ST-LN-85).
- `accord-executor` now declares `tools: Read, Write, Edit, Bash, Grep, Glob`, so in Claude Code it no longer inherits the host's skills, MCP tools or web tools; it reads library docs and source through Read and Bash. One added sentence tells it to stop and return `NEEDS_CONTEXT` with a question naming what it needs and why when it needs something from outside the repository, instead of guessing. `accord-build` routes that stop as it already routes any `NEEDS_CONTEXT`: a question that touches intent, a veto, a criterion or a public interface goes to the owner, and any other question is answered by the main session as a Ruling before a fresh executor gets the answer. A new package is still a `BLOCKED` that goes to the owner. Cursor, Codex and Copilot are unaffected, since accord renders agent files only for the `claude` runtime (backlog 999.11) (ST-LN-85).
- A rule the owner states to last beyond a ticket, an override of a skill's step and a refused option are offered at any stage of a ticket as one line (a rule line, or `Rejected: <option> — <reason>`) by the one procedure in `shared/ask.md`; on an explicit yes the line waits in the ticket ledger's `## Conventions` and `accord-verify` step 6 or lane S's finish writes it into `accord/product/conventions.md`, and nothing is written without a yes (a lasting rule stated outside a ticket's stages is not offered; a ticket abandoned with no verify never writes its line). `accord drop <id> --reason <r> --rejected` appends `- Rejected: <title> — <reason>` to `accord/product/conventions.md` in the drop commit, only when the flag is given, and `accord related <id>` now ends with a `## Rejected` section holding every `Rejected:` line of that file as written (`(none)` when there is none). `accord-intent` and `accord-approach` compare each option with those lines and name a matching one to the owner before proposing it. No lint or gate rule reads `conventions.md`.
- `accord deferred <id>` prints the Must and Should items under the ticket ledger's `## Deferred`, one short line each (`Must: <text>` or `Should: <text>`, the line without its list marker, cut at 160 characters with an ellipsis), the Must items first and every `## Deferred` section read in order; a line's rating is its first `(Must)`, `(Should)` or `(Nice)` mark and a line with no mark counts as Should; Nice items are never shown, and with none to show it prints `no Must or Should deferred items`. `/accord-verify` shows those lines in the owner's report and, after the owner's answer at step 5, asks one question: which of them become backlog draft tickets, each yes going through the queue route (`accord new ticket --queue`), the rest staying in the ledger as a record. No gate reads an undecided item, so `accord gate done` passes as before, and no existing ledger line is edited, moved or triaged (ST-LN-12).
- `accord-researcher` (sonnet at high; `models.researcher` overrides it) is the only agent with web tools. It is read-only: every built-in tool that changes a file or runs a command is withheld, so it writes no file and runs no command, and it returns facts as text. It runs only at the intent stage's discuss step, once per library, when a gray area or the ticket turns on an outside library, API or version that the code cannot answer. Each fact it returns carries a source (a library documentation tool's id when one is installed, then the official docs, then web search) and the date it was read; the session writes the reply as one record per library under `accord/research/`, leaves out a fact with no source or no date, lists the record under the ticket's `research:` key and gives it to the planner. Its file reaches a repository at its next `accord skills sync`. Cursor, Codex and Copilot render no agent files (backlog 999.11), so there the session looks the library up itself under the same rules.
- A story whose `parent:` names an epic now gets the epic's rules as CLI-built input: `accord anchor` prints `## Epic <id> "<title>"` with the epic's `### Vetoes` and `### Decisions` and an `### Epic lessons` part, and the SubagentStart hook adds the same block to the scout, planner, critic, reviewer and final reviewer of a story's worktree; the default branch's copy of the epic wins, and no skill tells an agent to open the epic. At `/accord-verify` step 6 a Ruling or lesson that holds for the whole epic is offered to the owner as `shared/ask.md` says, and on a yes it is written as `- Lesson: <lesson> — "<the owner's words>"` under `## Epic lessons` in that story's own ledger and nowhere else; the `### Epic lessons` part of a later story lists those lines of every sibling story (same `parent:`) that is on the default branch, in id then ledger order, so a lesson on an unmerged branch is not shown and no shared file is written. Cursor, Codex and Copilot, which have no accord hooks or agents, see the block only through the anchor. A ticket with no `parent:` is unchanged (ST-LN-28).
- Lane L is built. `accord new ticket --type epic --lane L --split <file> [--queue]` writes an epic and its stories in one step from a split file (`title`, `intent`, `vetoes`, `decisions`, and `stories` with `title`, `intent` and `after`): every story is lane M with `parent:` the epic and `depends_on` from `after`, and with `--queue` the epic and every story are one commit on one backlog branch. The epic's `## Decisions` holds the `decisions` lines numbered `D-01` on, so a story's epic block carries them; a `decisions` line that already starts with a `D-` number is refused, and a split file without `decisions` is read as before. The epic's `## Approach` lists the stories in order, each with the stories it waits for. `/accord-new` proposes lane L for a request that names three or more parts that would each be a story of its own, and follows a new `epic.md` for it: one epic-level interview that also asks for the Decisions, a proposed split, the owner's explicit yes, then that one command; the epic itself gets no approach or plan critique and each story gets its usual one when it is picked up, in its own worktree and pull request. The plan-size refusal of `accord gate plan` now names splitting the work into an epic of smaller stories with `/accord-new` (lane L), a wording change that applies to every ticket, and the new warning `gate.plan-large` (a lane M plan of 15 tasks or more; fails nothing; a team may lower it through `strictness.levels`) says the same, from `PLAN_LARGE_FROM` (0.8.0, with `TITLE_RULE_FROM`): a ticket claimed from that release on is judged, and a plan of a ticket claimed before it gets no warning. (ST-LN-28).
- `accord worktree clean` removes a local `backlog/*`, `fix/*` or `release/*` branch with a commit of its own that origin's default branch already holds through a merge commit, or whose merge into it would change nothing (a squash or rebase merge), and the worktree that has it checked out, an agent folder under `.claude/worktrees/` included, after the same guards as any worktree removal: it prints `deleted <branch>: merged into <default>` and the worktree's `removed` line. A branch with commits the default branch lacks stays with `kept <branch>: it has commits <default> lacks`, and a branch cut from the default branch that has no commit of its own yet stays with `kept <branch>: it has no commit of its own`; a ticket's own branch, any other branch name and every remote branch are never touched. The session-start clean does the same, so on a repository with such merged branches the first run after the upgrade deletes them (ST-LN-87).
- `accord dashboard` makes one fetch from origin, bounded at 10 seconds, before it reads, so a teammate's pushed claim shows under TEAM without a manual fetch; when it fails or times out the dashboard goes on with the refs already in the clone and prints one `fetch from origin failed ...` line before the sections (text) or sets the field `offline` in `--json`, which stays one JSON document; with no origin it fetches nothing and says nothing. The sentence says why the script did not run (never allowed, another command, or which covered files changed), what an allow covers, and the checkout to run `accord trust` in, because the files are read from that checkout: Continue checks the ticket's worktree, not the checkout it runs from, and it checks and runs the `git.sync` of the ticket's worktree (the one `accord worktree sync <id>` runs there and `accord trust` there shows), so the allow the line asks for is the one that unblocks the next Continue; when the worktree's `accord/config.yml` is missing or does not load, the checkout's own `git.sync` is used, under the same check. `accord trust` alone shows each declared script, with its command, a digest of what it covers (`(digest <16 hex characters>)`), what an allow covers (and the files themselves when there are at most 20) and the files that changed since its last allow, and allows nothing. `accord trust git.sync@<digest>`, `accord trust tracker.command@<digest>`, or both, with each digest as the preview printed it, allow only the scripts named and only the content that was shown, and print the same block: a script named without a digest, or whose covered files changed after the preview so the digest no longer matches, exits 2 and nothing is written, so a file an agent or a pull edits between show and allow is never bound unread, and allowing the sync script after reading its diff never also allows a changed tracker script; `accord trust --revoke` withdraws every allow, and `accord trust --revoke git.sync` that script's only. Each command and covered path is printed with its control characters (ESC, the other C0 and C1 controls, bidi and zero-width marks) written as `<U+001B>` and the like, so a command cannot hide its start from the person reading it. The allow is a local file, `accord-trust.json` inside the repository's common git directory (`git rev-parse --git-common-dir`): every worktree of the clone shares it, it is never committed and nothing under `accord/` changes. It holds up to 16 allows per script, one per command and set of file contents, so two worktrees whose script files differ each keep their own allow and going back to content you allowed before needs no new allow. Allows and revokes take a lock file beside the record (`accord-trust.json.lock`; one left by a killed process is taken over after 60 s) and apply their change to the record as it is on disk, so allows made in parallel worktrees both land and an allow never brings back what a revoke withdrew; an entry accord cannot read is ignored, read as no allow, with one `warning:` line from `accord trust`, and from `accord status` when it checks a tracker script. An allow is bound to the command text and to the git content id of every tracked file the command reaches, as it is in the working tree: for a file git sees unchanged, the id the index holds (the blob of a file of any size, the target text of a symlink, the commit of a submodule); for a changed file, the id `git add` would give it (a checked-out submodule counts by the commit it has checked out). That boundary is stated, not promised. A check that finds no allow of the command to compare with (`accord status`, Continue, `accord worktree sync`) computes no digest at all. A tracked file the command names, or one a word becomes with an extension that Node, Windows PATHEXT or an interpreter adds (`node scripts/tracker` runs `scripts/tracker.js`; `.mjs`, `.cjs`, `.cmd`, `.ps1`, `.sh`, `.py` and the like), binds the whole directory of that file, every tracked file below it at any depth; a file at the repository root binds every tracked file outside `accord/`, so a script kept in a folder of its own is asked about less often. A tracked directory the command names binds everything below it, and `node .` binds `package.json` and, as above, the directory of the file its `main` names (`index.js` when it names none). `npm run <name>` (and `npm run-script`, `npm test`, `pnpm run`, `yarn run`, a bare `yarn <name>`, `bun run`) binds `package.json` and the runner's own files (`.npmrc`, `.yarnrc.yml`, `.pnp.cjs`, `.yarn/releases/` and the like), and follows the package.json script, with its `pre` and `post` scripts, as a command of its own. When the command reaches no tracked file, the root manifests an interpreter or task runner reads (`package.json`, `Makefile`, `justfile` and the like) are bound. Paths are matched without regard to case on every system and in every path component, so `Scripts/tracker.mjs` on Windows binds `scripts/`, and an index entry `Scripts/lib.mjs` beside `scripts/tracker.mjs` is held by `scripts/`. A bare word with no `/` or `\` is tried with an added extension only where a script stands: the word that starts a command, or the first word that is not an option or an `A=1` assignment after it or after a launcher (`node`, `python`, `bash`, `env`, `npx` and the like); anywhere else it matches a tracked file only as written, so the `main` of `--since main` never reaches a root `main.py` and with it every tracked file. accord checks only the files `accord trust` lists; anything else the command loads is not checked, and every `accord trust` output says so in one line. Not checked: other runner forms (`node --run`, `npm -w`/`--workspace`, `--prefix` and the other workspace options, `bash -c` or `sh -c "..."` and `cmd /c "..."`, `node -e`, `python -m`, `npx` and `npm exec`, the `npm install` lifecycle scripts, `.npmrc` `node-options`); a file loaded from outside the listed directories (an `import '../lib/x.mjs'`, a path read from a config file); the scripts a `make` or `just` target runs (the Makefile is bound only when the command reaches nothing else); a path built from an environment variable (`$ACCORD_ROOT/scripts/x.mjs`); a package.json script chain deeper than 8; `npm start` with no `start` script, which runs `server.js`; a command word and a tracked name that differ only in Unicode normalization (macOS); and anything outside the repository (programs on PATH, installed dependencies in `node_modules`). When the command, or a package.json script it follows, uses one of the forms above that accord can spot, `accord trust` adds a `not followed:` line and the refusal adds `(not followed here: ...)`, so a cover of `package.json` alone never reads as complete. Whoever allows a script must review the pull request that changed it. A branch that changes a covered file, with the command text unchanged, is not run until you allow it again; a branch that changes only a file outside the cover is run. The built-in adapters (`none`, `github-issues`, `jira`, `linear`) run no repository script and are unchanged; the Jira credential still goes only to the `tracker.url` the default branch names. That comparison needs a default branch ref (`origin/HEAD`, `origin/main` or `origin/master`, else a local `main` or `master`): in a clone with none, such as one made with `git init`, `git remote add` and `git fetch` of a repository whose default branch has another name, there is nothing to compare with and the working `url` stands; and a `url` you set with `accord config set` is not sent a credential until it is committed to the default branch. Because the pin on `tracker.command` is gone, a command that only a branch holds runs once you have allowed it there. A repository that uses neither script is not affected. Never allow a script you have not read: run `accord trust` first and read the files it names, since the script runs as you, with your whole environment.
- `accord config set` stores the value as typed. A value is never unwrapped: `'"./my scripts/sync.sh"'` and `'"C:\tools\build.cmd"'` are stored with their quotes and backslashes. The onboard skill passes the bare value (`accord config set git.merge 'squash'` for the printed `"squash"`).
- `accord upgrade` no longer writes `ruleset` into any ticket (this retires the backfill described under 0.5.0). A ticket approved on the default branch is still in flight on its claim branch, where the next `accord approve`, `gate ready` or plan write appends to the same end of the frontmatter, so the line conflicted at the next merge, and the ticket, not done, made the upgrade pull request's `gate done` loop fail. While the claim commit is reachable the claim fact already gives the rules the ticket was claimed under. `ruleset` is written into the branch's own copy (`backfilled: <id> ruleset <pin>`), before a rebase or a team script can rewrite the claim commit, only by the first Continue (stages intent to review) or `accord worktree sync <id>` (at verify) after the upgrade that takes the default branch into the ticket branch; one that takes nothing in, because the branch is not behind or Continue leaves it alone and prints `behind:`, writes nothing. In a repository that declares `git.sync` that waits for the allow: Continue leaves a branch alone and `accord worktree sync` refuses until `git.sync` is allowed in the ticket's worktree (`accord trust` there, then `accord trust git.sync@<digest>`), and the next Continue or `worktree sync` that takes the default branch in after it writes `ruleset`. - The rules a ticket was claimed under (corrects the 0.5.0 note on `ruleset`): the five rules that read the claim pin take the claim fact from git first (its first `ruleset`, else its pin), and a failed claim read applies the new rules. The ticket's own `ruleset` field decides only when git holds no claim fact and the ticket is done (it carries `verified_hash` and `verified_commit`), which is the squash or rebase merge of a finished ticket that dropped its claim commit. ## 0.5.0 — 2026-11-15

Release 0.5.0 gives a team settings for how it merges, names its tickets and commits, how strict it is and what a ticket holds, which tracker it reads, and how it sets accord up on an existing repository (five groups below). A repository that sets none of the new keys behaves as in 0.4.1, except for the `ruleset` line a claim now writes into each new ticket. The rule that reads the ticket's own `ruleset` has a cut-off constant in `packages/core/src/round/pin.ts`, `RULESET_FROM`, which holds the first release that ships the rule and reads `0.5.0`.

- Tickets in flight: a ticket claimed under 0.4.x keeps the claim-commit reader of 0.4.1 (the five pin-reading rules read the `accord:` pin at its claim commit) until `accord upgrade`, or its first `accord worktree sync` or Continue, writes `ruleset: "<claim pin>"` into it. From then on a squash merge or a rebase merge, which drops or rewrites the claim commit, keeps the ticket's rules. A ticket claimed under 0.5.0 or later carries `ruleset` from its claim. A ticket that is done or has no claim branch is left as it is.
- Repositories pinned to 0.4.1: they keep 0.4.1's answers and skills until `accord upgrade`, which moves the pin, regenerates the skills and backfills `ruleset` into the tickets in flight. Nothing in this release moves a pin by itself, and the repository's own pin moves after publish through `accord upgrade`. A config that uses one of the new keys (`git`, `ids`, `commits`, `strictness`, `template`, or a tracker adapter other than `none` and `github-issues`) needs 0.5.0 or later, and an older accord refuses it.

Teams that merge pull requests by squash or rebase (ST-LN-96, group 1). Nothing below changes a repository that sets no `git:` key and keeps merging with merge commits, except the `ruleset` line the claim adds to a new ticket.

- Ruleset per ticket (from `RULESET_FROM`, 0.5.0): the claim writes `ruleset: "<pin>"` into the ticket, in the claim commit (and `accord new ticket <id> --worktree` writes it into the ticket it commits), where `<pin>` is the `accord:` pin of the repository at that moment. A claim under a pin below 0.5.0 writes nothing and stays an empty commit. This is a one-way addition to the published ticket schema (D-02): a ticket that carries the field needs 0.5.0 or later, and an older accord refuses it, so a repository pinned to 0.4.1 never gets the field until `accord upgrade`. The five rules that read the claim pin (`DISCUSS_FROM`, `APPROACH_CAP_FROM`, `PLAN_FORMAT_FROM`, `PLAN_CAP_FROM` and `PLAN_GROUNDS_FROM`) now read the ticket's `ruleset` first, so a squash merge or a rebase merge, which drops or rewrites the claim commit, no longer changes the rules a ticket was claimed under. A ticket without the field keeps the claim-commit reader of 0.4.1, and a `ruleset` that is not a plain x.y.z is ignored.
- `gate.ruleset-changed` and `gate.ruleset-missing` (from 0.5.0): the field is never edited by hand. While the ticket's claim commit is reachable, `accord gate ready`, `gate plan` and `gate done` (lanes M, S and R) compare the field with the first `ruleset` the branch wrote, which is the one in the claim commit or, for a ticket claimed before 0.5.0, the one in the backfill commit below, and a different value is an error that names both. A ticket claimed before 0.5.0 that no commit ever gave a `ruleset` is compared with the pin at its claim commit, as before. `gate.ruleset-missing` fires only when the ticket held a `ruleset` at the reachable claim commit and has none now. A rebase moves the config pin at a rewritten claim commit but replays the ticket's own line, so a rebased ticket passes. After a squash merge no claim commit is reachable and both rules are silent: the ticket is done by then.
- Backfill (from 0.5.0): a ticket in flight at the upgrade has no `ruleset`. `accord upgrade` writes `ruleset: "<pin at its claim commit>"` into every ticket on the default branch that has a lane, is not dropped, is approved there (an `approved_hash` or an `ac_hash`) and has no `ruleset`, is not done there, and has a `claim: <id>` commit on a claim branch (the `branch` template, local or on origin); the value is the `accord:` pin of `accord/config.yml` as committed at that claim commit, and it goes into the one `upgrade/<version>` commit, which the upgrade's own lint pass checks. Done, unclaimed, already written and unapproved tickets are left as they are: a draft's copy on the default branch has no rules to pin yet, its file on the claim branch gets the field at its first sync, and a field written into the draft would conflict with the branch's approve and fail the pull request's gate. A ticket whose claim pin cannot be read, because the blob is missing or the pin is not a plain x.y.z, gets no field and one `warning: <id>: ruleset not written, ...` line on stderr, and the exit code does not change. A ticket whose file is only on its branch gets the field at its first sync instead: `accord worktree sync <id>` and Continue write `ruleset: "<claim pin>"` in one commit named `ruleset: <id> from its claim commit` and print `backfilled: <id> ruleset <pin>`, once the branch carries (or is about to take in) a pin of 0.5.0 or later. Under `git.merge: rebase` or `git.sync` the commit is made before the sync, while the claim commit is still reachable, and a refused sync takes it off again. A branch pinned below 0.5.0 is not given the field (its published schema refuses it), and a ticket that lost a `ruleset` an earlier commit wrote is not backfilled: `gate.ruleset-missing` reports it.
- `git.merge` and `git.sync` (from 0.5.0, new keys of `accord/config.yml`): `git.merge` is `merge`, `rebase` or `squash` and says how the team merges pull requests into the default branch. With no key a repository means `merge`, and everything works as in 0.4.1. - Approach critic (from `APPROACH_CAP_FROM`, 0.4.1): for a ticket of lane M, L or P the critic runs at most two rounds, and no Ruling raises the cap. A third round is refused with the findings still open. An open `risk: data-loss` or `risk: security` finding blocks the approval, in every round of such a ticket and when round 2 reports no findings or a verdict ends the loop: `accord show <id> --approval --short` lists it under `## Blocking findings`, and `accord approve` refuses with exit 1 and names it. This is a change in public behaviour: `accord approve` read no approach record before 0.4.1. The approach record is read strictly and fails closed. The one separator is ` — `; a hyphen, two hyphens or an en dash is part of the text of a state, a reason, a test or a command, so `command: npm test -- <path>` is never cut. A risk is read only from the finding's mark slot: a ` — `-separated segment after the finding's text that is `risk: security` or `risk: data-loss`, or `rests on: risk: security` or `rests on: risk: data-loss` (the critic's own wording), in any letter case, after the state or before it, whether the severity is followed by ` — `, a colon, a hyphen or an en dash (`1. Must: <text> — risk: security — open` is read like `1. Must — <text> — risk: security — open`); or the `rests on:` line of the critic's block, the lines under a finding that are indented deeper than it, as `agents/critic.md` prints it. The block's other `rests on:` lines (`ac-<n>`, `D-<nn>`, a quote, `test:`, `command:`) are read as grounds, so a round 2 block with `rests on: ac-1` is not refused for grounds; a block may carry several of them, and a ground on the finding line may stand beside one in the block, and every one is read: a second ground, or a second `test:` or `command:`, is never a record problem. Any other line under a finding, indented or not, is a note, and a note is prose: `   - Risk: a stale cache shows old rows` refuses nothing. Prose is never searched for a risk word: the finding's own words, a note under a `## Round` heading, the reason of a `withdrawn:` or `unverified:` state, the owner's words, a `No findings` line and a test name such as `risk:data-loss` are read as nothing, so they never refuse. A finding that names a risk only in prose, or in a line with no ` — `, is not a blocking finding; while it is an open Must or Should the short view lists it under `## Risks`, and an open Nice is never listed. A mark slot is a segment after the finding's text, or a `rests on` line of the block, whose key is `risk`, `risks` or `rests on` and whose value is a security or data-loss kind written some way, and a mark slot whose value does not parse is a record problem: `risks: security`, `risk: data_loss`, `risk; security`, `risk, security`, a mark in backticks, quotes or asterisks, `risk: security.`, a hyphen that is not the ASCII one as in `data‑loss`, a kind one edit off the whole word, counted over its letters, the `data` part of `data-loss` included, and whatever up to three characters that are no letter separate the letters or come before them (`risk: secrity`, `risk: date-loss`, `risk: data-lost`, `risk: data/loss`, `risk: secu-rity`, `risk: .security`; a value two or more letters off is prose) and `rests on risk: security` (no colon) are problems. A value that is no such kind is prose, not a problem: `risk: none`, `risk: low`, `risk: a partial file is left on a crash` and `rests on: ac1` refuse nothing. A line directly under a finding, with no blank line between, that is no deeper than the finding and is a mark slot (`rests on: risk: security` or `risk: security` at the start of the next line) is a record problem too, because Markdown renders it as part of the finding: indent it under the finding, or leave a blank line before it, so that it is a note. A risk finding is open, whatever its severity, while its state is `open`, `unverified` or `deferred` (a risk finding is never deferred), while it is `repeated as` a finding that is not in a later round of the cycle, and while an `owner:` state has no words. A finding repeated as another, or repeated by a `repeats <round>.<n>:` line, passes its risk on, so a repeat line without a `risk:` mark blocks too. A risk finding stops blocking when it is `fixed`, `withdrawn`, repeated as a finding that exists, or dropped by the owner as `owner: "<words>"` (the short view then lists it under `## Risks` with the owner's words), and when any `## Closed` line (the owner's no with a Correction, `ruled out by`, `the owner picked`) starts a new cycle.
