<objective>
Build the release path and prove the one part of it that can be proved before it runs.

D-149: a pushed tag matching `v*` and nothing else. A `workflow_dispatch` leaves nothing in git
saying which commit became which version; a GitHub Release adds a UI step plus release notes, which
is separate work. The pin (D-94) is exact string equality against a version in `config.yml`, so one
point in git has to name that string, and a tag is that point.

Purpose: the workflow is the thing ROADMAP criterion 1 is about — *published from GitHub Actions
via npm trusted publishing*. Its filename becomes part of the npm trusted-publisher record in 09-05
and can never be changed afterwards without silently breaking authentication, so it is fixed here,
at creation.

Output: `.github/workflows/publish.yml` and a test that executes its version-check body against a
real shell rather than reading it.

**This plan builds nothing.** 09-01 is Wave 1's sole owner of `packages/core/dist/` and
`packages/cli/dist/`: it rebundles them and runs the tests that read them. `dist/` is gitignored,
so `files_modified` and the wave guard cannot see the overlap — this paragraph is the declaration.
Everything below runs from `src/`: vitest transpiles TypeScript, and `npm run lint` and
`npm run typecheck` write nothing (`noEmit: true` in `tsconfig.base.json`). Task 2's suite is filtered to this plan's own test
file: the unfiltered `--project cli` run would execute `bin.test.ts` and `new-ticket.test.ts` while
09-01 is mid-edit of both, and spawn a `dist/cli.js` 09-01 is mid-rebuild. 09-06 Task 1 runs the
whole suite once the wave has settled.

    Create `.github/workflows/publish.yml`. **Fix this filename now and never rename it** — the npm
    trusted-publisher record configured in 09-05 matches on the filename exactly, and renaming it
    later produces an authentication error on a workflow whose diff shows no change.

    Trigger: `on: push: tags: ['v*']` and nothing else. Do NOT add a `paths:` filter — a job that
    skips itself leaves a required status check pending forever (the same trap D-138 already names
    for the emitted `accord.yml`).

    Declare `permissions` at **job** level, not workflow level: the `publish` job gets
    `id-token: write` (this is what mints the OIDC token) and `contents: read`; the `smoke` job
    declares nothing, so it cannot inherit a write scope it has no use for. `ci.yml` declares its
    permissions at workflow level — deliberately diverge here and say why in a comment.

    Do NOT add an `environment:` key. It is optional per npm's documentation, and an environment
    whose branch protections do not allow the tag ref blocks the job with an error that reads
    nothing like its cause.

    **Job `publish`**, `runs-on: ubuntu-latest`, declaring
    `outputs: { version: <the version-check step's output> }`:

    1. `actions/checkout@v7`.
    2. `actions/setup-node@v7` with `node-version: 24`, `registry-url: 'https://registry.npmjs.org'`,
       and `cache: npm`. `registry-url` is load-bearing: it writes a project-level `.npmrc` pointing
       at the registry, which is what the OIDC exchange targets. Do NOT add `always-auth` — that
       input does not exist on this action. Node 24 because trusted publishing requires npm 11.5.1
       and Node 22.14 on the runner, and Node 24 ships npm 11.19.0; comment that fact beside the
       version so the reason survives.
    3. Do **not** add `npm install -g npm@latest`. `.claude/CLAUDE.md` decision 6 prescribes it; it
       was written when Node 22's bundled npm 10.9.8 was below the trusted-publishing floor. On
       Node 24 it is one more network call that can fail. Leave a comment saying it becomes
       mandatory again if this job ever moves to Node 22.
    4. The tag-vs-manifest check, **before anything is installed or built**, with a `name:` in the
       house voice, `shell: bash`, `set -euo pipefail`, an `id:` so its output is addressable, and
       the tag bound through `env:` rather than interpolated into the script body. Read the manifest
       with `node -p` over `./packages/cli/package.json` — a JSON parser is already on the runner and
       a regex over JSON is the classic silently-wrong step. Strip the leading `v` from the tag with
       a shell parameter expansion and compare the two strings with shell inequality: no semver
       library, no range, no tolerance, exactly the rule `pinMessage` enforces. On mismatch, print
       both values to stderr naming which is which, and exit 1. On match, append a `VERSION=` line
       to both `"$GITHUB_ENV"` and `"$GITHUB_OUTPUT"` — `GITHUB_ENV` does not cross a job boundary,
       so the smoke job needs the `$GITHUB_OUTPUT` half. Comment the `node -p` line explaining that
       `-p` evaluates in CJS scope, which is why `require` works in a `"type": "module"` repository.
    5. `npm ci`.
    6. `npm run check` as ONE step (D-152), not the four separate script steps `ci.yml` uses.
       Comment why one run rather than the 2-OS x 2-Node matrix: `ci.yml` already runs that matrix on
       every push to `main`, and the one hole it cannot cover is a tag pointing at a commit that
       never went through CI, which a single check closes.
    7. The publish step, named in the house voice. `set -euo pipefail`. Probe the registry first with
       `npm view "<pkg>@<version>" version 2>/dev/null || true` and compare the captured output to
       the version: if equal, echo that it is already on the registry and exit 0. The `|| true` is
       load-bearing and must carry a comment saying so — on the first publish the package does not
       exist at all, so `npm view` exits non-zero with E404, and a guard without `|| true` under
       `set -e` would fail the very release it protects; the emptiness of stdout is the signal, not
       the exit code. Otherwise run `npm publish --workspace packages/cli --access public`. Pass
       `--access public` explicitly even though npm 11's default for a new package is already
       public: it is a no-op under the current default, correct under the historical default, and
       self-documenting at the one call site that matters. Do **not** pass `--provenance` — npm
       generates and publishes the attestation automatically under trusted publishing, and the flag
       changes the failure mode on a non-OIDC path.

    **Job `smoke`**, `needs: publish`, `runs-on: ubuntu-latest`, and deliberately **no checkout**:
    `npx --yes <pkg>@<version>` in a bare runner with no `package.json` and no `node_modules` is the
    closest thing Actions offers to criterion 1's "clean machine". One `actions/setup-node@v7` step
    with `node-version: 24`, then one `shell: bash` step with the package name and
    `needs.publish.outputs.version` bound through `env:`. `set -uo pipefail` here, not `-e`, with a
    comment saying why the two jobs differ: the retry loop reads a non-zero exit as "not yet
    visible" and must not be stopped by it.

    The loop: 12 attempts, `sleep 15` between them, a three-minute budget, echoing the attempt
    number each time. Inside a successful invocation, compare the last printed line to the expected
    version — if it differs, fail immediately rather than continuing to retry. Collapsing *not yet
    visible* into *visible but wrong output* would let a genuinely broken bundle burn the full budget
    and then report a propagation failure. Do NOT use a fixed `sleep` before a single attempt: both
    a 3-second and a 60-second fixed budget are documented as too short in real release pipelines.
    Do NOT set `continue-on-error: true` on this job — it is the only proof for criterion 1's clean
    machine clause, and evidence that can be ignored is not evidence.

    The whole document is LF with one trailing newline, matching every other file the repository
    emits.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| a pushed git tag → a shell step on a runner holding registry write access | The tag name is a maintainer-controlled string that flows into a script. |
| GitHub Actions OIDC → the npm registry | The publish job holds, for the length of one job, the authority to write a package every user installs. |
| the npm registry → a clean runner | The smoke job executes whatever was just published. |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-09-10 | Tampering | the version-check `run:` body | high | mitigate | The tag is bound through `env:` and referenced as a shell variable; it is never interpolated into the script text with an Actions expression.
