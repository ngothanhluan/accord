    Per the skill's step 7 and D-158: open a **subagent** — the first branch of D-109, because the
    runtime provides one — and hand it `.claude/skills/accord-dev/review.md` and the ticket id and
    the commit being reviewed, and nothing else. The context that wrote the code does not write
    `verification.md`, and does not edit it afterwards either. A finding it disagrees with is a
    finding; a defect the reviewer names goes into the review and is fixed as new work, not edited
    out of the record.

    The reviewer writes `accord/tickets/README-1/verification.md` with `ticket:`, `commit:` and
    `reviewed_on:` in its frontmatter, one `## @ac-n <scenario name>` block per scenario in tag
    order, each with a `Result:` line and an `Evidence:` line beginning their own lines. `commit:` is
    the commit it reviewed.

    Then, per step 8, **the developer** runs the scenarios and ticks `verified:` in the ticket
    frontmatter, writing one line per scenario under `## Verification notes` naming the logic that
    makes it correct. Nobody else ticks — not the review context, not whoever wrote the acceptance
    criteria.

    **The commit binding, stated explicitly so step 9 is not a surprise.** `gate done` compares the
    ticket's `verified_commit` and `verification.md`'s `commit:` against the checkout's `HEAD`. Both
    must name the commit you are gating, which is the last *implementation* commit. So: run
    `accord gate done README-1` with the review file and the tick edits present in the working tree
    and **not yet committed**. That is the only arrangement in which the values can equal `HEAD`, and
    it is how the gate is designed to be run — 09-08 Task 1 carries the probe that establishes it.
    Capture the PASS transcript at that moment; it is ROADMAP criterion 3's evidence and it cannot be
    reproduced after the next commit.

    Then commit the review file and the tick edits as the final commit on the branch. Expect that a
    re-run of `gate done` after that commit reports `gate.tick-stale-commit` and `gate.stale-review`.
    That is the structural gap recorded in 09-08 Task 1, not a mistake in this task — record the
    re-run output too, because it is the evidence for whichever option was chosen there.

    Do not relax a rule to obtain the PASS, and do not rewrite `verified_commit` to chase `HEAD`
    across commits: it does not converge, and the attempt would be the wrong lesson to take from the
    dogfood.
  </action>
