Can AI-DLC (awslabs/aidlc-workflows) replace accord?

Survey of 2026-09-14. Sources: README, rule files and docs on GitHub, for both the v1 branch (1.0.1, rules-only) and main (2.8.2, with a CLI). Branch v1 is 301 commits behind main.

Conclusion: it cannot replace accord. v1 is a set of prompt rules with no deterministic check at all, exactly the kind of "general planning system" accord was set up to replace. v2 has a real engine and sensors, but it is a 33-stage lifecycle aimed at AWS, with no MCP server for non-technical people, no Gherkin parsing, and sensors that only warn by default. Accord's three defining requirements (a deterministic Ready/Done gate on Gherkin, a BA working through a chat app over remote MCP, no API key) are missing from both versions. Keep going with accord and borrow the 3 ideas below.

3. Options

OptionGainLoss
A. Use aidlc v1 instead of accordNothing to build.No gate beyond the model's promise. Exactly the failure mode accord targets (36% instruction-following failure). No way in for the BA.
B. Use aidlc v2 instead of accordEngine, sensors, audit and reviewers ready-made; maintained by the AWS team.Many times heavier than an agency's 2–6 week need; Bedrock by default; no MCP server; no Gherkin/EARS; no ticket/tracker; has to live inside their aidlc/spaces/… structure.
C. Hybrid: aidlc v2 for dev, accord only for the gate + MCPLess workflow to build.Two systems, two folders, two states; accord has to read aidlc's artifacts instead of its own tickets. Breaks "the process and the check must not drift".

5. A closer reading of the three proposals (2026-09-14, round 2)

Sources: v1 question-format-guide.md, overconfidence-prevention.md; v2 intent-capture.md, aidlc-sensor-claim-sources.ts (1,420 lines), aidlc-sensor-traceability.ts (637 lines), code-generation.md, build-and-test.md, stage-protocol-reviewer.md. Compared with accord's docs/design.md §2, §5 and packages/core/templates/verification.md.

5.1 v1: the question file and the answer check

The real mechanismFor accord
Never ask in chat. Every question lives in a <stage>-questions.md file, as multiple choice A–E, "Other" mandatory at the end, and the user fills in after the [Answer]: tag. The agent re-reads the file only when the user says "done".Borrow in part. For a BA working through a chat app + MCP, the questions live in the ticket (## Open questions), not in a separate file. The "Other is mandatory" and "do not invent options to fill A–D" rules belong in the BA workflow text.
Once answers exist, a check is mandatory: vague words ("mix of", "somewhere between", "not sure", "depends", "maybe", "probably"), undefined terms, answers that contradict each other (scope "bug fix" but "entire codebase affected"), answers that merge several options. If any are found, create a -clarification-questions.md file and do not move on.Borrow. The vague-word part is a regex, put in lint as a warning on ## Requirements, ## Acceptance criteria and the answers in ## Open questions. The contradiction part is the model's judgment, put in the readiness review text of the BA workflow.
overconfidence-prevention.md: they once shipped a rule "ask only when really needed" and the model skipped questions; it had to be flipped to "when in doubt, ask".A lesson in the direction accord is already taking: a gate blocks Ready while an open question remains, instead of trusting the model to notice on its own.

5.2 v2: the claim-sources sensor

The real mechanismFor accord
The question file opens with ## Sources: [desc] (the original description, matched byte for byte against project-description.json), [scope], [memory:M1] (must match exactly one rule line under exactly the right H2 heading in org/team/project.md). That is the whole universe of allowed sources.Do not borrow. A source tag on every passage is too heavy for a spec of 5–15 EARS lines. accord's sources are already fixed: Intent → Requirements → AC, in one file, with the BA as sole owner.
Every paragraph, list item and table row in the deliverable must carry at least one tag: [desc], [Q<n>] (must have a filled-in answer), [scope], [memory:…]. [assumption] may only appear in ## Assumptions & Open Questions.Do not borrow, for the reason above.
A remaining assumption must be confirmed by a person with the exact answer string A. Accept assumptions, and the text of each assumption at confirmation must match (after normalisation) the text in the artifact. The agent cannot delete the section or change an assumption once approved. "Acceptance does not turn an assumption into fact."Borrow the idea. accord already has assumptions: in the frontmatter and the rule "unconfirmed block Ready". What it adds: the confirmation must be a BA action recorded in git (the author is the evidence), and a confirmed assumption stays in the ticket instead of being deleted.
1,420 lines of TS, mostly to tell whether [Q1] is a tag or a CommonMark link reference (definition, container, indented code, title continuation…). They chose "fail-closed": better to flag falsely than to let one through.Confirms accord's choice: assumptions live in the YAML frontmatter, with no tags embedded in Markdown prose, so this parser does not have to be written. Keep as is.

5.3 v2: traceability.json and the Target Verification Matrix

The real mechanismFor accord
stories.md numbers IDs US1.2, AC1.2.3, requirements FR1/NFR1.1, rules BR1.1. The sensor pulls the IDs out of the upstream artifacts with a regex, requires upstream_ids to equal exactly that set, every ID to have a coverage row, a closed status OK/GAP/ORPHAN/Deferred/N/A, and OK/Deferred/N/A to have a target.accord already has a stronger equivalent: the @ac-n tag in Gherkin, scenario set = evidence set = verified set. No need to add anything.
At code-generation, the target of an OK must be a relative path in the workspace that exists, is a file, and does not escape the project. It only checks that the file exists; it does not run tests.Borrow one small rule: Evidence: in verification.md is free text today. Design §5 already requires the dev's ## Verification notes to name a path or symbol present in the snapshot; applying the same rule to the reviewer's Evidence: is a cheap lint. Running the tests, accord is already stronger (@test:<id> + JUnit XML).
Build and Test: a matrix of Target ID / Expected / Actual / Evidence / Owning Stage / Verdict, with a final verdict of Met | Not Met | Unverified; Pending may not remain when the stage ends; a "deferred" target is still Unverified and does not count as a pass unless a later stage takes responsibility; "Weakening, relaxing, lowering, or disabling a defined quality target is never an acceptable fix."Close to accord's Result: pass | fail | blocked. Two points design.md does not spell out yet, which need your decision (see §6).
Cross-unit final coverage gate: every FR/NFR/AC must be OK in at least one traceability.json and the target file must exist; any missing ID is a finding at the gate.This is exactly accord's Done gate at ticket level. Nothing to add.

5.4 v2: the reviewer protocol (read further because it is close to fresh-context review)

The real mechanismFor accord
The reviewer is a separate sub-agent and receives: the stage definition, the Q&A file, the artifact, the upstream contracts. It does not receive memory.md or the builder's plan: "The reviewer forms independent judgment."Borrow. accord's ticket holds both a ## Plan and ## Verification notes (dev-owned). The review context should be told to skip these two sections and read only the AC + code + test results. One line in the dev workflow text.
Adversarial contract: "Refute, don't confirm. READY is the verdict it fails to reach after trying to break the artifact, not the default it starts from." A finding based only on opinion is a suggestion, not a reason for NOT-READY.Borrow the wording for docs/skills/code-review.md; that skill already has "every finding must name a concrete failure scenario", in the same spirit.
The logger takes a byte fingerprint of the artifact when it is sent for review; a verdict is rejected if the bytes changed. After a verdict, the review-freeze hook blocks writes to the artifact until the approver acts. The reviewer may write exactly one review file.accord binds through commit: in the verification.md frontmatter, and the tick binds to the AC hash + commit sha. Need to be sure the Done gate compares the commit: of verification.md with the commit being gated (see §6).
Reviewer bookkeeping must not live in the artifact (no "reviewed", review round or finding status written into the deliverable) because it goes stale by construction.accord already separates these: verification.md is its own file, ticks sit in the frontmatter, QA lives in the tracker. Keep.

6. Decisions (answered 2026-09-14)

QuestionDecisionRejected option
Q1. Does Result: blocked in verification.md make Done fail, or is it only a warning?Fail. Blocked means not yet verified.A warning if the scenario carries the @ui tag; fail for the other scenarios.
Q2. What does a @test:<id> test in the skipped state in the JUnit XML count as?Not passed, Done fails. Switching a test off is a way around the gate.Treat it as a missing report (check skipped) when the whole file lacks that test.
Q3. Does the Done gate compare commit: in verification.md with the HEAD being gated, or only the verified tick binding the commit?It compares; a mismatch fails. Whatever the dev fixes after review, review runs again.Only a warning, because the reviewer may run before the dev fixes a small bug.
Q4. Where does the vague-word lint apply?A warning on Requirements, AC, and the answers in Open questions. It does not block Ready because the regex has false positives.Block Ready under the maintain profile, warn under build.
