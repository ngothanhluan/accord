  <name>Task 1: ROADMAP criterion 2 cannot be met as planned — decide how it is satisfied</name>
  <decision>Decide how ROADMAP criterion 2's *green* is satisfied, given that a pull-request-carried ticket cannot pass `gate done`.</decision>
  <context>
    **This was found at planning time by running the gate, and it changes what the rest of the phase
    can promise. D-162 is correct and necessary, and it is not sufficient.**

    The finding: **a pull request that carries a ticket at Done can never make `gate done` pass.**
    Not with D-162's `ref:` fix, not without it. The reason is structural, not a bug:

    - `tickStaleCommit` compares the ticket's `verified_commit` to `snapshot.git.commit`, and
      `staleReview` compares `verification.md`'s `commit:` to the same value
      (`packages/core/src/gate/done.ts:203-227`).
    - That value is the checkout's `HEAD` — `git show -s --format=%H HEAD`
      (`packages/cli/src/load/fs.ts:76`).
    - A file cannot carry the sha of the commit that contains it. So once the ticks are *committed*,
      `verified_commit` necessarily names an earlier commit than `HEAD`, and both rules fire.

    Probed rather than reasoned, on 2026-09-21, against a scratch clone of `examples/maintain` with
    the real built CLI:
    - ticks present in the working tree but **not committed**, `HEAD` at the implementation commit →
      `gate done` prints `0 errors, 1 warnings` and exits **0**.
    - the same edits **committed**, nothing else changed → `gate.tick-stale-commit` and
      `gate.stale-review`, `2 errors`, exit **1**.

    D-162 changes *which* commit is gated — the branch head rather than GitHub's synthetic merge
    commit — which is the correct semantics and fixes a genuine defect. It does not close the gap,
    because the branch head is still a commit the ticket file cannot name.

    This repository already knew: `.github/workflows/ci.yml`'s `examples` job rewrites the
    placeholder sha to the sandbox HEAD before gating, with the comment *"a file cannot carry the sha
    of the commit that is about to contain it"*. That workaround is available to a fixture and is not
    available to a real branch.

    The consequence for this phase: ROADMAP criterion 2 (*the generated CI workflow is green*) and
    criterion 3 (*one real ticket reaches Done*) cannot both be satisfied by one pull request that
    carries the ticket, which is what D-155 describes.
  </context>
  <options>
    - **(a) Let the check go red, and record the finding (recommended).** Open the pull request as
      D-155 describes. The `accord` job installs the published CLI through `npx`, lints, derives the
      ticket list from the diff exactly as D-137 intends, gates the ticket, and reports a real
      failure with a real reason. Criterion 2 as literally worded — *green* — is then **not met**,
      and the reason is recorded as the most valuable thing the dogfood found. File the gap as a v0.2
      requirement. Cost: the milestone closes with one criterion re-worded or carried.
    - **(b) Land the ticket on `main` first, then open a pull request that touches no ticket file.**
      The workflow prints *"no ticket file changed in this pull request - nothing to gate"* and exits
      with lint's code, so the check is green. Cost: the green check gates nothing — which is the
      exact failure mode this repository spent Phase 7 guarding against (`scaffold.test.ts:230`:
      *"a gate that silently passes is worse than no gate"*), and it defeats D-155's own stated
      reason for opening a pull request at all.
    - **(c) Change what the tick binds to — a gate change, deferred to v0.2.** Bind the tick to the
      last commit that changed something *outside* `accord/tickets/`, supplied as a new host fact by
      the CLI. This is the honest fix and it is a gate-semantics change, which this phase's domain
      block rules out ("no gate rule changes and no lint rule changes").
    - **(d) Accept any ancestor of the gated commit — also a gate change, also v0.2.** Requires an
      ancestry fact core cannot compute from a single sha, so the host contract grows.
    - **(e) Push one more commit re-pointing `verified_commit` at the previous head.** Named only so
      nobody attempts it: it does not converge. Each push moves `HEAD` again.
  </options>
  <recommendation>
    **(a).** It is the truthful outcome, and (b) is ruled out by the project's own stated value — a
    gate that passes without gating is worse than no gate, and buying a green check with one would
    make the milestone close on the anti-pattern Phase 7 was built to prevent. (c) is the real fix
    and belongs in v0.2, where it can be designed rather than squeezed into a publish phase.

    If you take (a), the concrete follow-ups are: reword ROADMAP criterion 2 to what the pull request
    can actually demonstrate, and add a v0.2 requirement for (c). Both are small; neither is this
    plan's to do unilaterally.
  </recommendation>
  <resume-signal>Type the option letter, plus any rewording you want for ROADMAP criterion 2.</resume-signal>
</task>
