# Ledger

## Rulings

- Ruling: the upgrade's pull request is opened the way the skills already open one, `gh pr create` when `gh` is available, otherwise the pushed branch is named for the owner to open by hand; the CLI itself never calls `gh` — the same pattern as packages/core/skills/accord/lane-s.md:58 and verify/ci.md:23, and adapter `none` stays usable — cost if wrong: an owner without `gh` opens the pull request by hand.
- Ruling: the registry check uses `fetch` with a short time limit, never spawns `npm`/`npx` (CLAUDE.md, What NOT to Use), runs at most once a day per machine with its result cached outside the repository, and says nothing when offline or when the registry fails — the owner's direction of 2026-10-19 that this ticket starts from — cost if wrong: a new release is announced up to a day late.
- Ruling: `accord upgrade` takes no version: it is run as the version wanted (`npx --yes @accord-dev/accord@<new> upgrade`, the version the notice names) and pins its own version, because skills sync writes the running version's skills and the pin check refuses a mismatched CLI; `upgrade` is exempt from the pin check as `init` is — cost if wrong: the interface gains a version argument at approach, back to the owner.
- Ruling: a Continue merge that conflicts is aborted, so the ticket branch is left as it was, and Continue exits 2 naming the conflicting files and the merge to run by hand (D-01); it gets a `risk:` test rather than a criterion, to keep five — cost if wrong: the owner wants it as a criterion at the yes.
- Ruling: a failed registry request counts as the day's request, so an offline machine pays the time limit at most once a day — cost if wrong: a release made public after a failed check is announced a day late.
- Ruling: the automatic clean also deletes the merged ticket's branch on origin (part 4 as the owner confirmed it), unlike ST-LN-20, which left remote branches alone; its tip is already on main, so no commit is lost — cost if wrong: a teammate's checkout of that branch loses its upstream.
- Ruling: the audit's split readings are settled in the criteria's wording — ac-1: "once a day" is a rolling 24 hours, not a calendar date, and the line must show by the second run, so the check may run in the background or inline (left to the approach); ac-2: a failed request counts as the check (per the ruling above) and the registry request is given up after 3 seconds; ac-3: the branch is cut from origin's latest main and the pin is the running CLI's own version; ac-5: "merged" is the branch tip being on origin's main, as `worktree clean` judges it today (ST-LN-20 D-03, so squash merges stay), "no session holds it" is the hold `worktree open` already records (ST-LN-7), and `accord worktree clean`, which the bare `/accord` runs, is a row of its own — cost if wrong: the owner rewords a criterion at the yes.
- Ruling: the 3-second registry limit is accord's own figure — long enough for a slow link, short enough that an offline session start is barely delayed once a day — cost if wrong: one number to change.
- Ruling: approach: Continue merges only when the ticket worktree has no uncommitted tracked changes and no merge in progress, and only after the hold is taken; otherwise it prints the `behind:` line and does not merge — the conflict path aborts on MERGE_HEAD and could abort the owner's own merge in progress — cost if wrong: a dirty worktree stays behind until it is committed.
- Ruling: approach: a failed push after the Continue merge prints one line and Continue goes on, never exit 2 — the merge commit is local and safe — cost if wrong: the owner wants exit 2.
- Ruling: approach: the automatic clean skips the ticket being opened, and deletes a merged origin branch only once the local branch is deleted or absent, so a kept worktree keeps its upstream — cost if wrong: a merged branch stays on origin until the next clean.
- Ruling: approach: the upgrade branch is `upgrade/<version>` (like `drop/<id>`); `upgrade` refuses with exit 2 and creates nothing when that branch already exists on origin, when origin's main already pins the running version or a newer one, or when `.claude/settings.json` there is not a JSON object (planHooks' refusal text); its success output follows drop's `branch:` / `base:` / `title:` lines — cost if wrong: a name and some wording change.
- Ruling: approach: the config pin is rewritten by changing only the top-level `accord:` line, keeping its comment, then checked with `loadConfig`; the workflow pin is an exact replacement of `<pkg>@<old>`, so the owner's own workflow edits survive — cost if wrong: a hand-reformatted pin line is refused rather than rewritten.
- Ruling: approach: the registry is the public registry.npmjs.org and `.npmrc` is not read (the CLI never spawns npm); a version is printed only when it matches `^\d+\.\d+\.\d+$`, since it enters the agent's context; "newer" compares major.minor.patch as numbers — cost if wrong: a machine that only reaches a private mirror never sees the notice.
- Ruling: approach: `accord dashboard --json` is unchanged; the notice is in text mode only, printed first, since the skill reads the actions from the last line — cost if wrong: a JSON consumer misses the notice.
- Ruling: approach: the notice line names the whole command, `npx --yes @accord-dev/accord@<new> upgrade`, so the `/accord upgrade` route takes it from there and no skill hard-codes the package name — cost if wrong: the route reads the name from the session rules line instead.
- Ruling: approach: the background registry check (architect option 3) is dropped — no criterion needs zero wait, and a detached child adds orphan and cache-race risks on Windows — cost if wrong: an offline session start waits up to 3 s once a day.
- Ruling: critic 4 — after a Continue merge, setup and the push run before the pin check, so a merge that brings a new pin (an upgrade landed on main) is still set up and pushed; the pin check then exits 2 with its usual message naming the version to run — cost if wrong: one extra Continue with the new version.
