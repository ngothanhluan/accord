# Ledger

## Rulings

- Ruling: the stage treats "a review round of the changes after C is recorded" as a commit touching review.md after the last hand-made commit, with a valid verdict as the file's last line — the stage sees commits, not round contents — cost if wrong: a round that does not cover the fix lets the ticket reach verify, where only the verifier would catch it.
- Ruling: "from the main branch" means commits reachable from origin's default ref, else the local default branch; with neither, every merge counts as a change — errs toward an extra review — cost if wrong: an extra review round after a merge from an untracked main.
- Ruling: the git fact is computed only while the verified commit is not reachable from the default ref, so a merged ticket stays done on main — post-merge failures are a new ticket by the intent — cost if wrong: a squash-merged branch keeps today's behaviour.
- Ruling: on git older than 2.36 the fact is read without --remerge-diff and merges count as changes, and no git error makes status, anchor or dashboard exit 2 — those commands must keep working — cost if wrong: an extra review round on old git.
- Ruling: a failure only CI's operating system shows keeps one debug episode open across verifies: red evidence is the CI log, green is CI at the next verify, and the failed-fix count carries over — the executor cannot see red on a skipped test locally — cost if wrong: the episode ends only when CI is green, so Continue keeps returning to debug until then.
- Ruling: the fix review after verify gets its own cap of five rounds, counted from the first round after verify — D-03 applies review's rules to the fix as a new review — cost if wrong: a ticket that used five rounds before verify gets five more.
- Ruling: a New request whose text reports a failure in a ticket at verify or done, and `/accord continue <id> <text>`, route to that ticket's debug, not to lane S — otherwise the ST-LN-20 path (main session fixes) survives — cost if wrong: a genuine new small request that mentions such a ticket is offered debug first.
- Ruling: the approach critic's two rounds are settled in the Approach, each finding fixed in the option or kept as a named risk there — cost if wrong: a finding resurfaces at plan review.
- Ruling: `Review` gains `trailing?: true` when a non-blank line follows the last verdict line, and a `review.md` commit closes a pending fix only when it is not set — record.md says nothing follows the verdict, and leaving the field absent keeps every existing `parseReview` expectation equal — cost if wrong: a round committed with text after an old verdict reads as unreviewed, which means one extra review.
- Ruling: the commits after verify exclude the default ref (`^<def>`), so a merge from main lists only the merge commit; one `git rev-list --ignore-missing <commits> ^<def>` drops tickets whose verified commit is on the default ref — this applies the "from the main branch" Ruling with one spawn instead of one per ticket — cost if wrong: an unknown verified sha reads as merged, so the ticket keeps today's stage.
- Ruling: the fact is read only for tickets with a tip: the current branch's ticket (HEAD) and non-terminal claim-view candidates, using the claim ref's own `verified_commit` — tickets with no branch cost no process — cost if wrong: `accord anchor <id>` run from the main checkout for another ticket shows today's stage.
- Ruling: the review base is the first parent of the first hand-made commit after the later of `verified_commit` and `verification.md`'s commit that no later valid `review.md` commit has closed — the fix review then covers only changes after the last recorded round — cost if wrong: a review package that is too small after several fix rounds.
- Ruling: `review-package` excludes the default ref only when HEAD is not on it and the default ref holds commits in `<base>..HEAD`; in that mode the stat and diff are per-commit with `--remerge-diff` — no cumulative diff can drop main's changes without merge-tree — cost if wrong: a reviewer reads per-commit patches in that case.
- Ruling: CI conclusions: `success` passes; `failure`, `timed_out` and `startup_failure` fail; every other conclusion is not checked, by name — the criterion names only cancelled and skipped — cost if wrong: a timed-out run opens a debug episode.
- Ruling: verify's local `accord lint` and `accord gate done` after the tick run in every case, but push and `gh pr ready` run only when Start pushed — without GitHub there is nothing to mark ready — cost if wrong: none found.
- Ruling: the accord skill's Continue step 2 drops "It prints the stage and the position from the ledger, then the owner's words verbatim." so the rendered `SKILL.md` stays under 5120 bytes with the `./failure.md` pointer — the anchor output itself is unchanged — cost if wrong: one less cue to re-read the owner's words.
- Ruling: the after-verify routing lives in `shared/failure.md`, loaded by the accord, debug and verify skills — `accord/SKILL.md` has about 14 bytes left under the cap — cost if wrong: none found.
- Ruling: CI checks are read per job through `gh run view <run-id> --json jobs`, not through `gh pr checks` — `gh run list --commit <sha>` keeps "only checks on the pushed commit count" (D-09) and gives the run ids that `gh run view --log-failed` needs, while `gh pr checks` reads the pull request's current head rather than a given commit — cost if wrong: one extra gh call per run.
- Ruling: before the first tick, the stage's start commit is `verification.md`'s `commit:` — the verifier writes it at step 3, before the CI wait at step 4 — cost if wrong: a leftover `verification.md` from an earlier verify run moves the start of the fix review back, so the review package is larger.
- Ruling: the commits after verify are also read in `stage` mode for every claimed ticket whose checkout copy has a start commit, using its claim ref; this replaces the Ruling above that read the fact only for the current branch's ticket and claim-view candidates (plan review 1.9: a Ruling cannot narrow @ac-3) — cost if wrong: one extra git process per such ticket on `anchor`, `next` and `hook`, and such a ticket is read twice in claim-view mode.
- Ruling: a ticket counts as having reached verify when `accord anchor` prints `verify` or `done`, or it has a `verified_commit:` or a `verification.md` — @ac-1's Given says "reached", and a ticket back at `review` after a fix has reached verify — cost if wrong: a failure reported during review of a fix after verify opens or rejoins a debug episode instead of being handled in review.
