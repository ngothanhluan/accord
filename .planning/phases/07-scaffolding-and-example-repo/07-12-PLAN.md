<surfaced_assumptions>
- **A-38 — `latin1` is the whole fix, and it is a fix rather than a different mangling.** Verified by
  running, on this host (Node 24, Windows), before this plan was written, on the exact bytes the
  verification report carried (`63 61 66 E9 20 96 20 64 61 73 68 0A`): the utf8 round-trip does not
  preserve the prefix; the latin1 round-trip does; the appended ASCII block is byte-identical
  afterwards; and a genuine UTF-8 file with multi-byte characters also survives the latin1 round-trip
  byte for byte. `latin1` maps `0x00`-`0xFF` onto U+0000-U+00FF in both directions with no
  substitution, which is why it is byte-exact for input it was never meant to describe.
  *Alternative rejected:* reading a `Buffer`, deciding on `buf.toString('utf8')`, and writing
  `Buffer.concat([buf, Buffer.from(suffix)])`. It needs `pointerText` to return the suffix rather than
  the whole file — a core signature change, in core, to fix a defect that is entirely on the CLI side
  of the seam.

- **A-39 — the mid-loop throw is reachable deterministically, and only through a direct call.**
  `writeSkillFiles`'s docstring says the caller owns the `assertNoLink` pre-pass, and both callers run
  it, so a bad path never reaches the loop through a command. Calling the exported function directly
  with a target whose path is an existing DIRECTORY makes `readFileSync` at `skills.ts:47` throw
  `EISDIR` — confirmed by running on this host, and the same errno on POSIX. No permission games, no
  platform-specific `chmod`, nothing that behaves differently for a CI container running as root.

- **A-52 — GC-WR-01 is a type decision, and the plan makes it rather than leaving it to the executor.**
