# Release notes

Each section lists what changes for tickets in flight and for repositories pinned to an older accord. A release pull request copies the `## Unreleased` section into its `release:` commit body and renames the section to the release version.

## Unreleased

These changes are on main and not yet released. Tickets in flight are unaffected, unless the repository sets a `branch` with `{type}` (the last bullets say what that needs); a repository pinned to an older accord gets them with `accord upgrade`.

- The claim branch template `branch` takes two more tokens, `{type}` and `{slug}`, each at most once beside the one `{id}`, so a team can name branches `fix/ABC-124-order-total-is-null` (GitHub issue 341). `{slug}` is the ticket title in ASCII kebab-case (accent marks removed, other non-ASCII letters dropped), cut at the new `branch_slug_length` (default 40). `{type}` is the ticket's new optional `change:` word, one of the new `branch_types` (default `feat`, `fix`, `refactor`, `perf`, `docs`, `test`, `build`, `ci`, `chore`, `revert`, `hotfix`); no type is guessed from `type:`.
- `accord new ticket` and `accord worktree open <id>` take `--change <word>`, checked against `branch_types`. Under a `{type}` template a claim whose ticket has no allowed word is refused before any git write, and the refusal prints the words and `--change`; the agent proposes a word and runs the command again with it. `--change` on `worktree open` also writes `change:` in the claim commit of an older draft, and on a ticket that holds another word it names the new branch from the `--change` word.
- `accord gate ready` fails with `gate.change-type`, naming the allowed words, when the claim template uses `{type}` and `change:` is missing or not listed. `accord lint` warns with `lint.branch-type-root` for a `branch_types` word that is also the first segment of a branch accord makes itself (`t`, `backlog`, `drop`, `conventions`, `upgrade`, `accord-task`); no word is refused. Both rules may be lowered through `strictness.levels`.
- A claim branch is found by a `{type}` template only under the words of `branch_types`, so a hand-made `drop/ST-9-x` or `wip/ST-9-x` is no claim. Removing a word from `branch_types` while a ticket still runs under it stops that ticket's branch being found; remove a word only between tickets.
- A later change of a ticket's title, or of its `change:` to another listed word, committed on its claim branch keeps the same branch as the ticket's claim. Among the ids a name can carry (`ST-LN-13-add-retries` holds several) the reader picks a known ticket, else an id of the repository's shape (`ids.pattern`, a tracker key with `ids.projects`, or a `legacy_ids` entry), else the shortest, and starts no git process for it. A teammate's `fix/ST-AB-5-add-retries` that this checkout lacks reads as `ST-AB-5` and is no audit orphan.
- When origin's default branch has no readable `branch` template (a local-only install whose `accord/config.yml` is git-excluded), a new claim is named by the checkout's `branch`; a template on the default branch still wins. A new worktree with no `accord/config.yml` runs the `setup` of the checkout that opens it; an invalid `accord/config.yml` in the new worktree still refuses.
- The finish and verify-ci steps define `<branch>` as the branch `git branch --show-current` prints in the ticket's worktree, so the pull request query finds a `{type}/{id}-{slug}` branch.
- Choices made for this change: a `branch` template refuses two tokens with nothing between them, such as `{type}{id}`, because a token next to `{id}` makes the id impossible to split out of a name. A title with no ASCII letter or digit gives the slug `ticket`, so a name never ends on a separator. `branch_slug_length` is a whole number from 1 to 99 written as a string, which keeps a name far under file-system limits. With no allowed change word, `{type}` stays literal in the branch an unclaimed row shows in `accord status`, and both claim commands refuse before any git write. An epic needs no change word, since it is never claimed on a branch of its own. `gate.change-type` and `lint.branch-type-root` are rules a team may lower, while the claim refusal still holds. `--change` is refused with `--split` and with `--continue`, and on a pick-up that finds an existing branch it changes nothing. `gate.change-type` judges the template a claim would use, the default branch's, else this checkout's `branch`. It has no claim-pin cut-off, because every earlier release's schema refuses a `{type}` template.
- More choices: `lint.branch-type-root` fires for a listed word that is one of accord's branch prefixes whether or not `branch` holds `{type}`. The `{type}` expansion, `branch_types` and `branch_slug_length` are read from this checkout's `accord/config.yml`, like the rendering and the gate, so a checkout whose config lags the default branch does not see a branch of a word only the default branch lists. Among a name's candidate ids the first known one wins, else the first of the repository's id shape, else the first (the shortest), with no git process and no audit change. A branch name over 255 characters is not matched by a template with `{slug}`.
- For a ticket in flight: a repository that adopts a `{type}` template needs one `change:` line (or `--change` at claim) on each ticket not yet past `accord gate ready`; branches already claimed keep their names and are still found while their word stays in `branch_types`. A repository that does not set `{type}` or `{slug}` sees no change.

## 0.18.0 — 2026-11-24

Release 0.18.0 makes `accord audit` and the test suite faster without changing what either reports, and adds one rule to the plan stage. `accord audit` on accord's own repository starts 56 git processes instead of 254 and runs in about 8 seconds instead of about 20, with a byte-identical report. Tickets in flight: no ticket is refused for something new, and no gate reads anything that changed. A repository pinned to 0.17.1 gets the plan stage and planner text with `accord upgrade`, which moves the pin and regenerates the skill files.

- The plan stage and the planner say that, of test files, a task's `verify:` and `files:` lines name only the ones the task writes or extends; a long existing regression file runs at wave end and in CI, so a task's test run fits its time box.
- `accord audit` reads the claim commits of finished tickets, the tickets of claim branches, the authors of what a clean would remove, the tips of queued drafts and the drafts on backlog branches with one git call each instead of one or more per ticket or branch; on accord's own repository it starts 56 git processes instead of 254, and its report is unchanged. `accord dashboard`, `accord deferred` and `accord pr` read the drafts on backlog branches the same way. The dry clean `accord audit` runs reads branch tips, their place on the default branch, verified commits, dropped tickets' research records, unpushed commits and stopped rebases once per run in batches, so a leftover branch costs no git call of its own beyond the merge check of a local branch the default branch lacks, where it cost several; it reports the branches as they were when the audit read them, and `accord worktree clean` itself reads and decides as before. A draft whose history the batched read cannot decide exactly (a file added twice, a merge it cannot place) and a short `verified_commit` are still read one at a time.
- After a review of those batched reads: a path that names a directory no longer moves the answers of the reads after it in the same `git cat-file --batch`; the offline dry clean no longer counts a branch ref that points at a tag object as having no commits missing from origin (it reads that branch as before); and the batched claim reader answers an id that is not a plain ticket id with the single-ticket read. Where two claim-ruleset commits are not ancestors of each other, `accord audit` may list them in a different order than the single-ticket read would; the report is the only thing that reads it.

## 0.17.1 — 2026-11-24

Release 0.17.1 fixes the ticket tab that 0.17.0 shipped, after a review of it. A plan.md that is only untracked, which is the normal state for the whole plan stage, keeps the stage line; the `plan-changed` warning no longer fires right after the first gate plan pass; the pane's frame timer cannot raise an unhandled rejection when the host refuses a redraw; the engine's own `SubagentHandback` call is no longer shown as an agent's tool; and an agent the host lists as waiting, idle or pending is no longer marked finished. Tickets in flight: no ticket is refused for something new and no gate reads anything that changed; a ticket whose plan.md is not committed yet now keeps its stage in `accord anchor` and `accord show --json`. A repository pinned to 0.17.0 gets the fixes with `accord upgrade`, which moves the pin and refreshes the committed pane. The cost of the pane's motion at 12 frames a second is still not measured on a real terminal: the pane animates only while something runs, and each person can turn motion off in the pane's settings view (key `s`).

- A plan.md that is only untracked, which is the normal state for the whole plan stage because it is committed with the plan-ready commit at the end of it, no longer hides the stage. `accord anchor`, and the session-resume hook that prints it, keep their `Stage: plan, ...` line and add a line after it saying the plan.md is not committed yet; `accord show <id> --json` carries that as a `plan-uncommitted` entry in `warnings`, and the pane draws it under the stage track instead of `not tracked`. Only an `accord/` that git ignores still replaces the stage with the `not-committed` text.
- The `plan-changed` warning no longer shows right after the first `accord gate plan` pass wrote `plan_hash` into a plan.md that is not committed as ready yet. It shows when the plan body differs from the recorded `plan_hash`, or when a plan that was committed as ready is changed again and not committed.
- The pane no longer risks an unhandled error on every redraw tick when the host refuses a redraw.
- The pane's tool line and NOW line no longer show the engine's own `SubagentHandback` call as an agent's tool.
- The pane marks an agent finished only when the host stops listing it or lists it as `completed`, `failed` or `killed`; an agent the host lists as `waiting`, `idle` or `pending` stays running.

## 0.17.0 — 2026-11-24

Release 0.17.0 ships the live ticket tab of the flightdeck pane. Its data: `accord show <id> --json` and `accord anchor` say when a ticket's stage cannot be trusted, and `show --json` gains the task in flight and the plan's task list. The ticket tab of the Claude Code pane reads them: it tells the truth about the stage, names what runs now, lists the plan's tasks and fills the pane. It also takes each person's colours and motion from a settings view; these change only how the pane looks. Tickets in flight: no ticket is refused for something new and no gate reads anything that changed; every new key is left out when it has nothing to say, so a ticket without the data keeps its JSON as it was, and the text output of `accord show` does not change. A pinned repository gets these with `accord upgrade`; until it does, its committed pane runs the older CLI, which lacks the new keys, and draws as before. The cost of the pane's motion was not measured on a real terminal before this release (12 frames a second is not measured): the pane animates at 12 frames a second only while something runs, and each person can turn motion off in the pane's settings view (key `s`).

- `accord show <id> --json` and `accord anchor` now say when a ticket that has a plan is not committed (an `accord/` that git ignores, or a plan.md that was never committed) as `warnings` entries of kind `not-committed`. The anchor, which the session-resume hook prints, shows that text in place of its `Stage:` line, so no stage or task count is given for such a ticket instead of a wrong `plan 0/3`. The stage is still read from the records git holds; an `accord/` kept only on the machine is not supported yet.
- A plan.md that changed after `accord gate plan` passed and is not committed as plan ready, which keeps the ticket at plan, is named as a `plan-changed` warning in `show --json` and on the anchor line after `Stage:`. A ticket the stage reads at build never carries it.
- A change after the ready commit is not a warning (D-02): a plan.md body edited and committed again under the `plan: <id> ready` subject is a deliberate re-ready, the stage rule is unchanged, and `accord task-done` refuses the next task with `plan.md changed since its plan_hash was recorded`, which is what you see.
- `accord show <id> --json` adds `now` (at build only: the task in flight, the lowest task without a done line, with its plan title, the same task `accord anchor` names as next) and `tasks` (each plan task in order with its done state and the criteria its `covers:` line names, such as `ac-1`). A ticket at intent, with no plan task or with the plan stage off has no `tasks`; only a ticket at build has `now`.
- In a clone without an `origin` remote, the `log` of `accord show <id> --json` now lists the ticket's commits on its branch, read against the local main or master; before, it listed none there.
- An unreadable report folder or gate log (a folder the process cannot read, a file another program locks) no longer makes `accord show <id> --json` fail: the log simply leaves those entries out and the ticket is shown.
- A gate run with `CI` set in its environment (any value but empty, `0` or `false`) no longer writes `.accord-reports/<id>/gate.log`; nothing in CI reads the file, and a read-only workspace no longer prints a stderr line on every gate run.
- The ticket tab shows the CLI's `not committed` line in place of the stage track, the task count, the progress bar and the task list when the ticket's `accord/` folder is not committed, and shows the `plan changed` line under the stage track of a ticket whose plan is held at its stage.
- Each criterion on the ticket tab shows the verifier's result (`verify pass`, `verify fail` or `verify blocked`) beside its label, and the label and that result sit right after the criterion's text instead of at the far right of the pane.
- A NOW line under the ticket's head names the task in flight with its number and title and the accord agent working on it with its time, the review round at review, or the stage word; it reads `Waiting for you` with the time and the last line of Claude's answer while Claude waits for you.
- Executor rows in the agents block carry the task number they work on, and each agent shows its last tool by name, such as `Edit view.js` or `Bash npm`; the arguments of a tool call are never shown. The pane now also listens to tool-call events, for display only: it never changes, delays or denies a call.
- The build count and the NOW line refresh right after an accord command the session runs (a task done, a gate run), not at the next turn end.
- An agent that the host no longer lists as running is shown as finished, so a crashed or stopped agent no longer stays running in the block.
- The lower half of the ticket tab lists the plan's tasks (`✓` done, `▸` the task in flight, `·` the rest) under a progress bar of tasks done out of tasks in total, between the NOW lines and the review rounds. A ticket whose `accord/` is not committed shows none of it.
- The log merges repeated lines (such as two `gate plan PASS` runs) into the newest one with `×<n>`, draws the newest line bold, and shows as many lines as the pane has room for (at least 8, at most the 50 the CLI sends); a pane that reports no height keeps 8.
- At a narrow width the stage track keeps its line at the last stage, and a newer report or commit no longer hides a failed gate run: the failure box follows the newest gate run.
- The Claude Code pane has a settings view (key `s` on the ticket tab) for each person's own colours and motion. It holds seven colour presets (aurora, ember, ocean, forest, sunset, mono and contrast) and your own custom colours, a gradient or one colour per place, and a colour for each place of the ticket tab (title, stage track, live line, agents, progress bar, criteria, log, done tick, waiting for you, failure). A colour you type must be `#rrggbb`; the failure and waiting colours are also checked for contrast against the pane's background, and one that is too faint is refused. The settings are kept in the pane's own store on your machine, under your Claude Code configuration, never in the repository or `accord/config.yml`, so they are yours alone and shared by all your repositories; everyone starts on aurora, a gradient and the lively motion. The ticket tab no longer gives each stage its own colour: it takes the one palette you chose.
- Motion has four levels, lively, mission, calm and off, or you switch single effects (`mine`). All twelve effects are separate switches: the shimmer on the live line, the flowing gradient title, the comet progress bar, the agent equalizer, typed log lines, sparkles and a rolling counter when a task finishes, the heartbeat line, the train on the stage track, orbiting agent marks, the scrolling log ticker and breathing criteria. Lively and mission are the two presets the design sketch showed; calm moves only the shimmer and the counter; off moves nothing.
- Motion stays within a budget. One frame timer redraws the pane at 12 frames a second (at most 10 on the Desktop Code tab) only while an accord agent runs or a short burst, blink or flash plays; when nothing does, no timer runs and the pane draws still colours. While Claude waits for you the diamond on the waiting line blinks and the line glows for the first 10 minutes of the wait and then stays lit, so a long idle runs no timer; a failed gate run that newly appears flashes the failure box red for about 1.5 seconds.
- The Claude Code pane passes `claude plugin validate` again: the settings view declared an inner binding named like the hook continuation, which the validator refuses as shadowing, and it now uses another name. A test reads the pane source for the same rule.
- Probe cut (frame rate): the cost of the pane's motion was not measured on a real terminal, so no effect is cut and motion starts at 12 frames a second; the live check after this release measures the pane and, if it is over budget, lowers the rate to 6 and then cuts the costliest effects, which the settings view then names as cut for speed.
- Probe cut (colour): the pane draws every colour as `#rrggbb` and the owner did not see the hex colours drawn on a terminal; no signal exists in the plugin API that says a terminal lacks true colour or that a person wants less motion, so everyone starts on lively and a terminal that cannot draw the colours is not told apart.
- Probe cut (Desktop Code tab): whether the Desktop Code tab redraws the pane on a timer was not observed, so motion stays on there at no more than 10 frames a second and the live check decides; if the tab does not animate, the pane draws only still colours there.
- Probe cut (client module): a separate surface module animated by its own timer was not drawn live and no cost was compared, so the pane uses the one redraw route and no such module.

## 0.16.0 — 2026-11-23

Release 0.16.0 closes the leftovers of the earlier phases' reviews and live checks. Tickets in flight: no ticket is refused for something new. A hand-edited skill or agent file can now ask for a security-lens round (below), `accord lint` accepts a prose heading in the security file, and a team pattern with two overlapping repeats is run on a package only up to a fixed budget, after which the scan reports the rest as not fully scanned (below); no gate reads anything else that changed. A ticket with the review stage off that was claimed before 0.16.0 is not asked for a security review (below). A deferred item marked ` → <id>` to an id that is no ticket is listed again by `accord deferred` and the audit (below). A repository pinned to an older accord gets these changes with `accord upgrade`.

- `accord skills sync` no longer adds a second hook set when an accord hook was edited into a quoted program path that holds a space, such as `node "C:\Users\A B\cli.js" hook session-start`: the edited hook is kept and sync adds none beside it.
- A hand-edited skill or agent file under `.claude/` or `.agents/` is now scanned for security triggers like any other changed file, so such an edit can ask for a security-lens round. The files `accord skills sync` writes unchanged, and paths listed under `generated:`, stay quiet, and Markdown outside those folders is still not scanned.
- A prose heading such as `## Notes` in `accord/product/security.md` no longer fails `lint.security-file`, which stays an error. A misspelt reader heading such as `## Pattern` still fails it, and so does an unread heading whose section holds a list line shaped like a pattern or a removal, since that line would do nothing.
- The security scan and the slop scan now stop running a team line pattern that has two overlapping repeats, such as `.*a.*b` or `a*a*b`, once it has read about 12 million squared characters of changed lines in one package (about thirteen lines of 1000 characters). The scan then reports the pattern once at the first line it left unread, as `(cannot tell: ...)` in the security triggers and as a `slop:unscanned` line under `## Slop`, so a huge diff of long lines can no longer hang `accord gate done` or `accord review-package` for minutes and the rest is never skipped silently. A reviewer fixes or justifies that line like a line over 1000 characters. The default patterns of `accord/product/security.md` and `slop.md` are not budgeted, and neither is a team pattern without two overlapping repeats.
- `accord/product/security.md` and `slop.md` now accept a nested fixed count such as `(?:a{5}){5}`, which has one way to match a text. The refusal text for a pattern with too many routes now quotes `[ab]?[ab]?[ab]?[ab]?[ab]?[ab]?[ab]?` and `(a|a)(a|a)(a|a)(a|a)(a|a)(a|a)`, which the guard really refuses, instead of a five-part form it accepts.
- `accord debug path` and the session hook's `Unfinished:` line now judge the outside-ticket debug folder (the `accord-debug-<hash>` folder in the system temp directory) with one shared check. On Windows the check reads the folder's owner and access list (one Windows PowerShell run by its System32 path, as SDDL, so no language dependence) and refuses a folder owned by an account other than you, SYSTEM or Administrators, or one that grants any account other than SYSTEM, Administrators and you, naming that account and the `TEMP` variable that moves the folder; the folder `accord debug path` creates is given that private list at once, so a shared `TEMP` does not make accord refuse its own folder. On Linux and macOS a folder another account owns, or one open to group or others, is refused and the refusal names `TMPDIR`. The folder name is unchanged and still predictable; what changed is that a folder another account can use is never read or written.
- The session hook reads the state file only through that check, and only up to 1 MiB; a refused folder, a link or a larger file gives no `Unfinished:` line, and `accord debug path` refuses a file over 1 MiB, naming its size. A filesystem that stores no POSIX modes (WSL on `/mnt/c`: a folder reading exactly 0777 that accord made in this run, or whose state file is yours and reads 0777 or 0666) is accepted for the folder's owner, where it was refused before. A folder open to others whose state file another account made is refused.
- The session hook stops printing `Unfinished:` for an episode whose state file was last written more than seven days ago. `accord debug path` still reports it open and `/accord-debug` resumes it. Tickets in flight are unaffected: no gate reads the debug folder.
- Ticket text in the epic block and in the related tickets' blocks is now line-checked before a scout, planner, critic, judge or reviewer reads it: an epic's Vetoes and Decisions, the Epic lessons of its other stories and the Vetoes and Decisions of a related ticket pass the same checks as product text (a hidden or bidi character, a line accord itself writes such as `Work dir:`, a forged heading), at 4000 characters a line, and an epic or ticket title has its control characters replaced by spaces. A refused line is replaced by `(accord withheld line <n> of <file>: it breaks a delivery rule; fix that line of the file)`, which names the ticket file and the line and never quotes it; an unclosed `<!--` withholds its own line and hides no later line. A team that sees that line in a brief should fix that line of the ticket file. Tickets in flight: no gate or lint rule refuses for it, so a withheld line is found only in a brief.
- With `strictness.stages.<lane>.review: off` a lane M, L or P ticket no longer loses its security review. `accord gate done` now asks for it when the ticket's changes (the whole diff from the plan's baseline to HEAD) match a security pattern: the ledger records it as `Security: lens security ran at <sha>` under `## Security` in `accord/tickets/<id>/ledger.md`, and `gate.security-unreviewed` is reported against the ledger until it does, or when code that matches a pattern changed after that commit, or when the commit is unknown or not an ancestor of HEAD. `gate.security-unreviewed` is now on the floor, so a `strictness.levels` key for it is refused by `accord lint` and `accord config`. A ticket with no security trigger needs no line. A ticket claimed before 0.16.0 is not asked, and a team with the review stage on sees no change.
- The stages-off line that `accord status`, `accord dashboard`, `accord show` and `accord anchor` print now ends `; the security review stays on` when review is one of the lane's stages that are off, such as `stages off for lane M: review; the security review stays on`. A lane with only other stages off prints the line as before, and no `--json` output changes.
- The build stage's next step (`build.md` step 8 and `build-no-plan.md` step 6) now sends a session with review off to a new section `With the review stage off` of `review-security.md` before verify: it runs `accord review-package <id> --security`, dispatches the security lens when a pattern matched, fixes each Must and Should finding through `accord brief <id> --fix`, then writes `Security: lens security ran at <sha>` under `## Security` in the ticket's ledger and commits. This is a skill change that `accord upgrade` ships; a ticket claimed before 0.16.0 is not asked for the line.
- `accord` now finds git when the session hook runs from Git Bash on Windows. A `cwd` the hook receives as `/c/Work/x` is turned into `C:/Work/x` before git starts, and a PATH written as `:`-separated `/c/...` entries is retried once in Windows form; entries already on PATH are only re-spelled, never added. Nothing changes on other platforms or for a folder and PATH Node already reads.
- When git cannot be started, the message now says which of two causes it is: `cannot use the folder <cwd>: it does not exist here` (on Windows with the `C:/...` form offered for a `/c/...` path) when the folder does not exist, else `git is required but was not found on PATH (<n> entries searched)`. Both messages come from one function, so `repoRoot` and the file listing cannot drift apart. Any other git failure keeps `not a git repository (or git failed)`.
- The session-resume hook's stage-file line now names the file's real path, `stage file: <repository root>/.claude/skills/accord/<file>, next to the /accord skill's SKILL.md; read it and go on at the step the anchor names`, in place of `./<file> of the /accord skill`, so a session cleared with `/clear` opens it at once instead of searching `~/.claude`. The file name still comes from the fixed stage map, never from repository text.
- `accord skills sync` now removes an empty folder of a retired accord skill (such as `.claude/skills/accord-queue`) left by an earlier sync whose removal failed, for example while an editor held the folder on Windows, on the next run and lists it `removed`. A retired folder that holds any file stays and is still listed as an orphan.
- The refusals and hints that keep the reader in the same session now say in words what to ask, with the id kept: `accord worktree open` ends the pin-mismatch refusal, the `claimed:` refusal and the rebase, merge and clash hand-fix hints with `ask to continue <id>` instead of a typed `/accord continue <id>`, and the similar-ticket option, the approach skill's closing line and the intent skill's lane S move say it the same way. The line that opens a new session (`stop: open a session in this folder and type the line below it` with `/accord continue <id>`), the session-check messages, the dashboard and the panel buttons keep their typed forms.
- The panel's New request button now sends the search text behind the lead-in `new request: `, and `/accord` routes that text by its meaning and says the route out loud, so search text that starts with a command word, such as `queue fix login` or `continue ST-1`, no longer runs that typed form.
- `accord pr` now refuses a ticket title that holds a percent sign (`%`), with exit 2 and the character named: cmd.exe expands `%NAME%` inside the double-quoted `--title` the skills pass to `gh`, so the title would reach GitHub changed. The characters `'`, `!`, `;` and `&` still pass, because they are literal inside double quotes in cmd.exe, PowerShell and non-interactive bash, and many ticket titles hold an apostrophe. A title with a double quote, backtick, `$`, backslash, line break or control character is refused as before.
- `accord pr <id>` now exits 2 for a ticket whose frontmatter does not parse, naming the ticket file and `accord lint`, and writes no body file; it used to open a pull request titled with the id and with no Intent.
- The `remaining:` lines of `accord pr` now name each unfilled template section by the heading a reader sees, without closing `#` marks or an inline `<!-- ... -->` comment, and a heading that sits inside an HTML comment of the template is no section and is never listed. An agent that matched the old raw heading text must match the visible heading.
- A name written as `@name` in a ticket's title, Intent, criteria or evidence lines now reaches the pull request body inside a code span, so the body notifies nobody; `@ac-n` and `@test:` tags keep their code spans.
- A commit subject is now exempt from the team's commit rule as a revert only when it is exactly `Revert "<text>"`, git's own shape; `Revert "wip` and `Revert "x" and more` are judged like any other subject. The `accord commit check` description now says only the revert exemption applies there, and merge commits are exempt at the gates only.
- A slop justification line `slop:<kind> <path>:<line> — <reason>` now clears its hit only when its reason holds a letter or digit, and the refusal says the path and line are those of the ticket's final diff. Tickets in flight: a justification written without a word, such as `— .`, is now refused at `accord gate done` and needs a real reason.
- The skills that open or comment on a pull request now write the body file as a double-quoted path, `--body-file "<body-file>"`, in `/accord` (lane S, lane R, the CI step of verify and a new epic) and in `/accord-review-pr`, so a path with a space reaches `gh` whole instead of being split by the shell. A skill file you copied before this release keeps the unquoted form until `accord skills sync` rewrites it.

A ticket without the field keeps the claim-commit reader of 0.4.1, and a `ruleset` that is not a plain x.y.z is ignored.
- `gate.ruleset-changed` and `gate.ruleset-missing` (from 0.5.0): the field is never edited by hand. While the ticket's claim commit is reachable, `accord gate ready`, `gate plan` and `gate done` (lanes M, S and R) compare the field with the first `ruleset` the branch wrote, which is the one in the claim commit or, for a ticket claimed before 0.5.0, the one in the backfill commit below, and a different value is an error that names both. A ticket claimed before 0.5.0 that no commit ever gave a `ruleset` is compared with the pin at its claim commit, as before. `gate.ruleset-missing` fires only when the ticket held a `ruleset` at the reachable claim commit and has none now. A rebase moves the config pin at a rewritten claim commit but replays the ticket's own line, so a rebased ticket passes. After a squash merge no claim commit is reachable and both rules are silent: the ticket is done by then.
- Backfill (from 0.5.0): a ticket in flight at the upgrade has no `ruleset`. `accord upgrade` writes `ruleset: "<pin at its claim commit>"` into every ticket on the default branch that has a lane, is not dropped, is approved there (an `approved_hash` or an `ac_hash`) and has no `ruleset`, is not done there, and has a `claim: <id>` commit on a claim branch (the `branch` template, local or on origin); the value is the `accord:` pin of `accord/config.yml` as committed at that claim commit, and it goes into the one `upgrade/<version>` commit, which the upgrade's own lint pass checks. Done, unclaimed, already written and unapproved tickets are left as they are: a draft's copy on the default branch has no rules to pin yet, its file on the claim branch gets the field at its first sync, and a field written into the draft would conflict with the branch's approve and fail the pull request's gate. A ticket whose claim pin cannot be read, because the blob is missing or the pin is not a plain x.y.z, gets no field and one `warning: <id>: ruleset not written, ...` line on stderr, and the exit code does not change. A ticket whose file is only on its branch gets the field at its first sync instead: `accord worktree sync <id>` and Continue write `ruleset: "<claim pin>"` in one commit named `ruleset: <id> from its claim commit` and print `backfilled: <id> ruleset <pin>`, once the branch carries (or is about to take in) a pin of 0.5.0 or later. Under `git.merge: rebase` or `git.sync` the commit is made before the sync, while the claim commit is still reachable, and a refused sync takes it off again. A branch pinned below 0.5.0 is not given the field (its published schema refuses it), and a ticket that lost a `ruleset` an earlier commit wrote is not backfilled: `gate.ruleset-missing` reports it.
- `git.merge` and `git.sync` (from 0.5.0, new keys of `accord/config.yml`): `git.merge` is `merge`, `rebase` or `squash` and says how the team merges pull requests into the default branch. With no key a repository means `merge`, and everything works as in 0.4.1. Under `merge` and `squash` a ticket branch takes the default branch by an ordinary merge commit, as before (accord never syncs with `git merge --squash`); under `rebase` it rebases. `git.sync` is a shell command that runs instead of the built-in merge or rebase, with the ticket, branch, base ref and root in `ACCORD_*` variables and never in the command text; a script that fails, runs past 600 s, leaves a merge or a rebase unfinished or leaves tracked files uncommitted is refused with exit 2 naming the command, and the branch is not pushed. A config with a `git:` key needs 0.5.0 or later; an older accord refuses it.
- `accord worktree sync <id>` (from 0.5.0): the primary name of `accord worktree merge`, which stays as an alias, so the installed skills and pinned repositories keep working. It takes the default branch into the ticket branch by the way `git.merge` or `git.sync` sets. A rebase prints one `rebased: <old12> -> <new12>` line per commit and pushes with `--force-with-lease --force-if-includes`; a refused push prints the command to run by hand and exits 0. A conflict aborts the rebase and leaves the branch as it was. The `accord-verify` skill and `accord/worktree.md` now call it and say the way is set by `git.merge`.
- `accord gate done` after a rewrite (from 0.5.0): when the commit a tick or the review was recorded against is no longer in the gated commit's history (a rebase or a team script rewrote it), `gate done` compares the contents of the ticket's files instead of the sha. Unchanged contents keep the verification; changed contents refuse it and name the files; a recorded commit that is not in the clone refuses it and says to verify again. The comparison applies only after such a rewrite: a commit made after verify, a merge of the default branch included, is judged as in 0.4.1 and still asks for verification again. `accord status`, `accord anchor` and the dashboard say what `gate done` says.
- Re-bind at accord's own rebase (from 0.5.0): when `accord worktree sync` itself rebases (`git.merge: rebase`, no `git.sync`) and no ticket file changed, it moves `verified_commit` and the `commit:` of `verification.md` to the rebased commit in one records-only commit (`verify: <id> rebound after rebase`) and prints `rebound:`, so the pull request's `gate done` passes in CI after the force-push. A changed ticket file, a rebase by hand and a `git.sync` rebase are not re-bound: CI's `gate done` finds the old commit missing and verifies again, and accord prints `verify again:` with the reason.
- Cleanup after a squash or rebase merge (from 0.5.0): `accord worktree clean` deletes a ticket branch that was squash- or rebase-merged even when the default branch edited the same lines afterwards, when every blob the branch wrote is found in the default branch's history. A deletion, a rename, a mode change, a link, more than 200 paths, a blob the default branch never held, or any git failure keeps the branch.
- Repositories pinned to 0.4.1: nothing changes until `accord upgrade`, which moves the pin, regenerates the skills and backfills `ruleset`. Tickets claimed under 0.4.1 keep the 0.4.1 rules, now also through a squash or a rebase merge once they carry the field.

## 0.4.1 — 2026-11-14

Each rule below that reads a pin has a cut-off constant in `packages/core/src/round/pin.ts` (`DISCUSS_FROM`, `APPROACH_CAP_FROM`, `PLAN_FORMAT_FROM`, `PLAN_CAP_FROM`, `PLAN_GROUNDS_FROM`, `GROUNDS_V2_FROM` and `PLAN_SIZE_FROM`), which holds the first release that ships the rule. The seven read `0.4.1`.

- Discuss stage (from `DISCUSS_FROM`, 0.4.1): a ticket of lane M, L or P (every lane but S) claimed under that pin or later needs `accord/tickets/<id>/discuss.md`, with every gray area mapped to a Decision, before `accord gate ready` passes. The areas are the list items at the top level of a line (indented by up to three spaces and less than the text of the area before it: a sub-bullet indented as far as that text, two spaces under `- ` or three under `1. `, and any item indented four spaces or by a tab, is a note under the area; a paragraph after a blank line ends the list, so an item after it is top-level again) under the `## Gray areas` heading and under any heading that starts with `Gray areas`, such as `## Gray areas (cont.)`. A repeated or continued heading, and a line with a group and a Decision but no gray area text, fail the gate. A ticket claimed under an older pin, in flight when the repository upgrades, needs none.
- Approach critic (from `APPROACH_CAP_FROM`, 0.4.1): for a ticket of lane M, L or P the critic runs at most two rounds, and no Ruling raises the cap. A third round is refused with the findings still open. An open `risk: data-loss` or `risk: security` finding blocks the approval, in every round of such a ticket and when round 2 reports no findings or a verdict ends the loop: `accord show <id> --approval --short` lists it under `## Blocking findings`, and `accord approve` refuses with exit 1 and names it. This is a change in public behaviour: `accord approve` read no approach record before 0.4.1. The approach record is read strictly and fails closed. The one separator is ` — `; a hyphen, two hyphens or an en dash is part of the text of a state, a reason, a test or a command, so `command: npm test -- <path>` is never cut. A risk is read only from the finding's mark slot: a ` — `-separated segment after the finding's text that is `risk: security` or `risk: data-loss`, or `rests on: risk: security` or `rests on: risk: data-loss` (the critic's own wording), in any letter case, after the state or before it, whether the severity is followed by ` — `, a colon, a hyphen or an en dash (`1. Must: <text> — risk: security — open` is read like `1. Must — <text> — risk: security — open`); or the `rests on:` line of the critic's block, the lines under a finding that are indented deeper than it, as `agents/critic.md` prints it. The block's other `rests on:` lines (`ac-<n>`, `D-<nn>`, a quote, `test:`, `command:`) are read as grounds, so a round 2 block with `rests on: ac-1` is not refused for grounds; a block may carry several of them, and a ground on the finding line may stand beside one in the block, and every one is read: a second ground, or a second `test:` or `command:`, is never a record problem. Any other line under a finding, indented or not, is a note, and a note is prose: `   - Risk: a stale cache shows old rows` refuses nothing. Prose is never searched for a risk word: the finding's own words, a note under a `## Round` heading, the reason of a `withdrawn:` or `unverified:` state, the owner's words, a `No findings` line and a test name such as `risk:data-loss` are read as nothing, so they never refuse. A finding that names a risk only in prose, or in a line with no ` — `, is not a blocking finding; while it is an open Must or Should the short view lists it under `## Risks`, and an open Nice is never listed. A mark slot is a segment after the finding's text, or a `rests on` line of the block, whose key is `risk`, `risks` or `rests on` and whose value is a security or data-loss kind written some way, and a mark slot whose value does not parse is a record problem: `risks: security`, `risk: data_loss`, `risk; security`, `risk, security`, a mark in backticks, quotes or asterisks, `risk: security.`, a hyphen that is not the ASCII one as in `data‑loss`, a kind one edit off the whole word, counted over its letters, the `data` part of `data-loss` included, and whatever up to three characters that are no letter separate the letters or come before them (`risk: secrity`, `risk: date-loss`, `risk: data-lost`, `risk: data/loss`, `risk: secu-rity`, `risk: .security`; a value two or more letters off is prose) and `rests on risk: security` (no colon) are problems. A value that is no such kind is prose, not a problem: `risk: none`, `risk: low`, `risk: a partial file is left on a crash` and `rests on: ac1` refuse nothing. A line directly under a finding, with no blank line between, that is no deeper than the finding and is a mark slot (`rests on: risk: security` or `risk: security` at the start of the next line) is a record problem too, because Markdown renders it as part of the finding: indent it under the finding, or leave a blank line before it, so that it is a note. Every cycle of the record is held to this, and any other line of `approach-review.md` that accord cannot read is a record problem as well: `accord round --approach` refuses it, `accord approve` refuses with exit 1 naming the problems, and the short view lists them under `## Blocking findings`. The plan record of a lane M, L or P ticket claimed under 0.4.1 or later follows the grounds rule from its first round, whatever pin its rounds were written under (see the plan checker's grounds below), so the same record problem refuses `accord round --plan` and `accord gate plan` (rule `gate.plan-rounds`) from round 1. For a ticket claimed under an older pin, a plan record follows the grounds rule only when its first round is written under 0.4.1 or later, and then the problem refuses `accord round --plan` and, once a cycle holds three rounds, `accord gate plan`, as before; a plan record of such a ticket begun earlier is read as before. `accord gate done` reads no plan record. A ticket claimed under an older pin and a lane S ticket are asked none of this: `accord approve` still reads no record for them. A risk finding is open, whatever its severity, while its state is `open`, `unverified` or `deferred` (a risk finding is never deferred), while it is `repeated as` a finding that is not in a later round of the cycle, and while an `owner:` state has no words. A finding repeated as another, or repeated by a `repeats <round>.<n>:` line, passes its risk on, so a repeat line without a `risk:` mark blocks too. A risk finding stops blocking when it is `fixed`, `withdrawn`, repeated as a finding that exists, or dropped by the owner as `owner: "<words>"` (the short view then lists it under `## Risks` with the owner's words), and when any `## Closed` line (the owner's no with a Correction, `ruled out by`, `the owner picked`) starts a new cycle. A ticket claimed under an older pin keeps five rounds and its stop, even when its approach critique begins after the upgrade, so no round is lost; `accord approve` does not refuse it, and the short view lists its open risk findings under `## Risks`.
- Approval (from 0.4.1, a skill change shipped by `accord upgrade`): `accord-intent` asks no separate yes. The owner approves once, from `accord show <id> --approval --short`, which prints the Intent, one line per criterion, the Decisions, the risks and the ticket path. `accord show <id> --approval` prints the full sections as before.
- Plan format (from `PLAN_FORMAT_FROM`, 0.4.1): for a ticket of lane M, L or P, `accord gate plan` reads each task of `plan.md` as `accord brief` prints it (an HTML comment hides nothing) and refuses three things, one finding per line. A task with no `after:` line, or whose first `after:` line holds nothing, is refused (`gate.task-after-missing`); the line names the tasks the task follows (`after: 1, 2`) or says `after: none`, and the key is read in lowercase only, as `covers:`, `files:` and `verify:` are, so `After:` or `after :` is not read and the finding names the line it skipped. A token of an `after:` line that is not a task of the plan, `none` written beside a task number included, is refused (`gate.task-after-unknown`); a task that names itself or a cycle of tasks is not checked here. A task holds code only as an interfaces block of one form: a line of three backticks and `interfaces` at column 0 opens it, and the first following line of three backticks at column 0 closes it, either line may end in spaces or tabs and holds nothing else, and a task may hold several such blocks. Every other fence-like line of a task, one that after any leading spaces, tabs, `>` or list markers starts with three or more backticks or tildes, is refused at its own line (`gate.task-code-block`): an indented fence, a fence on a list marker or in a quote, `~~~`, a longer run, a fence with a language such as `ts`, a code span at the start of a line, a fence inside an interfaces block, and an interfaces block no line closes, named at its opening line. A task of more than 120 non-blank lines is refused (`gate.task-too-long`); comment lines and interfaces blocks count. At the commit before this release the cap refuses 12 of 322 tasks in 11 of 49 plans of this repository (`docs/benchmark/metrics-st-ln-91-plan-format.md`). A lane S ticket is asked none of this. A ticket claimed under an older pin, in flight at the upgrade, passes as before even when its plan is written after the upgrade.
- Plan cap (from `PLAN_CAP_FROM`, 0.4.1): the plan critique runs at most three rounds per cycle, and stops the loop for the owner after a round from round 2 on whose count of Must and Should findings is above 0 and did not fall below the round before (a Nice and a finding deferred with its ledger line are not counted), as well as after a round from round 3 that still reports a Should or a Must. `accord round <id> --plan` prints `Round: <n> of 3`, gives the count in its stop reason, and refuses a fourth round; `accord gate plan` refuses a round past the cap or after the stop that no owner Ruling allows (`gate.plan-rounds`), and a stopped loop needs `verdict: accepted-by-owner "<the owner's sentence>"` after the stopping round, or a round the owner allows that reports no findings. An owner Ruling that allows a round still raises the cap. A ticket claimed under an older pin keeps five rounds and the stop from round 3, even when its plan critique begins after the upgrade.
- Plan checker (from `PLAN_CAP_FROM`, 0.4.1, a skill change shipped by `accord upgrade`): round 1 of each plan critique cycle dispatches one plan checker, the critic in plan mode with no lens running every plan check, plus one security critic when the ticket touches auth, money, migration or data deletion, or the plan touches a path under `sensitive:` in `accord/config.yml`. `accord round <id> --plan` prints `Critics: plan checker` at round 1 to say so, and `accord-plan` dispatches by that line. A ticket claimed under an older pin gets no such line and keeps the 0.4.0 round-1 split, one critic for a plan of one to three tasks and two critics for a plan of four or more tasks, in every cycle, with its five-round cap, now written in `accord-plan/legacy-round1.md` alone. There is one deliberate change for it: its security critic also runs when the plan touches a path under `sensitive:`, where 0.4.0 asked only about auth, money, migration and data deletion, so no security check is cut; nothing else changes in its plan critique.
- Plan checker's grounds (from `PLAN_GROUNDS_FROM`, 0.4.1): for a ticket of lane M, L or P, a Must or Should of plan critique round 1 that cites no ticket line (`rests on:` an `ac-<n>`, a `D-<nn>` or a quote), no `test:`, no `command:` and no `risk: data-loss` or `risk: security` stops `accord round <id> --plan`, which names it, until it is grounded or written `deferred` with its line and failing case under `## Deferred` in the ledger. A ticket claimed under an older pin keeps the Phase 2 rule: grounds from round 2, when the record's first round is written under 0.4.1 or later. The approach record keeps grounds from round 2 for every ticket.
- Repositories pinned to 0.4.0: a repository pinned to 0.4.0 keeps the 0.4.0 answers and skills until `accord upgrade`, which moves the pin and regenerates the skills. The discuss rule, the approach cap and the four plan rules above (format, cap, checker and round-1 grounds) read the pin at the ticket's claim commit: the newest `claim: <id>` commit that is not on the default branch, else the newest one overall. A ticket with no `claim: <id>` commit has no claim commit to read, so it gets the new rules after the upgrade, wherever its ticket file was added. It reads the working-tree pin only when the ticket has no such commit or git has no HEAD. When git fails reading the pin, or `accord/config.yml` cannot be read at the claim commit (a blob a blobless clone never fetched), the new rules apply. Then `accord gate ready` names the git error in its discuss finding, `accord round --approach` names it in the refusals the cap rules give (past the cap, an ended loop, a blocked approval), `accord approve` names it when it refuses on a blocking finding, and `accord show <id> --approval --short` names it in its `## Blocking findings` part; the cap itself (the round number and the cap it prints) applies the new rules without naming it. For the plan rules, every finding of `accord gate plan` under the format rules and `gate.plan-rounds`, and every answer of `accord round --plan` (the next round, as a `Note:` line, a stop and a refusal), adds the git error and `the claim pin could not be read, so the new plan rules apply`. Six rules follow the claim: the discuss rule, the approach cap with its approval block, the plan format, the plan cap with its count stop, the plan checker at round 1 and the plan's round-1 grounds, so a ticket claimed before the upgrade keeps no discuss stage, five approach rounds, the old plan format, five plan rounds and the 0.4.0 round-1 dispatch (with the security critic widened to `sensitive:` paths, the one deliberate change) until it is done. Two rules follow the record or the plan instead, and the upgrade changes them for such a ticket once a record or a plan begins after it: the grounds rule (round 2 and Must, `GROUNDS_V2_FROM`, and the plan fix scope) reads the pin at the first round of the record (`review.md`, `plan-review.md` or `approach-review.md`), except that the plan record of a ticket claimed under 0.4.1 or later is asked from round 1 by its claim pin, and the plan size rule (`PLAN_SIZE_FROM`) reads the pin at the plan's baseline commit. The version 2 review record, in force since 0.3.1, is not changed by this release. A ticket claimed under 0.4.0 whose approach critique begins after the upgrade therefore keeps five rounds and its stop but is held to the round 2 grounds rule; one whose record began before the upgrade keeps the old grounds rule.
- Lane R, research (new, no cut-off constant: it applies only to a ticket written as lane R): a ticket that asks a question accord cannot answer from the code, and asks for no change, is worked in lane R. `accord new ticket <id> --lane R` writes its template with `## Question`, `## Timebox` (`<n> minutes` or `<n> hours`) and `## Token budget` (`<n>`, `<n>k` or `<n>M` `weighted tokens`). The owner sets the timebox and the token budget; the session proposes neither. `accord gate ready` passes when the three sections are written and `## Decisions` quotes the owner on both values (D-13); `ac_hash` is taken over the three sections. Lane R has no approach, plan, critic, code review or verification: `accord gate plan` refuses an R ticket as having no plan (`gate.lane-r-plan`), and `accord round`, `accord approve`, `accord review-package`, `accord brief` and `accord task-done` refuse it with exit 2. An epic is never lane R.
- `accord budget <id>` (new): prints `within budget` (exit 0) or `stop: ask owner` (exit 1) for a lane R ticket, the elapsed time from the author time of the ticket's `claim: <id>` commit (a rebase or `git pull --rebase` keeps the author time, so it does not restart the clock), the weighted tokens of the checkout's own Claude Code transcripts since that claim (fresh input 1, cache write 1.25, cache read 0.1, output 5, each message once), and the `Spent:` line the research record copies. It stops only strictly past the timebox or the budget, and then prints the question for the owner and how the answer is written. Tokens read `not measured` when no full count since the claim exists: the checkout has no transcript folder, or its earliest transcript line is later than the claim (Claude Code deletes transcripts after 30 days by default); then the time alone decides (D-20). A ticket of another lane, an allowance that cannot be read, or a ticket with no claim commit is a usage error (exit 2).
- Lane R Done: the session writes a record under `accord/research/` with its header and a `Spent:` line, and lists it under `research:` in the ticket. `accord gate done` passes an R ticket when `ac_hash` still matches the three sections, `## Decisions` still quotes the owner's values, a listed record that the branch added or changed after the ticket's claim commit holds a `Spent:` line, and the branch changes nothing outside `accord/`: every other path it changes, a deletion included, is refused and named (`gate.research-shipped`), so a research script lives under `accord/research/`. Where no claim commit is reachable, as on the default branch after a squash merge, a listed record counts when the commit that added the ticket file, or a later one, changed it. A listed record that already existed is evidence: allowed, but never the ticket's result, and its `Spent:` line is not read; when git cannot say which records changed, or the ticket has neither commit, no record counts. The timebox is compared with the larger of the record's `Spent:` time and the time git measures from the claim commit to the record's last change, both author times, which a rebase keeps (the clock `accord budget` reads), so a `Spent:` line written lower decides nothing; with no claim commit reachable the `Spent:` time alone decides, since the pull request's own gate done judged the branch; the tokens cannot be measured from git and are read as written. A record past the ticket's timebox or token budget is refused unless it holds the owner's `Owner: write now — "…"` or `Owner: extended to … — "…"` line; an extension is the new value written into the ticket with its quoted Decision and a fresh `accord gate ready` (D-14). It asks for no plan, review, verification, suite or ticks.
- Lane R in CI and the views: the CI workflow `accord init` and `accord upgrade` write reads `ac_hash` on a lane R ticket as on lane S (`[SR]`), so a ready R ticket's accord-only pull request runs `accord gate done`, and an R ticket holding `ac_hash` cannot be deleted before it is dropped. A ticket approved as lane M, L or P that moves to lane R is refused as a lane drop, as a move to S is. `accord status`, `accord dashboard`, `accord anchor` and the session line show R tickets with their stage: `intent` until `gate ready`, `research` until a listed record the branch changed since the claim holds a `Spent:` line, then `done` (on the default branch once merged, by a merge commit, a squash or a rebase; the main checkout reads a claimed R ticket's research from its branch); the session line counts `research` as in progress. `accord status --json` may now carry the stage `research`, and `accord show --json` a `question` field (the question, with `intent` left empty) for an R ticket; `accord show` prints `Question:`. The `/accord` skill (a skill change shipped by `accord upgrade`) proposes lane R, without the scout, for a request that only asks a question, and follows the new `lane-r.md` from the owner's timebox and budget to the pull request.
- Lane R and the schema: `R` is a new value of the published ticket schema's `lane`, a one-way addition (D-10): a ticket that uses it needs this release or later, and an older accord refuses it. Tickets in flight and repositories pinned to an older accord change nothing until they write an R ticket.
- Lane R known limits: `accord gate done` judges the branch it runs on, so a later pull request that changes files outside `accord/` and also edits a done R ticket's file is refused for that ticket; edit a done R ticket in a pull request that changes only `accord/`; the timebox is calendar time since the claim commit, so nights and weekends count, and the owner's answer line (`Owner: write now` or `Owner: extended to`) covers a ticket that ran past it; once past `gate ready`, no accord command brings the default branch into a lane R branch that is behind it (`accord worktree merge` runs only at verify and refuses R), so such a pull request is merged as GitHub allows; tokens read `not measured` when the ticket's session ran in another checkout, such as the main one, because only the checkout's own transcripts are read; where no claim commit is reachable, a record added in the same commit as the ticket file counts as the ticket's own, so an R ticket is queued in a commit apart from the records it lists as evidence.
