**As a** team whose repository is pinned to one accord release,
**I want to** have a different release refuse before it touches anything,
**so that** the release my repository actually wants can still repair and complete it.

<objective>
Gap 1 (CLI-01, status `partial`): `accord init` performs its scaffold writes before it reads the
config and checks the pin, so a repository pinned to another release receives three files from the
running one and is told about none of them — the throw skips the report at `init.ts:99`. Because
`init` never overwrites an existing file, the release that repository actually wants cannot then
repair what the wrong one left, and `.github/workflows/accord.yml` is left pinned to a version
`config.yml` does not name.

The owner ruled **both halves**, and this plan is the tracer for the gap-closure run: it is the one
gap with a reproducible end-to-end failure and a runnable proof.

1. Move the config read and the pin check ahead of the scaffold write loop, so a repository that has
   refused this release receives no byte from it.
2. Print the accumulated `results` before rethrowing, so that if any write path ever again precedes a
   refusal, the partial run is auditable rather than silent.

Purpose: the pin guard is the mechanism D-94/D-95 rely on to stop one release's rules reaching another
release's tickets. On the one command that creates the pin, it currently fires after the damage.
Output: one reordered command, one report-on-throw, and the two regression cases that hold both.
</objective>
