# Accord design

Living design document. Captures decisions from the initial brainstorm (2026-09-04) and the research behind them. It will be replaced by real specs once the CLI exists.

The workflow layer — lanes, owner approval, the plan gate, task records, review convergence, the traced-test policy, and re-anchoring after compaction — is specified in [specs/2026-10-12-workflow-layer-design.md](specs/2026-10-12-workflow-layer-design.md). Its contract applies to tickets that carry `lane:`; a ticket without it keeps every rule below.

## 1. Why this exists

Small delivery teams adopt AI coding agents and get two recurring failures: features that do not match the intent, and testing with no acceptance criteria to test against.

Existing agent harnesses are single-person tools. They interview the person at the keyboard, but the intent is often held by someone else, such as the client. The gap is not another agent harness; it is a shared artifact contract between the stages of a ticket.

Research on where agent failures come from changes the design more than anything else. A study of 20,574 real coding-agent sessions (arXiv 2605.29442) reports:

| Failure mode | Share |
|---|---|
| Instruction-following failure (agent had a clear directive, did not comply) | 36% |
| Cannot determine | 27% |
| Underspecified instruction | 15% |
| Premature action (acted before gathering context) | 11% |

Underspecification is real but is not the largest cause. So Accord spends as much on the Done gate (independent verification against acceptance criteria) as on the Ready gate (capturing intent), and it makes the gates deterministic through a CLI rather than leaving them to prompts an agent can ignore.

No existing tool combines folder-as-source-of-truth, multi-stage workflow, deterministic gates, MCP editing, and conflict approval in one place. Accord borrows established ideas where they fit: EARS for requirements, a proposal-then-archive lifecycle, a role roster, and branch-based editorial approval.

## 2. Folder convention

The root folder is always `accord/`. It is not configurable; a `.accord` pointer file may be added later as an additive change.

```
accord/
  config.yml                    # version pin, profile, tracker adapter, token path, roles, runtimes
  product/
    glossary.md                 # domain terms
    business-rules.md           # rules, thresholds, rounding, edge cases already decided
  tickets/<id>.md               # one file per epic, story, or bug
  tickets/<id>/verification.md  # review record, written by the fresh review context
  assets/<id>/prototype.html    # the ticket's design reference
```

Flat files, not nested folders. Epics, stories, and bugs share one file type (`type: epic | story | bug`); a story or bug names its epic with `parent:`. An epic holds intent and requirements for its children and is linted but never gated. This mirrors every tracker's model and keeps indexing trivial.

Every ticket has YAML frontmatter validated against `ticket.schema.json`: `id`, `title`, `type`, `status` (`draft | open | archived`, document lifecycle only; work status stays in the tracker), optional `parent`, `tracker` (map keyed by adapter), `ui`, `design`, `assumptions`, `ac_hash`, `priority` (`high | medium | low`, absent means medium), and `verified` (always the last key). Unknown keys are errors, so tracker-owned data cannot leak into git; `priority` is the one such key accord reads, because the dashboard ranks by it.

The body has fixed headings in fixed order: `## Intent`, `## Requirements`, `## Acceptance criteria`, `## Open questions` (written at intent), then `## Plan` and `## Verification notes` (filled in at build and done, last). Epics omit Acceptance criteria, Plan, and Verification notes.

`## Verification notes` holds one `### @ac-n` block per ticked scenario, each a line the person who verifies writes themselves naming the logic that makes the scenario correct. It lives in the body rather than in frontmatter because it is the one field guaranteed to be free-form prose, and prose in YAML breaks the parse on the first colon.

Formats:
- Requirements in EARS: `WHEN <trigger> the system SHALL <response>` and its four sibling patterns. Lintable by regex.
- Acceptance criteria in Gherkin. Verification reads it, the agent reads it, and it can be turned into test skeletons (Reqnroll for .NET, playwright-bdd for JS).
- Intent is prose, capped short: five lines covering why, for whom, success measure, and explicit non-goals.

Size discipline: intent about 5 lines, spec 5 to 15 EARS lines, 2 to 5 scenarios per story. If the spec is longer than the code, the spec is wrong.

No binary assets in the repo. Prototypes are HTML text. Screenshots are rendered on demand, never committed. Figma stays a link.

## 3. Profiles

`config.yml` declares `profile: build` or `profile: maintain`.

- **build**: a new project, typically 2 to 6 weeks. In week zero the intent stage writes `product/` and one epic ticket per epic (5 to 10). Acceptance criteria are written per story just before it enters the sprint, not all up front.
- **maintain**: a delivered project receiving individual tickets. Epic tickets are optional. At handover, epic intent and requirements are folded into `product/business-rules.md` and the epics are set to `status: archived`.

Profiles decide what the gates require. The rule lives in config, not in someone's judgement per ticket.

## 4. Stages and the roster

The roster is `roles:` in `config.yml`. Its values are config values, not people. `ba` and `dev` are required and switch nothing on: the stage skills replaced them, and the key keeps them so no config breaks. `designer` is optional and switches on the `accord-designer` skill, the design-reference step of a `ui: true` ticket. The roster only decides which skills are rendered; it never changes a gate result. What a ticket needs at each stage is the same whoever does the work:

- **Intent** sets the intent, the spec, and every acceptance scenario. Only the intent stage edits acceptance criteria. The readiness review happens inside the intent stage before Ready.
- **Design reference** is the design link or prototype of a `ui: true` ticket.
- **Build** implements from spec, AC, design, and plan only. Never adds a requirement. A gap goes to `## Open questions` and work stops until the intent stage answers.
- **Testing** (outside the repo) runs against the acceptance criteria on the dev environment after Done passes and records the result in the tracker; it suggests missing scenarios to the intent stage, never by editing. AC is the test plan; there is no separate test plan artifact.

Review is a stage, not a person of a given title. The build stage's last step opens a fresh agent context (a subagent in Claude Code, a new chat in Cursor or Codex) and hands it `review.md`; only that fresh context writes `tickets/<id>/verification.md`. The agent that wrote the code never does. This is procedural, not tool-enforced, so the skill states it plainly.

That context does two separable jobs and writes both into the same file. The `## @ac-n` blocks answer whether the change does what the acceptance criteria say. A `## Review` section answers whether what it does is sound — edge cases no scenario covers, business logic invented rather than specified, state and error handling, trust boundaries, reuse missed. Every review finding names a concrete failure: the input or state, and the wrong result that follows. A finding that cannot produce one was a preference and is dropped. The review context reports and never edits, since a context that fixes has rejoined the work it was brought in to judge.

Two techniques are loaded by the stages rather than invoked on their own: systematic debugging, loaded at build for a `type: bug` ticket or any unexpected behaviour, and code review, loaded by the review context. A bug needs no debugging session file because the ticket is the session.

Role workflows ship as skill files (Claude Code, Cursor, Copilot, Codex) so every member gets the same workflow from their own AI subscription. Each skill starts by running the CLI gate and stops on failure.

Solo use is the same contract with one person. The stages (intent, approach, plan, build, review, verify) are passed through in order by one person and their agent, not by separate people; the roster still decides which skills are rendered, and no gate result changes. Nothing in the gates reads who a person is, which is why the single-person case needs no separate mode.

## 5. Gates

**Ready** (a story may enter the sprint). Applies to every story that touches code, including small bug fixes.

| Check | Stage |
|---|---|
| `## Intent` is not empty: it says what the story is for, in business language | Intent |
| `## Requirements` carries at least one EARS line | Intent |
| At least one Gherkin scenario. A bug fix is written as Given the situation, When the action, Then the correct result | Intent |
| `ui: true` and profile maintain: `prototype.html` exists and was generated from the project's existing styles | Build or design reference |
| `ui: true` and profile build: a Figma link or a prototype exists | Design reference |
| Unchecked `## Open questions` items or unconfirmed `assumptions:` entries block Ready | Intent |

Prototype rule: if the repo has design tokens (CSS variables, Tailwind config, a design-system folder; the path is declared in config) the prototype may only use those tokens, and the linter flags hard-coded colours and spacing. If there are no tokens, the prototype must open with a comment listing the stylesheets it was derived from, so a reviewer can check.

Not every ticket has UI. `ui: false` skips the design checks in both profiles.

Lint also warns, and only warns, on vague wording in `## Requirements`, `## Acceptance criteria`, and answered `## Open questions`: "depends", "maybe", "probably", "mix of", "somewhere between", "not sure", "TBD". The words are a regex with false positives, so the finding never blocks Ready; the intent stage reads it and decides.

**Done** (a story may go on to testing on the dev environment). Three layers, each defeating a different lie.

*Machine.* Every scenario not tagged `@ui` carries a `@test:<id>` tag naming the test that proves it. Done fails unless that test is reported passed in the JUnit XML report named by `tests.report` in `config.yml`; the host puts that file into the snapshot and core reads it with a line scanner. A free-text `Evidence:` line never satisfies a non-`@ui` scenario on its own, because an agent can write one without running anything. A `@ui` scenario is exempt and leans on the human layer instead — brittle end-to-end tests get muted, and a muted gate is a decorative gate. A test reported skipped is not passed: muting a test is the cheapest way past a gate, so a skipped `@test:<id>` fails Done exactly as a failed one does. A host with no report available reports the check skipped, as the author check does.

*Fresh context.* The build stage's final step opens a fresh agent context that produces `tickets/<id>/verification.md`, one `## @ac-n` block per scenario with `Result:` and `Evidence:`. The agent that wrote the code never writes this file. `Result: blocked` fails Done as `fail` does; a scenario that could not be verified is not verified. The file's `commit:` must equal the commit being gated, so a review of an older commit fails Done until the review is re-run.

*Human.* The person who verifies runs the scenarios on the dev environment, ticks `verified: [ac-1, ...]`, and writes one line per scenario under `## Verification notes` naming the logic that makes it correct. The note must cite a file path or test id that exists in the snapshot (a symbol is never accepted: the gate holds no source text) and must not be the scenario text pasted back; there is no character-count floor, which would only invite padding. Each tick binds to the AC hash and the commit sha, so a tick never survives a change to either.

Done passes only when the scenario tag set, the evidence tag set, and `verified` are the same set, every required test passed, every tick carries a valid note, and the acceptance criteria hash still matches the one recorded at Ready. Testing on the dev environment follows, and its outcome is recorded in the tracker. This is the part that addresses the 36% failure mode.

What this cannot do: verify that the person understood the code. No gate can. It verifies that a human touched the ticket, at the right version, in their own words, per scenario. Claiming more would be theatre.

## 6. Tracker and git: hybrid by durability

The tracker (Shortcut, GitHub Issues, Jira, Linear) remains the source of truth for status, comments, and estimates. Git holds what outlives the ticket: product docs, feature specs, acceptance criteria.

Repo weight is not a storage problem. Five hundred ticket files and a hundred prototypes are a few megabytes; only images are heavy, and images are banned. The real cost is noise: doc PRs mixed with code PRs, notifications, history. Controls:

- Edits made through tooling land on a working branch, one PR per day or per release, squash merged, `docs:` prefix.
- CI path filter: a PR touching only the accord folder does not build; it may auto-merge on the owner's approval.
- When a ticket is done, its final AC is snapshotted into `tickets/<id>.md` in the release commit so decisions remain searchable months later.

Adapter `none` must be fully usable. The first external users will be single people and two-person teams on GitHub Issues.

## 7. CLI

The 0.1.0 commands. The workflow layer's commands are listed in section 9.

TypeScript, distributed via npx, so it fits how AI-tool users already install things. The package name will likely be scoped, since `accord` on npm is held by an abandoned 2022 package.

```
accord init                 # create the folder, config, templates, skill files
accord new ticket [id]      # scaffold tickets/<id>.md; id assigned as <ST|BUG|EP>-<initials>-<n> under people, else required
accord new feature <slug>   # scaffold features/<slug>.md
accord lint                 # frontmatter schema, EARS, Gherkin, prototype token rule
accord gate ready <id>      # PASS or FAIL with reasons; exit code for CI and skills
accord gate done <id>       # checks verification.md and ticked scenarios
accord status               # table of features and tickets with gate state
accord dashboard            # ranked sections for the viewer; --json for the data
accord commit check <file>  # judge a commit message file against commits.message (the conventional preset or a team pattern)
accord commit message <id>  # build the message with the team's trusted script (commits.message.command), then judge it
accord audit                # report what a machine sees about the conventions: fact, gap and gaps lines, exit 0, no model, no gate runs it
accord deferred <id>        # print the ledger's Must and Should deferred items that carry no owner's mark (" → <id>" or " → declined"), for the owner at verify
accord worktree clean       # remove worktrees and branches of done tickets; --dry-run prints the same lines and removes nothing; --after-merge <id> drops this session's hold on <id> first, from outside its worktree
accord conventions write <file>  # put the accepted convention lines on their own branch conventions/<date> for a pull request the owner merges
accord pr <id>              # write a ticket's pull request title and body file from the PR template, pr.command or today's body (`accord pr build <id>` is the same, the default of the `pr` group)
accord pr wait <id>         # follow the ticket's pull request with gh, reads only, no model: ends on merged, closed, feedback, ci-failed or the limit pr.wait_minutes; the last line is `pr-wait: <word> ...`
accord show <id>            # one lane ticket in full: row facts, Intent, each criterion and its state; --json for the data; --approval prints the approved sections for the owner's yes, criteria compacted
```

When `config.yml` holds `people` (email to initials), `new ticket` assigns the id and refuses a typed one; `legacy_ids` exempts existing tickets, and `lint.id-convention` and `lint.initials-duplicate` check the rest. When this checkout's `config.yml` does not list the creator's email, `new ticket` takes the initials from origin's default branch, else from the fetched branches when their entries agree, and still refuses initials that another email holds on any branch.

The `titles` key of `config.yml` holds the rule a ticket's title follows: `rule` (one line of guidance, default `English, in business language: what the reader gets, not how the code changes`), `max_length` (digits, default 80) and `language` (`english`, the default, refuses a letter outside A-Z and a-z, or `any`). `accord new ticket --title <t>` checks the title against it, writes nothing when it breaks the rule, and prints the rule line (`title rule: ...`) beside every title it is given, so the model reads the rule when it writes the title. The rule is also held at two gates, each only from the release that ships it (`TITLE_RULE_FROM`, never a date): `accord gate ready` refuses a title that breaks it with `gate.ticket-title` for a ticket whose claim pin is not before that release, and `accord lint` reports `lint.ticket-title` (pointer `/title`) for a ticket whose own `ruleset` is not before it. A ticket that exists when the rule ships has an older ruleset or none, so no existing ticket is judged. Both are errors a team may lower through `strictness.levels`; the checks are length, letters and the template's placeholder, never a model call.

The `branch` template of `config.yml` names the claim branch of a new ticket: one `{id}`, and optionally `{type}` and `{slug}` once each, as in `{type}/{id}-{slug}`. `{slug}` is the title in ASCII kebab-case (accent marks removed, any other non-ASCII letter dropped, one hyphen per run, no hyphen at either end), cut at `branch_slug_length` characters (a whole number from 1 to 99, default 40); a title with nothing left gives `ticket`. `{type}` is the ticket's optional `change:` word, one of `branch_types` (default `feat`, `fix`, `refactor`, `perf`, `docs`, `test`, `build`, `ci`, `chore`, `revert`, `hotfix`), and no type is ever guessed from `type:`: under a `{type}` template `accord new ticket --worktree` and `accord worktree open` refuse a claim whose ticket has no allowed word before any git write and print the words, and `--change <word>` gives it (written as `change:` on a new ticket, or in the claim commit of an older draft). `accord gate ready` also fails with `gate.change-type` naming the allowed words when the template uses `{type}` and `change:` is missing or not listed (an epic is exempt, and a team may lower the rule through `strictness.levels`), and `accord lint` warns with `lint.branch-type-root` for a `branch_types` word that is also the first segment of a branch accord makes itself (`t`, `backlog`, `drop`, `conventions`, `upgrade`, `accord-task`); no word is refused. A branch name is read back through the template written out once per listed word, so `{type}` matches only the listed words and a hand-made `drop/ST-9-x` or `wip/ST-9-x` is no claim; `{slug}` and the id share hyphens, so among the ids a name can carry a known ticket wins, then one of this repository's id shape (`ids.pattern`, a tracker key, or a `legacy_ids` entry), then the shortest that starts with a letter and ends in a digit run (every accord id pattern and tracker key starts with letters and ends in a number, so `fix/export-ST-9` reads `ST-9`, never `9`), with no git process added; a name with none of these is no claim, so a hand-made `chore/bump-deps` is never a ticket's branch, and `{id}` may start or end the name (`{id}-{slug}`, `{type}/{slug}-{id}`). When the id was such a guess among several candidates with none known, `accord audit` names the branch as a guess and prints no delete command for it, since a wrong guess would otherwise hand the owner a delete of a teammate's live claim; `accord status` and the hooks still read the guessed id. A hand-made branch such as `fix/issue-341-branch-tokens` under a `{type}` template therefore reads as a guessed claim of `issue-341`, which `accord worktree clean` no longer deletes on its own and the audit lists without a delete command. Before `git worktree add`, both claim commands check the rendered name with `git check-ref-format --branch` and read it back through the templates in force: a name git refuses (one ending in `.lock`) or one that reads back as another id (a `t` word, since a `t/` name is read only as `t/{id}`) is refused with nothing created. `--change` on a ticket already claimed is refused, since the claim keeps its name. A later change of the title, or of `change:` to another listed word, never loses the branch, but removing a word from `branch_types` while a ticket's branch carries it stops that branch being found, so a word is removed only between tickets. Such a branch also stops being a ticket's branch to `accord worktree clean`: a local `fix/` claim branch is then an ordinary `fix/` branch, which the clean deletes, with its worktree, once merging it into the default branch would change nothing, so the ticket loses its claim branch even though no commit is lost. Only when the default branch holds no `accord/config.yml` at all (a local-only install), or there is no default branch, does a new claim use the checkout's `branch`; a default-branch config without `branch` means `t/{id}`, so one person's unmerged `branch` never renames only their own claims, and a template on the default branch always wins. `branch_types` holds at most 30 words, since the claim listing puts two patterns per word on one git command line. A new worktree with no `accord/config.yml` runs the `setup` of the checkout that runs the command (`accord worktree open`, `accord new ticket --worktree`, a task worktree), which can be any linked worktree, including one on a teammate's branch whose `accord/config.yml` adds or changes `setup`; like a branch's committed `setup`, it runs without `accord trust`, so open a worktree from a checkout whose `setup` you would run yourself.

The `commits.message` key of `config.yml` holds the commit-message rule of a team: `preset: conventional` (Conventional Commits, the shape `type(scope)!: subject`, with an open set of types) or a `pattern` (a JavaScript regex source judged against the first line, with an `example` that passes it), and optionally a `command`, the team script that builds the message, which runs only after `accord trust`. One core function judges every message, for `accord commit check`, `accord commit message`, `accord task-done` and `accord gate done`; accord installs no git `commit-msg` hook. The rule covers the commits of a ticket branch that are not merge commits and are not on the default branch, and a subject that starts `Revert "` passes; the `upgrade: accord <version>` commit of a pin pull request, and the `drop` and `queue` subjects, are made on branches that are not ticket branches and are outside it. `accord lint` reports a bookkeeping subject (`commits.subjects`, the people-entry commit included) that would break the rule, with the fix. A ticket claimed before the release that added the rule is not refused.

The `pr` key of `config.yml` shapes the title and body of a ticket's or epic's pull request: `template` names one tracked pull request template, and `command` is a team script that replaces the template entirely and runs only after `accord trust`. `accord pr <id>` writes the body to a file under the git directory and prints `title:`, `body-file:`, the template or script it used and one `remaining:` line per template section nobody could fill; the lane S, lane R, verify-draft and epic skill steps then run `gh pr create --title "<title>" --body-file <path>`, and a test scans the skill sources so none of them keeps `--fill` or an inline `--body`. Template discovery reads only the paths git tracks, in the order of `gh`: `pr.template`, then a single `pull_request_template` in `.github/`, the root or `docs/`, then the first file of a `PULL_REQUEST_TEMPLATE/` folder. The fill never rewrites a heading line; a section whose body is empty and whose heading names the Intent, the acceptance criteria or the test evidence takes that text directly under the heading, and a slot no heading matches goes in an opening block that always begins `**<id>: <title>**`. The queue, upgrade and drop pull requests keep their short fixed body, because a team template asks for sections that do not apply to them. `accord pr <id>` never reads the live pull request back; only `accord pr wait <id>` does (the follow-through paragraph, below). Two more keys belong to that follow-through: `pr.wait_minutes` (a whole number from 1 to 120, default 120: how long a session waits on its pull request) and `review.post` (`draft`, the default and the only level built: what the resolve step would post waits for the owner's yes).

`/accord-audit` is optional: it runs only when the owner asks, no gate runs it and no gate points to it, and accord calls no model. It runs `accord audit`, which prints `fact:` lines (languages, folder layout, the linter and the rules its config turns on, the formatter, type-check strictness, test frameworks, the PR template, the commit rule, the conventions file) and `gap:` lines, each with the one command or step that fixes it, then `gaps: <n>`; it exits 0 whenever it ran. A gap that asks for a linter, a formatter or a stricter compiler is never fixed there: the skill offers to queue it as a draft ticket. A `no-pr-template` gap is listed only when no template is tracked and `pr.command` is not set, because a script replaces the template. When `accord/product/conventions.md` holds no convention line (no line that is not blank, a heading, a comment or a `Rejected:` line), `accord new ticket` (on stderr) and the dashboard text print one line naming `/accord-audit`; every repository `accord init` made shows it until its first convention line is written, and it never refuses. On the owner's yes the agent drafts 10 to 20 convention lines from the code, each with evidence (how many files follow it and how many break it, with one `file:line` of each) and an `enforced by:` value (a rule the linter config turns on, else `prose`), and asks about one line at a time. `accord conventions write <file>` puts only the accepted lines on the branch `conventions/<date>`, committed with the `conventions` subject (`commits.subjects.conventions`; like `queue` and `drop`, a branch that is not a ticket branch, so outside the commit rule), and the skill opens a pull request with a short fixed body that waits for the owner.

`accord audit` also reports accord's own setup, each gap with its fix: the version pin against the running accord and against npm (`pin-mismatch`, `pin-behind-latest`; an unreachable registry prints `no observation`, never that the version is current), the CI workflow (`workflow-missing`, `workflow-pin`, `workflow-timeout`), the rendered skill, agent and panel plugin files that were edited by hand, are missing or are left over (`render-edited`, `render-missing`, `render-orphan`, `render-retired`), accord's hooks in `.claude/settings.json` judged per hook identity (`hook-missing`, `hook-edited`, `hook-doubled`), the config keys added since the pin with their defaults (the `new-key` facts, from `packages/core/schemas/config-keys.json`), scripts with no trust allow or a stale one (`script-untrusted`, `script-trust-stale`) and the problems `accord lint` finds in `accord/product/security.md` (`security-file`), and a work-hygiene group that reads the claim branches already in this clone (it fetches nothing): `ticket-idle` for a claimed ticket with no activity for longer than `stale_days`, naming the claimer, and `draft-stale` for an unclaimed unfinished ticket untouched for longer than `stale_draft_days` (default 90), naming its creator, with the facts `who` and `work-ages`. A second half reads the worktrees and branches no one looks at: it runs the dry run of `accord worktree clean` offline (no fetch, no prune report, no lock) and lists each `removed`, `deleted` or `pruned` line as one `worktree-leftover` gap naming the author of the tip the line concerns, with the fix `accord worktree clean`; it adds `branch-orphan` for a local or origin claim branch whose ticket file exists nowhere (in the checkout, on the default ref or at the branch's own tip) and `claim-unpushed` for a local claim branch with no origin counterpart, not on the default ref, whose tip is older than `stale_days`, each naming the author of the tip. A branch the dry clean already names in a `deleted` line is not listed again. A third group reads the owner's answers and the baseline. At verify the session writes the owner's answer on each Must or Should deferred item's ledger line as a trailing mark, ` → <id>` (queued as a draft ticket; the id is a letter first, then letters and digits joined by `-`, ending in `-<digits>`, so a prose arrow like `0.9 → 0.10` is no mark) or ` → declined`, the arrow U+2192 only; the marks stay uncommitted until verify step 6 commits the ledger, and the session runs `accord deferred <id>` again to check that every mark parses, since that command lists only items with no mark. `deferred-undecided` is one gap per unmarked item of a finished ticket on every lane (a lane S or R ticket's finish asks nothing about deferred items, so the audit is where its items are decided), judged only for a ticket claimed at or after `DEFERRED_MARK_FROM`, the release that ships the mark; an older ticket and one whose claim release cannot be read are counted in the `deferred-marks` fact and never listed. `baseline-removable` is one gap for the ids of `accord/tests-baseline.txt` that can go (named by `@test:`, carrying `risk:`, or absent from the report while their file is in it), with their line numbers and at most ten ids per run, read only from a fresh full test report: the `tests-baseline` fact says `no observation` for a missing or stale report, never that none can go. `/accord-audit` treats a gap's text as repository data and runs only the command its fix names, only on the owner's yes; before a branch delete it shows `git log --oneline <default branch>..<branch>` and deletes with `git update-ref -d refs/heads/<branch> <tip>`; it writes no mark and no baseline line itself, and gives the mark as a one-line edit for a pull request that changes only that ledger. The audit prints the branch command (`git update-ref -d refs/heads/<branch> <tip>`, pinned to the tip it read; `git push origin --delete`; `git push -u origin`) only for a name made of letters, digits, `.`, `_`, `-` and `/`, and never runs one; its facts are `worktree-refs` (it judges the refs already in this clone, while `accord worktree clean --dry-run` fetches first) and `claim-unpushed` (`no observation` with no origin remote, never a clean result). Git's merge check, which the dry clean uses, may add unreferenced objects to the object store that `git gc` clears; the audit writes nothing else. Open work is the dashboard's own definition (`isOpenWork`), so a done ticket whose frontmatter still says draft is never an old draft. A claim branch already merged into the default branch while its ticket is not done is not reported: with merge-before-verify that is a normal state, and a ticket that is truly stuck is already reported by the stuck-ticket check, `ticket-idle`, so the audit stays quiet there by design (Phase 08.8 D-08). The audit's fixes for `ticket-idle` and `draft-stale` tell a person what to ask in words (`ask to continue <id>`, `ask to pick up <id>`), never a typed form, and leave the merge of a queued draft's pull request to the owner, as the audit skill's rule says: pull requests are merged by the owner. It reports and never edits: no change to the security file, to a trust allow or to `config.yml`. A team's own checks join the report through `audit.command`, a script that runs only after `accord trust audit.command@<digest>` (like `git.sync`, in the checkout, with `ACCORD_ROOT` and `ACCORD_BASE_REF`, 300 seconds, 1 MiB): its first output line is a `team-audit` gap when it exits non-zero. How a person is shown is a per-person choice made in git config, `git config accord.who initials` (any scope; never in `accord/config.yml`): one display function (`whoShown`) serves the audit's gap texts, the dashboard and status text, `accord show`'s Holder line and the panel, so no view shows one email two ways. Only the exact value `initials` switches it; `email`, unset and any other value show the email, and a bad value never fails a command. The JSON identity fields (`claimedBy`, `holder`) stay the email; `accord dashboard --json` adds `claimedByShown` and `accord show --json` adds `holderShown` in initials mode only, which the panel prints. The end of `/accord-upgrade` and of the onboard flow asks whether to run the audit; no gate runs it and nothing runs it unasked.

The version pin of `config.yml` (D-94) is a hard refusal for every command that reads the repository: exit 2 naming both versions, no flag and no environment variable that skips it. D-95 exempts `--version` and `--help`, and `upgrade`, which runs as the newer version. D-18 (Phase 8.1) adds `audit` as the second command that runs under a mismatch: it reports the mismatch as a `pin-mismatch` gap instead of refusing, reads the pin from the raw text of `config.yml` when this accord's schema refuses the file (a key a newer release added; it then also reports `config-invalid`), and writes nothing, so running an unpinned accord over the repository can change nothing. A team script still needs its trust allow, and none runs while the config fails this accord's schema.

`accord new ticket --queue --title <title> --note <line>` queues an idea from any session, a session that works a ticket included: it writes the draft in one commit on `backlog/<id in lower case>-<date>`, cut from origin's default branch in a temporary worktree, adds the creator's `people` entry to that commit when origin's default branch does not list the creator (and has a `people` mapping, which the queue never creates), prints that entry as a `people:` line, and pushes it, leaving the session's branch and working tree as they were. `queue.merge` in `config.yml` is `owner` (the default) or `at-once` and decides what the typed form `/accord queue <idea>` does with the pull request it opens: under `owner` it leaves the pull request for a person to merge, under `at-once` it merges it at once with the method `git.merge` names, never with admin rights. The commit subject is `commits.subjects.queue`, default `backlog: queue {id}`.

Slop (Phase 8.1 D-14, D-15, D-16, D-20). Every review package from `accord review-package` ends its security triggers with a `## Slop` section that lists, one line each as `- slop:<kind> <path>:<line> — <label>`, the AI slop a pattern can see in the ticket's whole diff (the range its first review round has, whatever the round the package is for, so the final reviewer sees what a gate would judge). Every added line of every changed text file is judged, test files included; only Markdown files, generated files (the `generated:` paths of `accord/config.yml` and the exact copies `accord skills sync` writes) and dependency lockfiles (`package-lock.json`, `yarn.lock`, `pnpm-lock.yaml`, `Cargo.lock`, `go.sum` and the like, in any folder) are skipped. The patterns are single-line regexes written like the security patterns, `- <id>: line /<regex>/[i][ for .<ext>[, .<ext>]] — <label>`, with the same backtracking guard and line bound, and an optional `for` scope. The built-in kinds, whose names are stable (the id is the kind, with a language suffix per language row, so a count by prefix works): `empty-catch`, `empty-catch-cs`, `empty-catch-py`, `any-type`, `any-type-cs`, `any-type-py`, `commented-code`, `commented-code-cs`, `commented-code-py`, `commented-code-html`, `commented-code-css`, `important-css` and `inline-style-html` (TypeScript and JavaScript, C# and .NET, Python, HTML and CSS), and three that are code, not patterns: `new-dependency` (a name added to a package manifest: package.json, composer.json, `*.csproj`, Directory.Packages.props, packages.config, requirements*.txt, pyproject.toml, go.mod, Cargo.toml, Gemfile; a version bump is not one), `file-growth` (a file that crossed `slop.max_file_lines`, default 500, or was already over it and grew by a tenth of it) and `orphan-file` (a new file whose path and stem no other tracked file holds; tests, dotfiles, config and data files, images and files under `bin/`, `accord/`, `.github/`, `.claude/` and `.agents/` are not). A team adds patterns for other languages in `accord/product/slop.md` (`## Patterns`, `## Removed`, not written by `accord init`), replaces a default by giving a pattern its id, and switches a default or one of the three kinds off with `- Removed: <kind> — <reason>`. A team pattern that can backtrack catastrophically, or does not read, is not in force, and `accord lint` reports it as `lint.slop-file`. The three structural kinds that need understanding, not matching (a new helper that duplicates a function the repository already has, a function too long to read at once, an export nothing imports), are the reviewer's, a checklist under the `quality` lens.

The slop gate (Phase 8.1 D-17, D-15). `accord gate done` gives `gate.slop-unresolved`, an error, for every slop hit of the ticket's cumulative diff (the list `accord review-package` prints under `## Slop`, read again at Done) that is neither fixed, so gone from the diff, nor justified. A justification is one line in the last `## Round` of `accord/tickets/<id>/review.md`, with or without a list marker (`-`, `*`, `+` or `1.`): `slop:<kind> <path>:<line> — <reason>`, naming the hit's own kind, path and line; a line in an earlier round, with another line number, or with no reason resolves nothing. The reviewer writes it in its report outside any numbered finding, and the review record copies it into the round as it copies `Not an interface:` lines. The refusal prints the exact line to write. The rule belongs to the review stage (`STAGE_OF` in `packages/core/src/gate/floor.ts`), so it leaves with `strictness.stages.<lane>.review: off` and has no level a team can set; it sits in the lane M and lane S Done tables, not lane R's (lane R has no review). It fails closed: a team pattern of `accord/product/slop.md` that is not in force (does not compile, is refused by the guard, does not read) is a finding at its line naming `accord lint`, and slop facts that cannot be read (no plan baseline, a git failure) are one finding quoting why, never a silent pass. Only a ticket claimed at or after the release that ships it is judged (`SLOP_FROM` in `packages/core/src/round/pin.ts`, read through `claimPinBefore`); a ticket in flight keeps its answer and starts no slop read.

Why a CLI and not just templates and prompts: templates are suggestions and prompts are advice. Both can be ignored by an agent, which is the dominant failure mode. The CLI gives the same deterministic answer on a laptop, inside an agent session, in CI, and later in the hub, from one implementation.

## 9. Workflow layer

The contract above says what must be true before and after a ticket. The workflow layer is how a coding agent gets there without drifting from the owner's intent. The full rules are in the [workflow layer spec](specs/2026-10-12-workflow-layer-design.md); this is the map.

**Entry point.** `/accord` with no argument runs `accord dashboard` and shows its output verbatim: YOURS, TEAM, READY, UP NEXT with the unclaimed open tickets that are not ready, EPICS with children done over all children, one count line, and the actions that apply. The CLI ranks every section; the model never reorders or adds to it. Any other text after `/accord` is routed by intent (next paragraph); a request to change something starts work: the change route proposes a lane, says why, and starts the intent stage. A person never needs a special form: text in any words that asks to resume or take a ticket, named by id or described, reaches Continue or Pick up through the routing, and an idea to note for later reaches the queue. Three typed forms skip the routing, and they are what the dashboard, the panel buttons and accord's own printed lines send: `/accord continue <id>` resumes a ticket at the stage and step it reached, `/accord pick-up <id>` claims an unclaimed ticket and starts it, and `/accord queue <idea>` notes an idea as a draft ticket on its own backlog branch without starting it. There is no separate command for a new request, a continue, a pick-up or a queue: they are steps of `/accord`.

**Routing.** `/accord <text>` routes the text by intent, in the main session, because the CLI cannot judge intent and accord never calls a model. The session says the route out loud ("I read this as a question and will answer it; say so if not"), takes the owner's override, and asks one short question when it is unsure, never defaulting silently; it never chooses a model. The routes are a change (the change route starts work: lane S or M, a bug whose cause nobody has shown going to `accord-debug` before its approach), a question (answered from the code, with no ticket and no lane proposal), a brainstorm (a Socratic back-and-forth that ends by proposing build now, queue, research or nothing), an idea to queue (`/accord queue <idea>`), work on a named or described ticket (Continue for a claimed one, Pick up for an unclaimed one, asking which ticket when the text fits none or several), research (lane R), a change, drop or merge of an existing ticket (an edit, or `accord drop <id> --reason`), a review of code or a pull request accord did not build (read-only, `/accord-review-pr`), and a request about accord itself or the feedback on a pull request, which loads the command that owns it (`/accord-upgrade`, `/accord-audit`, `/accord-onboard`, `/accord-config` or `/accord-resolve-pr`) with no ticket and no session check. A session that works a ticket runs all of them but a change to another ticket: the prompt-expansion hook (matcher `accord`) lets the dashboard, free text, `/accord queue <idea>` and `/accord-upgrade` through and refuses a typed Continue or Pick up of another ticket, the CLI guard behind it refuses a change typed as free text, and both give a line ready to copy that opens a new session in the right folder. A session is never moved from one ticket to another.

**Dashboard and the network.** `accord dashboard` makes one fetch from origin, bounded at 10 seconds, before it reads, so a teammate's pushed claim shows under TEAM without a manual fetch. When the fetch fails or times out it goes on with the refs already in the clone and says so: one line starting `fetch from origin failed` before the sections in text, and the field `offline` (the reason) in `--json`, which stays one JSON document; with no origin remote it fetches nothing and says nothing. The panel draws from `accord dashboard --json --no-fetch`, which starts no fetch and so pays no bound, and its one background run, which fetches, pays the same bound. A ticket file that a `backlog/*` branch (local or origin's) adds over the default branch, whose id neither the working tree nor the default branch holds, is a queued draft: it is a row of UP NEXT and part of the backlog count, read from that branch's tip, and it disappears from the view once the default branch holds the id. The dashboard draws one picture per repository (Phase 15 D-17), the same from the main checkout and from any worktree of the clone: every ticket but the one the checkout itself claims is read from the default ref, with each unmerged claim branch overlaid on it, and the checkout's own ticket is read from its own files, so an uncommitted tick shows only there; a ticket file that only this checkout holds (a draft not yet pushed) keeps showing from this checkout. A ticket whose claim branch merged, by ancestry or, for a squash or rebase merge, because the records at the claim's tip are the very blobs the default ref holds and a ledger exists, and that is not done on the default ref, is listed under "merged, waiting for verify" with verify as its next step (D-29): never as ready, up next or the pick-up suggestion, and its worktree stays until verify (08.8 D-08). A ticket in review or verify on the default ref with no claim ref left (the host deleted the branch) is listed there too, for lanes M, L and P. Merge state is read from git and never written to a ticket (D-21), and no server or background process keeps the picture fresh (D-16): the pane re-runs the same command. `accord status`, `next`, `show` and audit keep the checkout's files as their base for now. `accord status` and every other read command still never fetch. Progress before verify goes to the ref `refs/accord/<id>`, never to the branch (Phase 15 D-12): `accord worktree push <id>` sends `+refs/heads/<branch>:refs/accord/<id>` at the same points as before, after every stage and every recorded build task (D-14), and `--branch` keeps the branch push, which verify uses. The ref is a mirror of the claim branch, never a claim: a teammate's dashboard fetches `refs/accord/*` into `refs/remotes/origin-accord/*` in its one fetch, with no refspec edit, and reads a ticket's records from the ref only when it descends from the claim tip; `accord worktree clean` deletes the ref with the ticket's branches, and audit `claim-unpushed` counts a claim whose tip is on the ref as pushed (D-15). A failed or refused ref push prints one line and never stops the work. The setting is `progress.push` of `accord/config.yml`: `off` pushes no progress before verify, `auto` pushes the ref only on a host a recorded test proved, `ref` pushes it on any host (the team's own choice); an absent key means `off`. Which hosts are proven (D-13, D-33): none. The one test that can prove a host is a push of `refs/accord/T-1` to a private scratch repository on github.com whose `push` workflow has no filters, then a look at `gh run list` for a run the push started; it needs the owner's yes at that time because it creates a repository in the owner's account. On 2026-11-26 the owner's standing goal answered not-now, so the test has not run: no verdict is recorded, `PROGRESS_REF_PROVEN` stays empty and the default stays `off`, so `auto` pushes nothing on github.com either, and SC-5 stays open until the test runs. GitLab, Azure DevOps and self-hosted hosts are not tested; `auto` pushes nothing to them, and a team that knows its host starts no CI on such a ref sets `ref`. Until then the claim shows to teammates at claim time and the progress when verify opens the pull request.

**Branch clean.** `accord worktree clean` also judges the local `backlog/*`, `fix/*` and `release/*` branches against origin's default branch. One with a commit of its own whose tip is on it (reached only through a merge commit's second parent, never on the default branch's first-parent history), or whose merge into it would change nothing (a squash or rebase merge), is deleted together with the worktree that has it checked out, an agent folder under `.claude/worktrees/` included, after the guards every worktree removal passes (uncommitted work, a hold of another session, this session's own folder, a rebase under way); it prints `deleted <branch>: merged into <default>` and the worktree's `removed` line. One with commits the default branch lacks is kept with `kept <branch>: it has commits <default> lacks`, and one whose tip is on the default branch's first-parent history, a branch cut from it with no commit of its own yet, is kept with `kept <branch>: it has no commit of its own`. A ticket's own branch is left to the done and dropped cleans, any other branch name is never judged, no remote branch is deleted, and the whole clean runs under the clean lock, so two sessions never clean at once. `accord worktree clean --dry-run` runs the same decisions and prints the same lines in the same order, stale remote refs and stale worktree records included, and removes, deletes, pushes, prunes and locks nothing (no clean lock, no holds lock, no record rewrite; a forgotten folder keeps its files). It still fetches from origin first, as a real clean does, and reports the prune of stale remote refs through `git remote prune --dry-run`; each step a real clean could fail (a push, a worktree removal) is printed as it would read when it succeeds, so a real run can differ by exactly those lines. `git push --dry-run` is not used to narrow those lines (Phase 08.9 D-06): it costs one network call per branch, needs credentials, can hang offline, and the dry run, which `accord audit` also runs, is meant to stay quick. `accord worktree clean --after-merge <id>` is the clean a session runs once its pull request merged, from outside the ticket's worktree: it first drops this Claude Code session's own hold on `<id>` and no other session's, then judges the folder by every guard above and removes what a plain clean removes, so the ticket's worktree, local branch and origin branch go only when `<id>` is done on the default branch. Inside `<id>`'s worktree, or any folder of it, it refuses with exit 2 and `is the worktree this session stands in: leave it first`, and removes and drops nothing; with `--dry-run` it prints `would release the hold of <id>` and writes nothing.

**Follow-through.** After its finish report (verify step 7) a session whose ticket has an open pull request does not end its turn: `shared/pr-wait.md`, rendered as `accord/pr-wait.md`, has it run `accord pr wait <id>` with the Bash tool in the background, so a command and not a model does the polling (Phase 15 D-19, D-20, D-22). `accord pr wait` asks `gh` every 45 seconds, reads only (no write call, no model, no comment text ever printed), and its last stdout line is the one the session reads: `pr-wait: merged #<n>`, `closed #<n>`, `feedback #<n>: <counts> from <logins>`, `ci-failed #<n>: <check names>` or `limit #<n> after <m> minutes (<f> polls failed)`, each ending the wait with exit 0; `pr-wait: unavailable: ...` (`gh` missing, not logged in or too old) and `pr-wait: no pull request for <branch>` end it with exit 2, and mean the wait never started; the one exception is a `no pull request for slice/<id>/<n>` printed after lower slices merged, which means the next slice needs its pull request, `accord pr <id> --slice <n>`, before the wait starts again. The verdicts are judged in the order merged, closed, feedback, ci-failed. Feedback is a comment, a review or an inline comment made after the head commit by an OWNER, MEMBER or COLLABORATOR, or a standing CHANGES_REQUESTED; a bare approval is not feedback, the `gh` user's own replies are not, and what others wrote is only counted on an `ignored` line. The limit is `pr.wait_minutes`, 120 by default, because Claude Code stops a background command after two hours at most; a run whose last line is none of the above is read as the limit. Feedback starts `/accord-resolve-pr` for that pull request with `review.post` at `draft`, so replies wait for the owner (D-32); the next wait starts only when the resolve ended with a new commit pushed, and at most three waits follow a feedback line in one session, since the same comments would end the next wait at once. A failed check follows `failure.md` from its step 1. A merge ends with `ExitWorktree` (action `keep`) and then `accord worktree clean --after-merge <id>` from the main checkout, which removes the ticket's worktree and branches under every guard (**Branch clean.**, above); when the session cannot leave its folder the skill prints one line, `<id> merged: its folder and branch go at the next session start in another folder`, and ends the turn, and that line is the shipped behaviour, never a removal by hand. The merge is read, never written (D-21): nothing edits the ticket to record it. At the limit the session prints one reminder line and ends its turn; nothing runs after that, so the dashboard keeps the open wait visible: a ticket verified on its claim branch and not done on the default ref carries `waitingSince` (additive in `accord dashboard --json`: the ISO 8601 UTC time of its newest activity, a commit time git already gave the loader and never a `gh` answer), the text row reads `(waiting for merge, 2h)` and the pane draws `waiting for merge, 2h` under the row, the age in whole minutes under an hour, whole hours under two days, else days, computed at each draw; no gate or decision reads `waitingSince`. The next session makes the wait up: that row is in YOURS with `/accord continue <id>`, which takes the stage `done` to verify step 6 and its finish report, and the finish report starts the wait again, with no routing text of its own. With stacked slices the session waits at the last slice (`slices.md`): the command follows the lowest open slice pull request, judges every open one each round so that feedback or a failed check on any slice ends the wait naming it, moves the next slice's base to the default branch with `gh pr edit <n> --base <default>` after a merge (the one write `pr wait` makes, guarded by a fresh `gh pr view`; a refusal is printed and the wait goes on), ends `merged` only when every slice has merged, and one limit covers the whole wait (D-28). There is no server and no process that runs with no session open (D-16), and no `accord inbox` (D-30): other people's pull requests waiting for the user stay with `gh pr status`, GitHub's notifications and `/accord-review-pr` when typed. **Unproven.** Two host behaviours this rests on have not been run live: `ExitWorktree` on a path-entered worktree on Windows, and a background run waking an idle session when the pull request closes. Every test intercepts `gh` and replays its answers, so none reaches the host, and the owner's live checks (15-07 task 3, D-33) are still to do; nothing here claims they pass, and if `ExitWorktree` fails on Windows the fallback line above is what ships. **Parity exception.** The background wait and `ExitWorktree` are Claude Code tools; the rendered skill says "tools of the host" because a test bans product names in skills, so the declaration is here. `accord pr wait` and `accord worktree clean --after-merge` are CLI commands and run anywhere, and the text dashboard's waiting row is the same in every runtime, but nothing is built, tested or promised for Cursor, Codex and Copilot (Claude Code first, 2026-11-22): there the skill text renders unchanged and no run of it is claimed.

**Lanes.** The size of the work decides how much each stage does; no lane skips a stage.

- **S, small fix.** Intent is a two-line write-back in chat, the main session does the work, one reviewer pass, and the affected tests must pass. It proceeds without waiting when the request has a concrete anchor and one plausible reading.
- **M, feature.** A ticket with `lane: M`, an owner-approved approach, a checked plan, one fresh executor per task, review to convergence, and an evidence report. A story too large for one review is planned as slices (`## Slice <n>` sections of `plan.md`, checked by `accord gate plan`, Phase 15 D-09): the planner cuts them under every `review:` mode when the expected size is over a review budget that counts every line a reviewer reads, code, tests, docs and skills, added plus deleted, and no ticket record, generated file or lockfile (D-06). The budget is `review.slice_lines`, default 1000 lines per slice; a slice over it gets a warning that shows its split, and so does a plan of more than three slices, which proposes an epic and leaves the choice to the owner (D-03). Each slice leaves the default branch working once merged, with no feature flag; when the planner cannot cut such a slice, the tasks stay in one slice (D-11). The slices ship as stacked pull requests, one after the other without waiting for a merge (D-07, `packages/core/skills/accord/slices.md`). Slice 1 is built on the ticket's claim branch and slice n on `slice/<id>/<n>`, a branch no claim template matches that `accord worktree slice <id> <n>` cuts at the tip of the branch before it and records in the git folder's `accord/slices`, so the dashboard, `worktree clean` and `pr wait` find it (D-31). Each slice's draft pull request is opened with `accord pr <id> --slice <n>` and a `--base` of the previous slice's branch (the default branch for slice 1); its body names the slice, the criteria it delivers and its measured size. When review changes an earlier slice, the change is committed on that slice's branch and merged forward into each later slice branch in order with `accord worktree sync <id>`, always by a merge, never a rebase or a force-push, whatever `git.merge` says (D-08); after a slice merges, `accord pr wait` moves the next slice's base to the default branch. Each slice is reviewed on its own diff, from the start `accord anchor` prints on its `Slice:` line, and the last slice also gets one integration review of the whole ticket from the plan's `baseline:` (D-10); the stage skill states this in `slices.md` and leaves `review.md` as it is, which sits a few bytes under its size cap, so a session that skips `slices.md` runs the whole-ticket final review at every slice, which reads more and misses nothing. Criteria are ticked per slice: `accord gate done <id> --slice <n>` judges only slice n's criteria and the tasks of slices 1 to n, the last slice judges the full set, and the CI script derives `--slice` from the head branch (D-31). A slice over the budget warns with `gate.slice-diff-large`, which shows the measured split and blocks nothing, and a team may lower it (D-06). No feature flag is used: each merged slice leaves the default branch working (D-11). **Unproven.** `gh pr edit --base` on real stacked pull requests, and a live session running the whole flow on a sliced ticket, have not been run: every test intercepts `gh`.
- **L, epic.** `/accord <request>` proposes it when a request names three or more parts that would each be a story of its own, runs one epic-level interview (why, for whom, the Vetoes, the Decisions), reads the code once with the scout for the whole epic, proposes a split into two to ten stories, each with its Intent lines, the earlier stories it waits for (`depends_on`) and the files and folders it is likely to touch (`touches`), has one critic pass check the split, and on the owner's explicit yes writes the split file outside the working tree and runs `accord new ticket --type epic --lane L --split <file> --queue`. That one command writes the epic and every story (lane M, `parent:` the epic, `depends_on` from the split) as a single commit on one backlog branch and a pull request; it claims nothing and starts nothing. The split file is YAML: `title`, `intent`, `vetoes` and `decisions` (lists of one-line entries) and `stories`, each with `title`, `intent` (one to five lines), `after` (the numbers of earlier stories) and `touches` (a list of paths, a folder ending in `/`); an `id` on the epic and on every story only where accord assigns none. The epic's `## Decisions` gets the `decisions` lines numbered `D-01` on, so every story's epic block carries them, and its `## Approach` lists the stories in order, each with the stories it waits for and what it touches. The epic itself gets no approach and no plan critique: the owner's yes to the split is its approval. Stories that touch the same file, or where one story's folder holds the other's file or folder, must be chained by `after`, directly or through other stories; otherwise `accord new ticket --split` refuses the split before it writes anything (D-02). A new-code epic, where most of the code does not exist yet, starts with a foundation story that fixes the interfaces (types, signatures, data shapes, file layout), and every other story waits for it (999.60 decision 3). One `accord-critic` pass in mode `split` reads the split file and the scout's reply before the owner sees the split and looks for stories that edit the same code without a `depends_on`, missed logical dependencies and stories that cannot stand alone; it runs once, with no second round, and the owner decides (D-01). A story that finds late, at plan or build, that it needs code another story of its epic builds and its `depends_on` does not name that story follows `epic-dependency.md`: it stops and asks the owner; the default proposal splits the shared piece out as a small story both depend on, and the fallback waits for the other story within `stale_days`, which `accord audit` reports as `ticket-idle` once passed, after which the owner moves the piece into this story or hands the other ticket on; a stacked branch between stories stays rejected (999.60 decision 4). A scope that is too big is judged by purpose, never by a count of criteria (D-04): the approach critic, which reads the whole ticket once, asks "do the acceptance criteria serve one outcome for the person in the Intent, or several outcomes that could ship separately?", and several independent outcomes is a Should finding that proposes an epic for the owner to decide, as many scenarios of one feature are one outcome; with the approach stage off, the plan-mode critic asks the same question; no new agent runs it. Each story then runs lane M as today, picked up with `/accord pick-up <id>` in its own worktree and pull request, in parallel when nothing it depends on is unfinished, and each story gets its usual critique. A plan that grows too large is pointed here: the plan-size refusal names splitting the work into an epic of smaller stories with `/accord <request>` (lane L), and `gate.plan-large`, a warning that fails nothing and a team may lower, says the same for a lane M plan of 15 tasks or more. It applies only to a ticket claimed from `PLAN_LARGE_FROM` on (read through `claimPinBefore`, the same release as `TITLE_RULE_FROM`), so no plan that exists when the rule ships is judged.
- **P, project.** Not built yet. `/accord <request>` says so and proposes an epic instead.

Hidden complexity found mid-task lifts the lane; a lane never drops mid-task. A ticket without `lane:` keeps every 0.1.0 rule.

**Stages.** Each is a file of the `/accord` skill folder, read by the ticket's stage, and each starts with `accord anchor`, which re-reads the ticket's Intent, Vetoes, Decisions, Corrections, and position from git rather than trusting memory. The stage comes from `accord anchor` after every `/clear` or compaction: `/accord` reads the file its `## A ticket at a stage` section names for the lane and stage (core maps them in `STAGE_FILES` and `stageFile`), and in Claude Code the session-resume hook prints a `stage file:` line naming it, while the description's stage clause serves the other tools. The approach stage has the file `approach.md`, but the anchor prints `intent` for a ticket still at approach, so the hook names `intent.md` for it and `/accord` takes the approach row from the ticket's `## Approach`.

| Stage | File of `/accord` | Ends with |
|---|---|---|
| intent | `intent.md` | a ticket with Intent, two to five criteria, and Vetoes; ambiguity scored down to 0.2 or less |
| approach | `approach.md` | a brief of about 15 lines; the owner's yes runs `accord approve`, which writes `approved_hash` |
| plan | `plan.md` | `tickets/<id>/plan.md`; `accord gate plan` passes and writes `plan_hash:` |
| build | `build.md` | one ledger line per task, written by `accord task-done` |
| review | `review.md` | `tickets/<id>/review.md` ending in `verdict: converged` |
| verify | `verify.md` | `tickets/<id>/verification.md`, the owner's report, and `accord gate done` |

The plan stage also ends with a short summary for the owner, whose six items are fixed and whose length is not capped: what the plan does, how it is split (task count and slices), which criteria it covers, the Rulings taken, the risks and the next step; no task, ticket or `plan.md` is pasted (Phase 15 D-26, `plan-summary.md`). It is the only stage that does: intent and approach end as above because the owner approves their content, build and review leave the owner nothing to decide, and verify already ends with its own fixed finish report (D-27).

The intent stage has no audit step: a criterion with two readings is caught by the approach critic and by the owner's approval of the short approach view, then, once Phase 10 builds them (its D-02), by the acceptance tests written red before any code.

A team may switch `discuss`, `approach`, `plan` or `review` off for lane M, L or P with `strictness.stages.<lane>.<stage>: off`; `intent`, `build` and `verify` never leave, and no stage of lane S or R does. With `review` off the security review of a lane M, L or P ticket stays on the floor: `gate.security-unreviewed` is one of the locked security and data-loss rules (`packages/core/src/gate/floor.ts`), not a rule of the review stage. With `review` on it reads the `Security:` line of each round of `review.md`; with `review` off there is no round, so `accord gate done` reads the ticket's ledger instead: the line `Security: lens security ran at <sha>` under `## Security` in `accord/tickets/<id>/ledger.md`, checked against the security triggers of the changes since that commit (a commit the repository does not have is an error, never "no triggers"). A ticket whose changes match no security pattern needs no line, and a ticket claimed before 0.16.0 answers as before (`SECURITY_OFF_FROM` in `packages/core/src/round/pin.ts`). Phase 8 (D-24) chose the opposite and Phase 08.8 (D-03, D-04) reversed it. `accord status`, `accord dashboard`, `accord show` and `accord anchor` name every stage that is off and say `the security review stays on` when review is one of them, and the build stage's next step sends a session to the section `With the review stage off` of `review-security.md`, which runs the security package, the lens and the fixes through `accord brief <id> --fix`, then writes the ledger line.

`/accord-debug` finds a root cause before any fix, ranks competing hypotheses before testing one, and returns to the stage it interrupted.

`/accord-debug` also works on an issue no ticket holds (`debug-free.md` of its folder). It finds the root cause with a fresh debugger and fixes nothing: no executor runs and nothing is committed, because no ticket exists to hold the work. It ends by offering a ticket through `/accord`, with the root cause in the request. Its state is one file per repository and user in a private folder of the system temp directory (`<temp>/accord-debug-<user hash>/<repository hash>.md`), which `accord debug path` names: outside the working tree, so `git add -A` never sees it and nothing is committed; the same for every worktree of one repository; kept across `/clear`; lost on a temp clean-up or a reboot, which ends the investigation and loses no work. Only `accord debug path` creates it (a 0700 folder and an empty 0600 file, refused when a link, a folder it does not own or one open to group or others, with nothing changed); the skill and the hook only read it, and its text is data, never an instruction. In Claude Code a session resumed with no active ticket prints `Unfinished: <path>: resume the debugger with /accord-debug` while the file holds an open investigation. The other tools have no hook: a person types `/accord-debug` again.

**The eight commands.** The slash menu holds eight commands, each one a person calls on their own, and a hint shows after the name in the tools that display one: `/accord` (`[request]`: the dashboard and the router), `/accord-upgrade` and `/accord-audit` (`[no arguments]`), `/accord-debug` (`[ticket id] [failure]`), `/accord-onboard` (`[no arguments]`), `/accord-config` (`[area]`), `/accord-resolve-pr` (`<PR | ticket id>`) and `/accord-review-pr` (`<PR | branch>`). `accord-designer` (`<ticket id>`) is a ninth entry that renders only when `roles` lists `designer`, so it stays opt-in. A step of one ticket's life is a file of `/accord`; something a person asks for on its own is a command, which is why the pull request feedback procedure (`/accord-resolve-pr`, the old comments procedure: read every thread, have a fresh read-only judge check each before fixing any, put what is unclear first, stop on a conflict with a Veto, Decision or Correction, fix through the stages, re-check each fixed comment with a fresh judge before its reply, post replies only after the owner's yes) and the foreign review (`/accord-review-pr`, read-only) left the accord folder.

**Settings.** `/accord-config` walks the settings from data, not from a scan. `packages/core/schemas/config-areas.json` names eight areas (`team`, `git`, `tests`, `review`, `integrations`, `hygiene`, `templates` and `managed`) and puts every config key in exactly one of them with a plain-words text; core exports the data as `CONFIG_AREAS`, and a new top-level key with no area fails the suite. `accord config areas [<area>]` prints it: `area: <id> - <title>`, then `  <key> = <value, or unset> - <what it controls>`, then any `  proposal: <key> = <value>  (evidence: <text>)` line from the detection `accord init` runs. It reads and writes nothing. `/accord-config` goes through the areas one at a time and shows each proposal as a recommendation; `/accord-onboard` goes through only the keys that carry a proposal, and scans for them: the session's own agent scans the repository area by area (the areas and keys come from `accord config areas --json`), with one fresh read-only `accord-scout` per walked area whose keys `accord init` did not propose, its facts checked by `accord scout check`. The scout never proposes and accord calls no model, so the session turns the facts into proposals, each with evidence. `accord config areas --proposals <file>` merges them through core's pure `mergeProposals`, `accord init`'s proposal winning on the same key, an ancestor or a descendant, because it is deterministic. In code it drops a key accord writes, evidence with a line break or any control character (so evidence can never carry rows of a scout report of its own), evidence with no file and line or count, a script behind `accord trust` (also through a parent key), a value holding a control, format or separator character in any string or key (tested on the value itself, not on its JSON text), a value over 1000 characters or nested over 8 levels, a value `accord config set` would refuse (the one refusal function `config set` itself uses, a floor problem already at the proposed key included) and the current value and a citation that does not resolve (checked on the evidence as one line, so no pattern is ever run), and prints each as a `dropped:` line that the walk never asks about; a check that fails drops its own proposal, never the run. Under `--proposals` each `proposal:` line carries `[init]` or `[scan]` right after the colon, so the origin of a proposal never depends on its evidence text, and no printed key, value or reason is longer than 1000 characters. The rule the owner set on 2026-11-21: the worktree setup and the test commands may be proposed, and they are shown verbatim with where they run (the worktree setup runs whenever accord opens a ticket worktree, without `accord trust`). `/accord-config` still scans nothing, and looking at the repository again is `/accord-onboard`. Both follow one per-key walk (`shared/walk.md`): say what the key controls, ask one question that stands alone, write only through `accord config set` after the owner's yes, and say that a script key runs nothing until `accord trust`. The `managed` area (what accord writes itself) is shown and never walked.

**Epics.** A story whose frontmatter `parent:` names an epic gets that epic's rules as input the CLI builds, never as an instruction to go and read the epic. `accord anchor` prints, after the story's own sections, `## Epic <id> "<title>"` with the epic's `### Vetoes` and `### Decisions` as written and `### Epic lessons`; the SubagentStart hook adds the same block, after the ruleset, to the scout, planner, critic, reviewer, final reviewer and judge dispatched in the story's worktree (not to the foreign reviewer, which has no ticket). The epic is read from the default branch (a Decision added to the epic after the story branched binds now), and the lessons come from there too: at a story's verify a Ruling or lesson that holds for the whole epic is offered to the owner, and on a yes it is written as `- Lesson: <lesson> — "<the owner's words>"` under `## Epic lessons` in that story's own ledger and nowhere else. A later story of the epic sees it, as `- <story id>: <line>`, once the first story is on the default branch; a lesson on an unmerged branch is not shown. No shared epic state file is written or read: every story branch writes only its own ledger, so parallel branches of one epic never conflict, and what a story knows is derived from git. Parity exception: a runtime without accord's hooks or agents (Cursor, Codex, Copilot) sees the epic block only through the anchor, since it has no SubagentStart hook to carry it to its sub-agents.

**Product text.** Product files reach agents only as text the CLI builds through one core function (`productBlocks`), which a role decides the blocks of. The line checks are one core definition (`lineProblem`, applied to the whole file by `checkProductText`): a regular file only (a link, a junction, or a git tree entry that is not mode 100644 or 100755 is never read), HTML comments stripped with the line numbers kept, a hidden character refused (bidi controls and tag characters named, TAB refused, variation selectors, the combining grapheme joiner, the Hangul fillers and the Braille blank refused, U+200C and U+200D kept between two letters and one emoji selector kept after an emoji), the line starts accord itself writes in a brief (`Work dir:`, `Report file:`, `Test command:`, `---`, `Commit rule:`, `Example that passes:`, `Test only:`) and the fixed block headings refused as a reader reads them, that is whatever the case, spacing, list, quote, heading or emphasis marks, full-width letters or joiners inside the word, and a line over 300 characters (4000 for a findings file, which holds finding text and pasted comments). Every scan the check makes is linear in the line, and the length is measured before any expression runs. Each refused line is shown to the agent as a fixed placeholder that names the file and the line and never the text, and `accord lint` reports it as `lint.conventions-file` over the whole file, an error in the floor group that no strictness key lowers; delivery never fails on a bad line, it withholds it. `accord conventions write` uses the same check, so it accepts exactly the lines delivery delivers, and `accord upgrade` lists the lines to fix, so the upgrade pull request is where old lines are fixed. There is no size cap yet (backlog 999.51). Each block carries one duty line that says what the agent does with it. Every executor brief, the task brief of a ticket claimed from 0.13.0 and every fix brief, is `accord brief` output in one order: the ruleset, the ticket, the task or the findings under `## Findings`, the conventions under `## Conventions`, then only the lines the CLI writes (`Work dir:`, `Report file:` and its contract, the test command, the commit rule, and `Test only:` with `--test-only`), so no repository text follows a CLI line. `accord brief <id> [task] --fix <findings file>` builds the fix brief from a findings file that passes the same line checks; a ticket claimed earlier keeps its task brief byte for byte with its conventions append line-checked (a line that holds a comment is checked as written, and again for each piece the comment marks cut it into, because that append prints raw lines), and its fix brief has the layout of any other (no CLI-built fix brief existed to keep, so a fix brief gated on the claim pin would send an old ticket back to a hand-written one). `--out <file>` writes an agent file as UTF-8 with no byte order mark into the git-ignored `.accord-reports/<id>/`. From 0.13.0 and outside lane S, `accord round` refuses a fixed finding whose `checked:` places no executor fix report (`fix-<k>.md`) lists, through the same `checked:` mark and with no second receipt; the fix report lives on the working machine, as the task report does, so a session that changes machine between the fix and `accord round` runs the fix again (a known window, D-19); a ticket with no claim commit git can read is never refused for a report. The debug fix made before any fix record exists is built by `accord brief --fix` like the others, but nothing refuses a session that skipped it: this is a stated gap, and the later review round of the episode's commits is the backstop. A judging agent (the reviewer in every lens but security, the final reviewer, the lane S reviewer, the judge, the foreign reviewer) reads the default branch's copy of `accord/product/conventions.md` as the rules in force and the branch's own change to it as a diff read as text whatever the branch's attributes say, so a branch cannot loosen a rule for its own reviewer (D-05); a writer or planner reads the working branch's copy (D-06). In a clone with no default ref the judging agents get the working copy and one line that says so, and the text then depends on the last fetch of that clone, which is accepted because it is prompt text and never a gate verdict (D-07). A pull request of another repository gets none of this repository's conventions and is judged against its own stated purpose: the CLI tells it apart from the link `gh pr view` printed and origin's URL, never the model, and a fork clone whose origin is the fork counts a pull request as another repository when the pull request's repository differs from origin's (R-9; an origin on `github.com`, `ssh.github.com` or a `github.com-<name>` ssh alias with the same owner and repository is this repository, and the same name on a host the CLI cannot place is told as unknown, never as another repository). Business rules and the glossary never reach the foreign reviewer or the judge. The scout, the planner, the critic and the judge each get one `accord related <id> --for <role>` file (the ruleset, the related tickets, the Rejected lines and a story's epic block, then conventions): the scout's, the critic's and the judge's from the default branch's copy and the planner's from the working copy, and the judge's also holds the branch's own change to `conventions.md` under `## Product files changed`, so the judge gets both halves as every other judging agent does (D-30). The skills pass the path of that file at every scout, planner and critic dispatch, a diff round and the legacy plan round 1 included, except the approach critic, which still never gets the planner's `direction.md`; Phase 10 keeps those lines, and a test pins them. **Agents.** Work that must not grade itself runs in fresh agent contexts, installed for the `claude` runtime at `.claude/agents/accord-<role>.md`: `scout`, `critic`, `planner`, `executor`, `reviewer`, `final-reviewer`, `foreign-reviewer`, `judge`, `verifier`, `debugger`, and `researcher`. Every agent receives the ticket verbatim, never a summary; an executor gets it inside `accord brief <id> <task>` and never sees chat history. The foreign reviewer has no ticket: `/accord`'s review of code accord did not build gives it a description file and a diff package that the main session wrote outside the working tree, and it declares only Read, Grep and Glob, so no text in a pull request can make it run a command, write a file or dispatch an agent; the ticket reviewer keeps Bash for ticket reviews. The judge, `accord-judge`, decides whether one item of feedback holds (a comment on a pull request or one reviewer finding), from files only, with only Read, Grep and Glob, and answers `holds`, `does not hold` or `unclear` with the evidence its kind needs: a bug claim holds only on a failing test its caller ran, a claim about the code needs a file and line, a style item is checked against the team's conventions (the default branch's conventions in the file `accord related <id> --for judge` or the review package gives it, with the branch's own change to them as a change to judge, or else it goes to the owner), and a scope item that touches the intent, a Veto, a Decision or a Correction goes to the owner. One fresh judge runs per item, because the session that wrote the code tends to defend it. `/accord-review-pr` runs it on each de-duplicated finding before the owner sees it, and `/accord-resolve-pr` runs it on each comment before any fix and again on each fixed comment, against the new code, before its reply says it was fixed (a fix that fails the re-check goes back to fixing). That command runs no test on the code under review, so there a bug finding never holds: it is dropped when a file and line show it false and otherwise marked needs a manual check, while `/accord-resolve-pr` keeps the failing-test rule: a bug claim holds only on a failing test written before any fix, and the judge never runs a test, so its caller runs it and hands over the test id, its file and its output. In lane S the session writes that test. In lane M `accord-debug` writes it: its executor commits only the failing test and stops, a fresh judge then rules on it, and only after the judge's `holds` does a second executor run fix it; on `does not hold` or `unclear` no fix starts and the test commit is reverted when the comment ends with no fix. The executor stops after the reproduction test only when its brief's last line is `Test only: commit the reproduction test alone, then stop.`, a line `accord-debug` writes only for a run `/accord-resolve-pr` starts for a comment; every other brief is built or fixed as before. Between the test-only commit and the fix or the revert, the ticket branch holds a failing test, so its pull request's CI is red. A finding with no file and line is marked needs a manual check and is never shown as holding. Every agent but the researcher declares its tools; the researcher declares none and withholds every write-capable built-in tool instead (`disallowedTools`: Edit, Write, NotebookEdit, Bash, PowerShell, Monitor, EnterWorktree, ExitWorktree, Artifact, ShareOnboardingGuide, RemoteTrigger, CronCreate, SendMessage, TaskStop, and the agent-dispatch tool, `Agent` and its earlier name `Task`), so it is read-only, it inherits the web tools and any installed library documentation tool, and it is the only agent with web tools. It does not run by default: only the intent stage's discuss step dispatches it, once per library, when a gray area or the ticket turns on an outside library, API or version that the code cannot answer. It writes no file; the discuss step's session writes its reply as the one record per library under `accord/research/`, as `intent-research.md`'s `## Outside sources` says, with a source and the date read for every fact. Agent files render for the `claude` runtime only, so this is a declared parity exception: in a runtime with no `accord-researcher` agent the discuss step tells the session to look the library up itself with its own tools under the same section and to write the record the same way, with no fresh context until backlog 999.11. The judge has the same exception: on Cursor, Codex and Copilot, which get no `accord-judge` agent file, the session judges its own items, reading only, by the rules of the reference `judge.md`, which says so, and tells the owner the verdicts did not come from a fresh context; the owner accepted this exception on 2026-11-21, and Phase 11 may close it by rendering agents on every tool. What stays open, as the owner accepted on 2026-11-18: the researcher keeps the inherited MCP tools (a library documentation tool reaches it only through them), so a write through a write-capable MCP tool is not prevented, and a file it leaves is caught only at review, by the review package's `## Undeclared files` section, once a commit holds it; the agent-dispatch tool is withheld. The executor has Read, Write, Edit, Bash, Grep and Glob and no Skill, MCP or web tool: it reads installed library docs and source through Read and Bash, and when it needs something from outside the repository it stops and returns `NEEDS_CONTEXT` with a question naming what it needs and why, instead of guessing. Step 4 of `build.md` and its Rules route that stop as they already route any `NEEDS_CONTEXT`: a question that touches intent, a veto, a criterion or a public interface goes to the owner, and otherwise the main session, which keeps the host's web, MCP and skill tools, decides how to answer it as a Ruling before a fresh executor gets the answer. A new package is still a `BLOCKED` that goes to the owner. Agent files are rendered for the `claude` runtime only.

**Routing.** `models:` in `config.yml` sets each agent's model and effort; an absent entry falls back to the default in the table below, which is `AGENT_DEFAULTS` in `packages/core/src/skills/agents.ts`. `reviewer.final` routes the final reviewer. `reviewer` also routes the foreign reviewer, `accord-foreign-reviewer`, and the judge, `accord-judge`. From the fix round `escalation.fix_round_tier_up` names (default 4), the executor is dispatched one tier higher, in the order `haiku`, `sonnet`, `opus`. `accord skills sync` renders these values into each agent's frontmatter.

**Tests.** During build the orchestrator runs `tests.affected`, a command template in `config.yml` with `{files}` replaced by the task's files, then `accord task-done`. The CLI never runs a test command: `task-done` reads only the report `tests.report` names, and refuses one written before the current commit. So the `tests.affected` template must write that report, or every `task-done` refuses it as stale. `tests.full` runs on the plan's baseline before build and again at Done, and writes the same report.

**Done gate.** For a lane ticket `accord gate done` adds the review verdict, a ledger line per task, the approval, no failed case, and no untraced case to the 0.1.0 checks. Its commit match also accepts a later commit when every file changed since the recorded one is the ticket's own record (`accord/tickets/<id>.md` or a file under `accord/tickets/<id>/`) or `accord/product/conventions.md` (ST-LN-8 D-08), so committing the records does not make them stale. A ticket done at the merge base with the default branch is immutable together with its folder (Phase 15 D-23): when a pull request changes its file or any record under `accord/tickets/<id>/`, `gate done` fails `gate.done-ticket-edited` with one plain message that names the changed paths, in place of the stale-tick and stale-review reasons, and no other Done rule reads the ticket. A ticket finished inside the pull request is gated as before, since that pull request is where its verify lands. The evidence of a done ticket is history (D-24): the test files and report cases its `verification.md` cites are never resolved at HEAD, so a pull request that moves a test or deletes a cited file passes with no edit of the ticket. The rule lives in the core gate and the host only supplies the fact (the ticket's records at the merge base); the CI script collects ticket ids from the ticket file and from the ticket folder and runs `gate done` on each, so the answer is the same locally and in CI (D-25). A new ticket key such as `ruleset:` is never back-filled into a done ticket, and accord's own writers refuse it: `accord approve` exits 1, `gate ready` and `gate plan` print the verdict and skip the `ac_hash` and `plan_hash` write, and the ruleset back-fill of `worktree sync` and Continue writes nothing. Moving a done ticket unchanged into `accord/archive/` is Phase 16's.

**Hooks.** `init`, `skills sync` and `accord upgrade` write the accord hooks into `.claude/settings.json` and a launcher into `.claude/accord.mjs` (a stamped file like the other rendered ones, from `packages/core/launcher/accord.mjs`). Each hook is in exec form, so no shell reads it: `command` is `node` and `args` are the launcher's path, the pinned version, `hook` and the event, which runs as `node ${CLAUDE_PROJECT_DIR}/.claude/accord.mjs <version> hook <event>`. Claude Code substitutes `${CLAUDE_PROJECT_DIR}` itself, so a project path with a space needs no quoting. There are eight entries: `session-start` on startup prints the ruleset and a one-line summary; `session-resume` on resume, clear, and compact prints the ruleset and `accord anchor`; `subagent-start` gives every `accord-*` agent the ruleset; `prompt-expansion` on `accord` carries the routing guard; `pre-tool-use` on an Agent or Task call checks an executor's dispatch, and its three guards on Write, Edit and MultiEdit protect `verification.md`. The launcher is plain `node:` built-ins and starts the CLI of exactly the pinned version from a per-user cache (`%LOCALAPPDATA%\accord\versions` on Windows, `$XDG_CACHE_HOME/accord/versions` or `~/.cache/accord/versions` elsewhere). The cache holds package files only, never a git result, so it is outside the Phase 08.9 D-04 rule against caching what git says. The first call of a version fills the cache once: `npm install --prefix <temporary folder> --ignore-scripts @accord-dev/accord@<version>` runs through Node's own npm with no shell, in a temporary folder that is renamed into place last, under a lock folder that a second run waits on (up to 120 seconds, a lock older than 10 minutes is taken over). Three versions are kept (the running one and the two newest others). The launcher checks the version word against a version pattern before it builds any path or runs any command, and a version it cannot fill (no network, a registry refusal) prints one line naming the version and the command that fixes it, and a hook then exits 0, so a session is never blocked by the fill; any other call exits 2. Hooks went through `npx --yes <package>@<version>` before Phase 08.9.2, which cost about 1.5 seconds per hook even from its own cache; the launcher answers a call from a cached version in a fraction of that, and some calls with no process at all (the next paragraph). A call that begins with a command word and no version (`node .claude/accord.mjs off`) reads the version from the `accord:` line of `accord/config.yml`. This repository's own hooks run the released pin through the launcher, not a workspace build. `accord anchor` prints the same ruleset first on every tool but Claude Code, whose hooks print it, and the SubagentStart text is unchanged and built by the shared function. Every other setting and hook in the file is kept. The ruleset is one short shipped text: ask about intent, never guess it; record corrections verbatim; scope is impact; the lightest change that fully works; evidence before claims; one test per criterion; end each reply with what was skipped. The cache's limits: it is per user, in the user's own cache folder and never in the repository; npm's check of the tarball against the registry is the only integrity check, since the launcher verifies no signature or checksum of its own; the install runs no install script (`--ignore-scripts`), takes this repository's own package at the one exact pinned version and never a range, and the CLI's own pin check still runs after it. A hostile repository's `.claude/accord.mjs` is no new risk beyond Claude Code's workspace trust: a folder that can ship a hook can already run any command once its owner trusts it, and the launcher runs only a version of the accord package, never a path the repository names. The change also moves what a version change costs: `accord upgrade` moves the hooks and the pane to the launcher, and the first hook after it installs the new pinned version once. Parity exception: Claude Code only; the exec form needs Claude Code 2.1.139 or newer, and an older Claude Code runs a bare `node` and the hook fails without blocking. Cursor, Codex and Copilot have no hooks to move and nothing is built for them (Claude Code first, 2026-11-22).

**Early answers.** Some hook calls are answered before the CLI reads the repository, and the launcher answers the cheapest of them with no process at all. A call while accord is off for the person and a quiet session start (both below) are answered by the launcher from file reads. An Agent or Task call for any agent other than `accord-executor` is answered with `{}`, read from stdin as JSON; a write to `verification.md`, an executor's dispatch and stdin that does not parse still reach the CLI, so no guard is skipped on a doubt. In the CLI, `hook` answers what stdin alone decides (a `pre-tool-use` that is no executor dispatch, a `subagent-start` of an agent outside the epic roles, a `prompt-expansion` whose decision stdin carries) before any load, so those answers start no git process; the stdin-only answers make no pin check, like the `verification.md` write guard, since through the launcher the running version is the pinned one. Session start and resume keep their fetch and clean in the foreground, as before. Parity exception: Claude Code only; the launcher and these answers belong to Claude Code's hooks, which the other runtimes do not have.

**Quiet mode.** A team where some people work in the repository without accord sets `hook_mode: quiet` in `accord/config.yml` (`full`, the default, or `quiet`; a team key that `/accord-onboard` proposes in its step 6, which asks one plain question whether anyone works here without accord, and which writes the key only through `accord config set hook_mode quiet` after the owner's yes). In a quiet repository a session start prints one line and the personal-switch line, and a session resume prints the one line, with no ruleset, no fetch, no worktree clean and no git process: the launcher answers it itself with the CLI's exact bytes, which is one `node` start with no stdin read, no cache path and no bundle, and the CLI gives the same answer to a call that reaches it. Quiet is one anchored test on the raw text of `accord/config.yml` (`hook_mode:` then a space, `quiet` bare or in matching quotes, a comment only after a space), and any other spelling means full, so a doubt can only make accord louder. Quiet ends in three cases. A session that opens on a ticket's branch or worktree starts in full: the CLI wakes when the checkout's own branch templates name an id that has a file in `accord/tickets/`, and the launcher, which has no templates, hands any branch that holds a known id as a whole word to the CLI to decide; an unreadable config, branch or tickets folder means full. A detached HEAD stays quiet. Typing `/accord` in a quiet session wakes that session: the prompt-expansion hook answers with `additionalContext` holding the ruleset, the anchor and stage line of the active ticket (else the session line), one worktree clean's report after one fetch, and, for a person who switched accord off, the offer of `node .claude/accord.mjs on`, and writes `<common git dir>/accord-wake/<session_id>` (the common directory, as the off marker, so every worktree of the clone shares it). A woken session takes the full path for every later hook, in the CLI and in the launcher, which read the file with no process; another session in the same clone stays quiet; a second `/accord` prints `{}` and starts no git process; a session id that is not a plain name (letters, digits, `_` and `-`, one to 128 characters) names no file; files over 24 hours old are removed. `subagent-start` and `pre-tool-use` are unchanged by quiet, so an accord agent still gets its rules and the guards still run. That a UserPromptExpansion hook's `additionalContext` reaches the model was probed once, headless, with a random token that came back in the answer; the check in a real session belongs to the release's live checks. Parity exception: Claude Code only; quiet mode is a behaviour of Claude Code's hooks, and Cursor, Codex and Copilot have no hook to quiet.

**Personal switch.** `accord off` and `accord on` let one person silence accord's hooks and keep its pane from opening by itself in one clone, without touching the repository. `accord off` writes one file, the marker `accord-off` in the git common directory (a JSON file holding the time it was written, written to a temporary file and renamed), and nothing else: no `.claude/settings.local.json` and no `info/exclude` line, so Claude Code keeps loading the panel plugin and `/accord-panel` stays a known command. In 0.20.0 and 0.20.1 `off` also set `enabledPlugins["accord-panel@accord"]` to `false` in the checkout's local settings, so the host did not load the panel plugin and a typed `/accord-panel` was an unknown command; the live check of 0.20.1 found it, and the owner ruled on 2026-11-25 that `off` writes only the marker. `accord on` removes the marker. A marker from 0.20.0 or 0.20.1 records what that `off` did to the panel flag, and `on` undoes exactly that, as those versions did: a flag the person set to `true` since stays, a map `off` created is dropped only when empty, every other key and their order are kept, a local file that is not a JSON object or holds a panel entry that is not `true` or `false` is left as it is, and the file is written to a temporary file and renamed. A marker with no such record makes `on` open no settings file, and the marker goes last, so a failed write can be retried. Both run with no `accord/` folder and no pin check. The switch is a marker in the git common directory and not an `env` variable in `settings.local.json`: a session started in a linked worktree on Windows does not read the main checkout's local file, so an `env` switch would miss the worktrees where accord does its work, while the marker is one file that the main checkout and every linked worktree of the clone share, found with plain file reads (the `.git` folder or file, its `gitdir:` line and `commondir`) and no process. While it exists, every accord hook prints nothing, exits 0 and starts no git process, through the launcher before any cache path and through the CLI, with one exception, the `verification.md` write guard (below), and the pane stays closed at session start and at attach (`/accord-panel` still opens it). A person learns the switch from the session: a full-mode session start ends with one line naming `node .claude/accord.mjs off` and `on` and saying an agent runs either only when the person asks, and `accord worktree check` prints one line, `accord is switched off for you in this clone`, with the next action of offering to switch accord back on and running it only on the person's yes (the exit code is as before, and a ticket session is still refused first); that a real agent follows that next action is part of the live checks. Typing `/accord` while off wakes that session as in a quiet repository and leaves the marker. The switch silences hooks only: no gate, check or CI job reads it, and while accord is off for a person the executor's dispatch check is silent for that person too. The `verification.md` write guard is not (decision of the review of 0.20.0, WR-05): the marker is per clone, not per person or per session, so it also covers every ticket worktree and every agent a session starts; the guard costs no process (it decides from stdin alone, and its hook only runs for that one path), and it is the one hook that holds the core value, independent verification before done. While off, the launcher reads a `pre-tool-use` call's stdin once and hands exactly a Write, Edit or MultiEdit of `accord/tickets/<id>/verification.md` to the CLI, which denies it unless the `accord-verifier` writes it and prints nothing for any other call. A full off that also silences this guard is a decision for the owner to take, not a default. The wake file of a typed `/accord` lives in the common git directory beside the marker (review WR-02), so a session that moved into a linked worktree is woken for the launcher and the CLI alike. Parity exception: Claude Code only; the switch silences Claude Code's hooks and pane, and the other runtimes have none.

**Start-up cost.** Phase 08.9.2 cuts what a command does before it answers, with the output unchanged byte for byte (each change sits behind an oracle test that keeps the old path in the test). `fnv1a64` runs on two 32-bit halves with no BigInt, as one implementation that `contentHash` calls, with the same `fnv1a64:<16 hex>` text. A command parses each distinct file once: `loadSnapshot(input, { memo })` takes a per-command memo keyed by kind, path and text and shares it between the snapshots the command builds (the view, the checkout and the default ref); it lives in the command's process and is never written to disk. `status` and `dashboard` read a dropped ticket for its frontmatter only; the list is `dropped` alone, because a done archived ticket's body feeds the `blockedBy` of the tickets that depend on it and the epic counts, so archived tickets are read in full (the oracle found that difference, and the list is one constant, `DISPLAY_FRONTMATTER_ONLY` in `packages/cli/src/run.ts`); `status --all`, `lint`, the gates, `show`, `next` and the hooks keep the full parse. One-ticket commands read their own neighbourhood: `gate ready`, `gate plan`, `anchor [id]`, `show <id>` without `--approval`, the executor dispatch check and an epic role's SubagentStart read the config, every file under `accord/` outside `accord/tickets/`, and only the files of the target, its parent epic and the transitive `depends_on` of each ticket read, with every other ticket known by its file name. An oracle holds their output byte for byte equal to the full load's over a fixture with an epic, siblings with lessons, dependencies that are unfinished, finished, dropped, unknown and two steps away, a cycle, an archived ticket, lane S and R tickets and a claim branch on origin only, and a count of ticket files opened is the same at 5 and at 50 extra tickets (a story's `show` opens 6, where the full load opened 66 and 156). `gate done` keeps the full load (review of 0.20.0, CR-01): `gate.test-untraced` holds each report case against the `@test:` tags of every ticket, so a narrow Done reported the cases another ticket traces as untraced; a second oracle with a test report compares the three gates, the anchor and `show` with the full load. The one fallback taken: a claim copy that names a parent or dependency outside the narrow set makes that `show` call read the full claim view, and the narrow set is the ids the closure reached, listed or not, so a ticket filed only on its claim branch is found. The default branch's copy of every listed ticket is still read in one `git cat-file` batch, a git read and not a file open, so that batch grows with the ticket count. `dashboard` and `status` still read every ticket (D-08): each row shows what its ticket's records say. `accord dashboard --json` also carries `currentDetail`, the object `accord show <id> --json` prints for the ticket in flight, built by the same function and placed after `current`, and `accord dashboard --no-fetch` draws from the refs already in the clone, starts no fetch and prints no `offline` key. Nothing here is a wall-clock assertion in a test (Phase 08.9 D-02); the release measures and records the times.
