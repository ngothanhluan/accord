**I want to** run one command that installs accord's role workflows into every skill
directory my runtime reads, and run it again without it touching a byte,
**so that** the workflow my agent follows is the one accord ships, and I can tell at a

<assumption_delta_decision>
**The noun that is now primary:** `skill definition`. `role` is one variant of it.

**Decision: promote.**

The deterministic detector fired on "a second run is a no-op" and "two techniques render
alongside the roles". Both point at the same generalization: this phase produces three
shapes of rendered artifact — a role `SKILL.md`, a bundled technique, and a bundled
reference brief — and D-110 puts all three under one drift rule, D-111 gives all three the
same marker, and D-112 gives all three the same four-state sync report. A model keyed on
"role" cannot express the technique or the brief without a second mechanism beside it.

So the primary key of the data model is the **definition key** — the posix path of the
source file relative to `packages/core/skills/`, e.g. `designer/SKILL.md`,
`shared/prototype.md`, `dev/debug.md`. `kind: role | technique | reference` (D-106) is a
field on the definition, not a separate table. `role` survives in exactly two narrow
places and nowhere else: as the directory segment of a role definition's key, and as the
axis `config.roles` filters on.

This is not new debt: D-106 already put `kind` on the source frontmatter, so the
generalization is in the locked decisions. This block records that the plan honours it
rather than re-introducing a role-shaped primary key underneath it.

**The invariant test that encodes the generalized intent** is Task 3's
`every rendered artifact carries a marker whose stored hash equals a hash recomputed over
the file with that line removed` — it iterates the whole render output, not the SKILL.md
subset. It goes red the instant a future phase adds an artifact shape that skips the
marker.
</assumption_delta_decision>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `config.yml` -> `skillTargets()` | Repository-authored YAML steers which roles and which directories are written. Validated by `config.schema.json` (ajv, `additionalProperties: false`, closed enums) before `skillTargets()` sees it. |
| `skillTargets()` -> filesystem write | The only place in this phase where accord puts bytes into a user's repository. |
| Existing on-disk file -> `sync`'s compare | Whatever is already at the destination — possibly hand-edited, possibly a link, possibly created by something else. |

**Surfaces that are absent, stated plainly rather than padded:** this phase authenticates
nobody (ASVS V2 n/a), holds no session (V3 n/a), enforces no authority of its own beyond the

database — so injection, XSS, SQLi, CSRF, and session-fixation entries would be fiction.
The content hash is a drift detector; it is explicitly **not** a cryptographic control
(V6 n/a).
