imported read-side only, and `.github/workflows/ci.yml` is hand-written. There is no analog to copy,
so the workflow text is authored as a source literal and its shape is asserted by parsing it back.

Purpose: the contract stops depending on anyone remembering to run the gates.

- **A-08 — the workflow text is a TypeScript literal in `packages/core/src/scaffold/workflow.ts`, not a
  `packages/core/templates/*.yml` asset.** Decided, not left open. Three reasons, in descending weight:
  (1) `packages/core/test/templates.test.ts:119-124` asserts that no template contains the two-brace
  sequences a GitHub Actions expression is written with; a workflow asset would fail that test on the line
  that reads the base sha. (2) `gen-templates.mjs:7` filters `/\.(md|html)$/`, so a `.yml` dropped into that
  directory is silently absent from the generated record and the drift test at `templates.test.ts:128-135`
  would then compare two lists that already agree. (3) The text interpolates the package name and version,
  so it is a function of build facts, not a static document.
  *Alternative:* widen the codegen regex, exempt the new key from the three whole-record loops in
  `templates.test.ts`, and keep a placeholder-substitution step. Three edits to buy one file move.

- **A-09 — a ticket DELETED by the diff is not gated.** `git diff --name-only` lists deletions, and
  `accord gate done <id>` on a ticket that no longer exists reports `gate.ticket-unknown` at error and exits
  1 — so removing an obsolete ticket would fail the pull request that removes it. `--diff-filter=d`
  (lowercase, "exclude deleted") drops them. D-137 does not settle this.
  *Alternative:* gate deletions too and treat a removed ticket as a failure to be justified.

- **A-10 — the exit code is the worst of `lint` and every gate, and `lint` never aborts the run before the
  gates.** A pull request with both a lint error and a gate failure should report both, so neither step
  short-circuits the other; the script accumulates a code and exits with it. D-138's "exits 0" is about the
  no-ticket case specifically, and that case still carries whatever `lint` returned.
  *Alternative:* `set -e` and stop at the first failure, reporting one problem per push.

- **A-11 — the workflow pins `runs-on: ubuntu-latest` and `node-version: 24`.** One runner and one Node
  version: this is a user's repository, not accord's own matrix. Node 24 is the active LTS and is what
  `.github/workflows/ci.yml` uses for build jobs; `engines` floors at 22.12.
  *Alternative:* a matrix, which triples a user's minutes to test accord rather than their code.
</surfaced_assumptions>

It returns one template literal. Purity applies: no Node built-in, no serialiser — the document is written

Document structure, top level, in this key order:

- `name: accord`
- `on:` with exactly one child key, `pull_request:` and an empty value (D-136 — no `push`, no

The job has three steps:

1. `uses: actions/checkout@v7` with a `with:` mapping containing `fetch-depth: 0`. Carry a YAML comment on
   that line stating why: the diff below resolves `<base>...HEAD`, and the default shallow checkout does not
   contain the base commit, so the diff would fail or come back empty and every gate would be silently
   skipped.
2. `uses: actions/setup-node@v7` with `with:` containing `node-version: 24`.
3. A `run:` step named `lint and gate`, carrying `shell: bash`, an `env:` mapping with the single key `BASE`
   set to the GitHub expression `github.event.pull_request.base.sha`, and a block-scalar `run: |` script.
   The expression appears in the `env:` mapping and nowhere else — it must never appear inside the script
   body, because an expression is expanded into the script text before the shell reads it.

The script body, in this order, each as its own line:

- `set -uo pipefail` — deliberately not `-e`; the script accumulates an exit code so a lint failure and a
  gate failure are both reported (A-10).
- `code=0`
- an invocation of the pinned CLI with the `lint` argument, suffixed with `|| code=1`
- `tickets=$(git diff --name-only --diff-filter=d "$BASE"...HEAD | grep -E '^accord/tickets/[^/]+\.md$' || true)`
  — `--diff-filter=d` excludes deletions (A-09); the `[^/]+` is what keeps
  `accord/tickets/<id>/verification.md` out of the list while `accord/tickets/<id>.md` stays in;
  `|| true` keeps a zero-match `grep` from being read as a failure.
- an `if [ -z "$tickets" ]; then` branch that echoes exactly
  `no ticket file changed in this pull request - nothing to gate` and then `exit $code`, closed with `fi`
  (D-138 — the job runs, says why, and reports a result).
- a `while IFS= read -r file; do ... done <<< "$tickets"` loop — a here-string, not a pipe, so the loop body
  runs in this shell and its assignment to `code` survives. Inside: `id=${file#accord/tickets/}`,
  `id=${id%.md}`, then the pinned CLI with `gate done "$id"` suffixed with `|| code=1`. `"$id"` is quoted at
  the call site.
- `exit $code`

The pinned invocation is `npx --yes ${pkgName}@${version}` in both places, interpolating the two parameters.
This is the one place in the repository where the string `npx` may be written, and it is inside emitted text,
never a spawn (PITFALLS section 12, `spawn-surface.test.ts`).

earns its comment because a reader would otherwise delete it); say nothing about what it leaves out. The
reasoning for both omissions belongs in `workflow.ts`'s module header, above the returned literal, where no

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub event payload → runner shell | `github.event.*` fields are attacker-influenced on a pull request from a fork |
| repository file names → shell arguments | a ticket file name becomes a `gate done` argument on the runner |
| npm registry → runner | `npx --yes <package>@<version>` downloads and executes code on every pull request |
| runner → repository | the job's `GITHUB_TOKEN` scope decides what a compromised step could do |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-07-11 | Elevation of privilege | the `run:` script in the generated workflow | high | mitigate | No GitHub Actions expression appears in any `run:` body; the one value the script needs is passed through `env: BASE:` and read as `"$BASE"`. An expression is substituted into the script text before the shell parses it, so an attacker-controlled field there is code execution on the runner. Asserted by the Task 2 case that scans every `run` string for the expression delimiter. |
| T-07-12 | Tampering | ticket file name → `gate done` argument | medium | mitigate | The id is derived by prefix and suffix stripping and passed quoted as `"$id"`, so no word-splitting or glob expansion reaches the argument. The `grep -E '^accord/tickets/[^/]+\.md$'` filter bounds the shape further, and `accord`'s own id pattern rejects anything outside `[A-Za-z0-9][A-Za-z0-9._-]*` with `gate.ticket-unknown`. |
| T-07-13 | Elevation of privilege | job token scope | medium | mitigate | `permissions: contents: read` at the workflow level, deep-equality asserted in Task 2, so an added write scope fails the suite. |
| T-07-14 | Tampering | the diff the gates are computed from | high | mitigate | `fetch-depth: 0`. On the default shallow checkout `git diff <base>...HEAD` cannot resolve the base commit, so the ticket list would be empty and every pull request would report a green job having gated nothing — a gate that silently passes is worse than no gate. Asserted numerically in Task 2. |
| T-07-15 | Denial of service | the job never reporting | high | mitigate | D-138: no `paths:` filter anywhere, and the no-ticket branch echoes and exits rather than being skipped. A skipped job leaves a required status check pending forever. Asserted by the `paths:` absence criterion in Task 1. |
| T-07-16 | Tampering | `npx --yes` fetching the CLI on every run | medium | accept | Accepted with a named compensator: the version is an exact pin (D-139), equal by construction to the `config.yml` pin, and a drifted workflow is a hard refusal rather than a silent skew. Removing the registry dependency means requiring a `package.json` in the user's repository, which the independence constraint forbids. Integrity beyond the pin belongs to npm and to Phase 9's trusted publishing. |
| T-07-17 | Repudiation | a deleted ticket escaping its gate | low | accept | A-09: `--diff-filter=d` means removing a ticket is not gated. The removal is still in the diff a human reviews, and gating it would fail the very pull request that removes it. |
| T-07-SC | Tampering | npm/pip/cargo installs | n/a | accept | This plan adds no dependency to this repository. `npx --yes` inside the emitted text is executed on a user's runner, not here, and is covered by T-07-16. |
