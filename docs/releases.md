# Release notes

Each section lists what changes for tickets in flight and for repositories pinned to an older accord. A release pull request copies the `## Unreleased` section into its `release:` commit body and renames the section to the release version.

## Unreleased

Every rule below has a cut-off constant in `packages/core/src/round/pin.ts`, and each one holds the first release that ships the rule. The constants read `0.4.1` while `v0.4.1` is not yet tagged.

- Discuss stage (from `DISCUSS_FROM`, 0.4.1): a lane M ticket claimed under that pin or later needs `accord/tickets/<id>/discuss.md`, with every gray area mapped to a Decision, before `accord gate ready` passes. The areas are the list items at the start of a line under one `## Gray areas` heading; a repeated heading, and a line with a group and a Decision but no gray area text, fail the gate. A ticket claimed under an older pin, in flight when the repository upgrades, needs none.
- Approach critic (from `APPROACH_CAP_FROM`, 0.4.1): the critic runs at most two rounds, and no Ruling raises the cap. A third round is refused with the findings still open. An open `risk: data-loss` or `risk: security` finding blocks the approval, in every round of such a ticket and when round 2 reports no findings or a verdict ends the loop: `accord show <id> --approval --short` lists it under `## Blocking findings`, and `accord approve` refuses with exit 1 and names it until the owner's no with a Correction closes the cycle. This is a change in public behaviour: `accord approve` read no approach record before 0.4.1, and a ticket claimed under an older pin still approves as before. A ticket claimed under an older pin keeps five rounds and its stop, even when its approach critique begins after the upgrade, so no round is lost.
- Approval (from 0.4.1, a skill change shipped by `accord upgrade`): `accord-intent` asks no separate yes. The owner approves once, from `accord show <id> --approval --short`, which prints the Intent, one line per criterion, the Decisions, the risks and the ticket path. `accord show <id> --approval` prints the full sections as before.
- Repositories pinned to 0.4.0: a repository pinned to 0.4.0 keeps the 0.4.0 answers and skills until `accord upgrade`, which moves the pin and regenerates the skills. Every Phase 3 rule reads the pin at the ticket's claim commit: the oldest `claim: <id>` commit that is not on the default branch, else the oldest one overall. With no claim commit it reads the pin at the commit that added the ticket only when that commit is not on the default branch; a ticket queued on the default branch and worked after the upgrade with no claim commit gets the new rules. It reads the working-tree pin only when git has no commit that tells when work began (no git, no HEAD, no claim commit and no such adding commit). When git fails reading the pin, the new rules apply and the finding or refusal names the git error. So a ticket claimed before the upgrade keeps every old rule until it is done and the upgrade changes nothing for it.
